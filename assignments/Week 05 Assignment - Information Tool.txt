WEEK 5 ASSIGNMENT — BUILD AN IN-MEMORY INFORMATION TOOL

This week you'll build a small text-based tool for keeping track of something you choose, like the books on your to-read list or when each of your plants needs watering. The program stores records while it runs, lets a user add and explore them, and tells the user clearly what's going on at every step.

You can work in the companion Colab notebook:
https://colab.research.google.com/github/clarissalittler/cs160-course-site/blob/summerwork/assignments/Week%2005%20Assignment%20-%20Information%20Tool.ipynb

Or you can write the same ordinary Python in OnlineGDB, another browser-based interpreter, or a local editor. Nothing in the notebook is Colab-specific, so the code copies cleanly into one .py file.

== Step 1: Choose a topic and schema ==

Each record needs at least four named fields, including at least one numerical one. For example:

  - Community resources: name, area, category, cost
  - Books: title, author, genre, pages
  - Games: title, platform, genre, hours_played
  - Plants: name, location, care_type, days_between_watering
  - Recipes: name, meal, main_ingredient, minutes

Write a small data dictionary listing every key, its Python type, what it means, whether it's required, and what a missing value means. Do this before you write code. I know, everyone wants to skip it! But once the code exists, changing what a record holds means changing every function that touches it.

For required text fields, check for a blank or whitespace-only answer before adding the record, and ask again if needed. The starter shows this for name. Its numerical input expects number-shaped text, and you don't have to handle what happens when float() gets something that isn't a number. Just mention that limitation in your tests.

== Step 2: Build the tool ==

Store the data as a LIST OF DICTIONARIES. Use a while loop to show this menu until the user quits:

  1. Add a record
  2. Display all records
  3. Filter or search records
  4. Show a summary
  5. Quit

The program should always show the current record count, and it should say something sensible when the collection is empty or a search finds nothing, rather than printing a blank line and leaving the user to wonder.

== Step 3: Test the interface ==

Ask another person, or use a provided persona, to complete one task without any explanation from you. Write down one place they paused, misread a label, or expected something different. Make one change based on what you saw.

== Requirements ==

Your program must:

  1. Run from top to bottom without errors
  2. Store records as a list of dictionaries with consistent keys
  3. Have at least four fields per record, including one numerical field
  4. Let a user add records through a while-loop menu with a clear way to quit
  5. Display every record with descriptive labels
  6. Include at least one working filter or search
  7. Include a summary with a record count and at least one numerical total, average, minimum, or maximum
  8. Handle an empty collection and a zero-match filter explicitly
  9. Use functions for at least three distinct jobs, such as adding, filtering, summarizing, or displaying
 10. Deliberately leave out at least one field that would be unnecessary or too sensitive for what the tool does

Tuples and tuple unpacking are Unit 5 tools too, and you're welcome to use them wherever they fit: a returned pair, enumerate(), &c. But the main records need to be dictionaries, because named fields and a schema that can grow are exactly what this assignment is checking.
