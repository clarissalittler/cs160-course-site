Lesson 5 - Software as an Evolving Artifact

At the end of this lesson, you will be able to:

  • Turn a requirement into a concrete acceptance example.
  • Separate loading, processing, display, and saving responsibilities.
  • Use repeatable tests to protect behavior during refactoring.
  • Maintain a small change log and review copied or AI-generated code responsibly.

“It ran once” is a beginning

Real software changes. A file gains a column. A user asks for a new filter. A vague label confuses someone. A library update changes behavior. A teammate must understand code written months ago. Software engineering includes the practices that let a program remain useful through those changes.

Requirements need acceptance examples

A requirement such as “the program can filter resources by area” is helpful but incomplete. An acceptance example makes success observable:

Given three records, two with area North and one with area Central,
when the user filters for North,
then the program displays the two North records, reports “2 matches,” and does not display the Central record.

Also specify an empty result: filtering for South displays “No matching resources” without changing or deleting records.

Separate responsibilities

A single hundred-line menu function may run, but every change risks unrelated behavior. Give major jobs names:

def load_resources(filename):
    # Read CSV, convert fields, and return records.
    pass

def save_resources(filename, resources):
    # Write all records using the documented schema.
    pass

def filter_by_area(resources, requested_area):
    matches = []
    for resource in resources:
        if resource["area"].lower() == requested_area.lower():
            matches.append(resource)
    return matches

def show_resources(resources):
    # Display labeled records or an explicit empty state.
    pass

def show_menu(record_count):
    # Display state and available actions.
    pass

This is separation of concerns. Loading knows file format. Filtering knows the selection rule. Display knows how to communicate. The main menu coordinates those functions.

Tests protect behavior

A regression is old behavior that breaks after a change. A repeatable test set helps reveal regressions:

sample = [
    {"name": "Tool Library", "area": "North", "cost": 0.0},
    {"name": "Repair Cafe", "area": "Central", "cost": 0.0},
    {"name": "Bike Workshop", "area": "North", "cost": 10.0},
]

assert len(filter_by_area(sample, "North")) == 2
assert len(filter_by_area(sample, "north")) == 2
assert len(filter_by_area(sample, "South")) == 0
assert len(filter_by_area([], "North")) == 0

print("Filter tests passed.")

assert condition stops with an AssertionError if the condition is false. These are small automated checks, not a complete testing framework. They are valuable because they can be rerun after every revision.

File behavior also needs tests: missing file, empty file, one valid row, malformed numeric field, save then reload, and a filename without write permission. Some environments make permission tests difficult; document what you could and could not test.

Refactor without changing promised behavior

Refactoring changes code structure without intentionally changing its external behavior. You might extract repeated display code into a function, rename an unclear variable, or separate a calculation from input. Run the same acceptance examples before and after. If results change, decide whether you found a bug, introduced one, or actually changed a requirement.

Readable documentation has several levels

  • Descriptive names explain values and actions locally.
  • Comments explain non-obvious reasons and assumptions.
  • A function contract explains inputs, result, effects, and failure behavior.
  • A README explains purpose, setup, files, how to run, and known limitations.
  • A data dictionary explains fields, types, units, missing values, and provenance.

Comments that merely repeat syntax become stale. Document why cost = None is preserved, not that cost is assigned.

Version history is an explanation over time

Version control systems such as Git record changes, authorship, and messages. You do not need a GitHub account to practice the underlying discipline. Keep dated copies or a lightweight change log:

A useful change note says what and why, not “stuff” or “final final version.”

Code review is a conversation about evidence

A reviewer can check whether requirements are covered, names communicate intent, errors preserve data, file operations are safe, and tests include boundaries. Constructive feedback points to a behavior and consequence: “When there are no records, the average divides by zero; add an empty-state test” is more useful than “This is bad.”

Copied or AI-generated code remains your responsibility

Record where substantial borrowed code came from and follow its license or course rules. For AI-generated code, record the prompt or assistance when required, inspect every file/network operation, remove techniques you cannot explain, and test against the stated requirements. A confident explanation from a tool is not evidence that the program is correct or safe.

Maintenance studio. Take a working collection or file program and:

  1. write three acceptance examples, including an empty or failure case;
  2. separate at least three responsibilities into functions;
  3. create at least four repeatable checks;
  4. refactor one unclear or repeated section;
  5. ask another person for one evidence-based review comment;
  6. record the revision in a change log; and
  7. cite any substantial copied or generated code.

End of Unit 6: You can preserve records in files, audit a CSV, use documentation and dependencies deliberately, recognize a basic database query, and revise software while tests protect its behavior.
