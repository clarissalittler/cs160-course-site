Lesson 3 - Shape a Clear Text Interface

By the end of this lesson, you will be able to:

  • Create multi-line output with triple-quoted strings.
  • Insert changing values into a multi-line f-string.
  • Turn a collection of words into readable text with join.
  • Design a small command vocabulary that is visible, consistent, and keyboard-friendly.

Three quotes make room for multiple lines

So far, when we've wanted several lines of output, we've written several print() calls in a row, like the menu in the Unit 5 catalog. That works, but it gets clunky fast. A title screen or an event card has a shape, and when it's chopped into ten separate print() calls it's hard to see what the result will look like just by reading the code.

A regular string can't help, because a string that starts with one quotation mark has to end on the same line; hit Enter partway through and Python gives you a SyntaxError. But a string wrapped in three quotation marks can run across several lines. This is handy whenever the arrangement of the lines is part of the message:

announcement = """
COMMUNITY RADIO 91.7 FM
Tonight at 8: Songs for a Rainy Bus Ride
Requests open after the weather report.
"""

print(announcement)

What you see in the code is pretty much what you get on the screen, line breaks and all. (Because the text starts on the line after the opening """, there's a blank line before COMMUNITY RADIO when it prints. That's usually fine.)

Triple-quoted strings are ordinary strings that happen to contain line breaks, so everything from Unit 5 still works on them.

Multi-line f-strings can display changing data

event = {
    "title": "Repair Café",
    "when": "Saturday, 10:00–2:00",
    "where": "Community Center Studio",
    "tags": ["repair", "tools", "all ages"],
    "cost": 0,
}

tag_words = ", ".join(event["tags"])

card = f"""
+--------------------------------------+
EVENT: {event["title"]}
WHEN:  {event["when"]}
WHERE: {event["where"]}
TAGS:  {tag_words}
COST:  ${event["cost"]}
+--------------------------------------+
"""

print(card)

Put an f in front of the triple quotes and you get the best of both: the shape of a triple-quoted string and the fill-in-the-blanks of an f-string, which you've been using since Unit 3. Everything inside curly braces gets evaluated and dropped into place, so {event["title"]} becomes Repair Café and {tag_words} becomes repair, tools, all ages.

Notice that the list of tags gets turned into a string before the f-string, on its own line. You could cram {", ".join(event["tags"])} right into the braces and it would work, but a card template is easier to read when the braces only hold simple names and lookups. Do the fiddly work first, give it a name, then use the name.

The fixed labels and the border come from the f-string. The details come from the event dictionary. Hand it a different dictionary and the same display works again. That's the same idea as the connections code in Lesson 2: the code describes the shape, the data fills in what varies.

join turns several words into one string

access_features = ["step-free entrance", "captions", "quiet room"]
print("ACCESS: " + "; ".join(access_features))

This puts a semicolon and a space between each pair of neighbors. It reads a little backwards, since the separator is the thing you call the method on and the list is the argument, and it confuses nearly everyone the first time. I still have to think about it. Why is it like this? Python's designers wanted join to work on any collection of strings (a list, a tuple, the keys of a dictionary, &c.), and the one thing all those uses have in common is the separator string. So join lives on the string. join doesn't change the list; it makes one new string for display.

Why not just print(access_features)? Try it! You'll get ['step-free entrance', 'captions', 'quiet room'], brackets, quote marks and all. That's Python showing you what the data is, which is great for debugging and not so great for the people using your program. (One catch: every element has to already be a string.)

Put repeated presentation in a function

def show_event(event):
    tag_words = ", ".join(event["tags"])

    if event["cost"] == 0:
        cost_words = "free"
    else:
        cost_words = f'${event["cost"]}'

    print(f"""
EVENT: {event["title"]}
WHEN: {event["when"]}
WHERE: {event["where"]}
TAGS: {tag_words}
COST: {cost_words}
""")

This is the card from before, wrapped in a function so any event can use it, with one improvement: an if that says "free" instead of $0. Nobody reads $0 and thinks "great, it's free!" as fast as they read the word free. Small decisions like that are what the whole display is for.

This function's job is presentation. It reads the event record but never edits the title, tags, or cost. Why keep that wall up? Because it means you can change how things look without any risk of changing what's stored, and the other way around. If someone wants the cost shown before the tags, you edit one function. If the data is wrong, you know not to go looking in the display code. A resource directory, a recipe collection, a character roster, or a travel guide could all keep the same wall between data and display.

A small program: scaling a recipe

Here's a program that pulls together a surprising amount of what we've done so far. A recipe is stored as a dictionary, the ingredients are a list of tuples, and the program asks how many servings you want and rescales everything:

recipe = {
    "title": "Weeknight Black Bean Soup",
    "serves": 4,
    "ingredients": [
        ("black beans, drained", 2, "cans"),
        ("vegetable broth", 3, "cups"),
        ("onion, chopped", 1, "whole"),
        ("ground cumin", 1.5, "tsp"),
    ],
}

print(f"""
RECIPE: {recipe["title"]}
The original recipe serves {recipe["serves"]}.
""")

servings = int(input("How many servings do you want? "))
while servings < 1:
    print("Please enter a whole number of at least 1.")
    servings = int(input("How many servings do you want? "))

scale = servings / recipe["serves"]

print(f"INGREDIENTS FOR {servings}:")
for name, amount, unit in recipe["ingredients"]:
    print(f"  {round(amount * scale, 2)} {unit} {name}")

Each ingredient is a tuple of three things in a fixed order (name, amount, unit), the job Unit 5 said tuples are good for, and the loop unpacks each one into three readable names. The heading is a multi-line f-string, and the validation loop is the one from Unit 4.

The arithmetic is the kind where it helps to say the units out loud, like in Unit 3: scale means "servings wanted per serving in the original," so 6 servings of a 4-serving recipe multiplies every amount by 1.5. The one new built-in, round(amount * scale, 2), rounds to two decimal places so you don't get amounts like 1.125 teaspoons. Ask for 6 servings and you get:

INGREDIENTS FOR 6:
  3.0 cans black beans, drained
  4.5 cups vegetable broth
  1.5 whole onion, chopped
  2.25 tsp ground cumin

Two things in that output are a little funny. First, why 3.0 cans and not 3? Because / in Python always gives back a float, even when the division comes out even, and a float prints with a decimal point.

Second: "1.5 whole onion"? The arithmetic is completely right! The program just doesn't know that people buy onions one at a time, or that nobody on earth measures cumin to the hundredth of a teaspoon. A cook would fix both of those without even thinking about it. The program can't, because nobody told it how onions are sold. To fix it, you'd have to write a little kitchen knowledge into the code, like "round onions up to a whole number."

A command vocabulary is an agreement

An interactive text program understands exactly the comparisons its author wrote and nothing else. When someone types a command, the program is just checking command == "next", command == "save", and so on down the line. There's no understanding happening, only string comparison. That means the person at the keyboard has to guess the exact words you chose, unless you tell them. So let's make the vocabulary visible:

def show_help():
    print("Commands: next, previous, details, save, help, quit")

command = input("Choose a command: ").strip().lower()

.strip().lower() makes capitalization and stray spaces harmless. It doesn't make the computer understand English. If the program checks for next, then show me another one is still just a different string, unless you decide to support it.

A good vocabulary is small, and it's consistent: if one screen uses quit, don't make another use exit. It uses plain words people might guess on their own. And it's always one help away. (You might have played old text adventure games, the kind where you typed go north or take lamp. Part of what made them frustrating was guessing which verbs the game knew. Did it want take, get, or grab? Showing the list up front avoids the whole guessing game.)

Clarity matters more than decoration

Borders and text art can be fun, but a row of forty dashes is tedious through a screen reader ("dash dash dash dash...") and wraps into a jumble on a narrow phone screen. Use explicit labels like EVENT, WHEN, and COST, and don't signal status only through color, emoji, or spacing. A good test for any decoration: take it away and see if anything important went with it.
