Lesson 3 - Shape a Clear Text Interface

By the end of this lesson, you will be able to:

  • Create multi-line output with triple-quoted strings.
  • Insert changing values into a multi-line f-string.
  • Turn a collection of words into readable text with join.
  • Design a small command vocabulary that is visible, consistent, and keyboard-friendly.

Triple-quoted strings

So far, when we've wanted several lines of output, we've written several print() calls in a row, like the menu in the Unit 5 catalog. That works, but it gets clunky fast. A title screen or an event card has a shape, and when it's chopped up into ten separate print() calls it's hard to tell what it's going to look like just by reading the code.

A regular string can't help us here, because a string that starts with one quotation mark has to end on the same line. If you hit Enter partway through, Python gives you a SyntaxError. But a string wrapped in three quotation marks is allowed to run across several lines:

announcement = """
COMMUNITY RADIO 91.7 FM
Tonight at 8: Songs for a Rainy Bus Ride
Requests open after the weather report.
"""

print(announcement)

What you see in the code is what you get on the screen, line breaks and all. (Because the text starts on the line after the opening """, there's a blank line before COMMUNITY RADIO when it prints. That's usually fine.)

Under the hood, a triple-quoted string is just an ordinary string that happens to have line breaks inside it, so everything from Unit 5 still works on it.

Multi-line f-strings

event = {
    "title": "Repair Café",
    "when": "Saturday, 10:00–2:00",
    "where": "Community Center Studio",
    "tags": ["repair", "tools", "all ages"],
    "cost": 0,
}

tag_words = ", ".join(event["tags"])

card = f"""
+--------------------------------------+
EVENT: {event["title"]}
WHEN:  {event["when"]}
WHERE: {event["where"]}
TAGS:  {tag_words}
COST:  ${event["cost"]}
+--------------------------------------+
"""

print(card)

So what if some of the lines need to change, like the name of an event? Put an f in front of the triple quotes and you get the best of both: the shape of a triple-quoted string and the fill-in-the-blanks of an f-string, which you've been using since Unit 3. Everything inside curly braces gets evaluated and dropped into place, so {event["title"]} becomes Repair Café and {tag_words} becomes repair, tools, all ages.

You might have noticed that the list of tags gets turned into a string before the f-string, on its own line. You could cram {", ".join(event["tags"])} right into the braces and it would work fine, but personally I find a template like this much easier to read when the braces only hold simple names and lookups. So do the fiddly part first, give it a name, and then use the name.

The labels and the border come from the f-string, and the details come from the event dictionary. That means if you hand it a different dictionary, the same display works again. It's the same idea as the connections code in Lesson 2: the code describes the shape, and the data fills in whatever varies.

join

access_features = ["step-free entrance", "captions", "quiet room"]
print("ACCESS: " + "; ".join(access_features))

This puts a semicolon and a space between each pair of neighbors. Now, if this reads a little backwards to you, you're not alone! The separator is the thing you call the method on and the list is the argument, which confuses nearly everyone the first time. I still have to stop and think about it. So why is it like this? Python's designers wanted join to work on any collection of strings (a list, a tuple, the keys of a dictionary, &c.), and the one thing all those uses have in common is the separator. So join lives on the string. And like the string methods from Unit 5, it doesn't change the list at all, it just makes one new string.

Why not just print(access_features)? Go ahead and try it! You'll get ['step-free entrance', 'captions', 'quiet room'], brackets, quote marks and all. That's Python showing you what the data is, which is great when you're debugging and not so great for the people using your program. (One catch with join: every element has to already be a string, or you'll get a TypeError.)

Display functions

def show_event(event):
    tag_words = ", ".join(event["tags"])

    if event["cost"] == 0:
        cost_words = "free"
    else:
        cost_words = f'${event["cost"]}'

    print(f"""
EVENT: {event["title"]}
WHEN: {event["when"]}
WHERE: {event["where"]}
TAGS: {tag_words}
COST: {cost_words}
""")

This is the card from before, wrapped up in a function so that any event can use it, with one improvement: an if that says "free" instead of $0. It's a tiny thing, but people read the word free a lot faster than they read $0 and figure out what it means.

Notice that this function only reads the event record. It never changes the title, the tags, or the cost. Why be so strict about that? Because it means you can change how things look without any risk of changing what's stored, and the other way around. If someone wants the cost shown before the tags, you edit one function. If the data is wrong, you know you don't need to go digging through the display code to find the problem.

A small program: scaling a recipe

Okay, here's a program that pulls together a surprising amount of what we've done so far. A recipe is stored as a dictionary, the ingredients are a list of tuples, and the program asks how many servings you want and then scales everything:

recipe = {
    "title": "Weeknight Black Bean Soup",
    "serves": 4,
    "ingredients": [
        ("black beans, drained", 2, "cans"),
        ("vegetable broth", 3, "cups"),
        ("onion, chopped", 1, "whole"),
        ("ground cumin", 1.5, "tsp"),
    ],
}

print(f"""
RECIPE: {recipe["title"]}
The original recipe serves {recipe["serves"]}.
""")

servings = int(input("How many servings do you want? "))
while servings < 1:
    print("Please enter a whole number of at least 1.")
    servings = int(input("How many servings do you want? "))

scale = servings / recipe["serves"]

print(f"INGREDIENTS FOR {servings}:")
for name, amount, unit in recipe["ingredients"]:
    print(f"  {round(amount * scale, 2)} {unit} {name}")

Each ingredient is a tuple of three things in a fixed order (name, amount, unit), the job Unit 5 said tuples are good for, and the loop unpacks each one into three readable names. The heading is a multi-line f-string, and the validation loop is the one from Unit 4.

The arithmetic is the kind where it helps to say the units out loud, like in Unit 3: scale means "servings wanted per serving in the original," so 6 servings of a 4-serving recipe multiplies every amount by 1.5. The one new built-in, round(amount * scale, 2), rounds to two decimal places so you don't get amounts like 1.125 teaspoons. Ask for 6 servings and you get:

INGREDIENTS FOR 6:
  3.0 cans black beans, drained
  4.5 cups vegetable broth
  1.5 whole onion, chopped
  2.25 tsp ground cumin

Two things in that output are a little funny. First, why 3.0 cans and not 3? Because / in Python always gives back a float, even when the division comes out even, and a float prints with a decimal point.

Second: "1.5 whole onion"? The arithmetic is completely right! The program just doesn't know that people buy onions one at a time, or that nobody on earth measures cumin to the hundredth of a teaspoon. A cook would fix both of those without even thinking about it. The program can't, because nobody told it how onions are sold. To fix it, you'd have to write a little kitchen knowledge into the code, like "round onions up to a whole number."

If that sounds familiar, it should. It's the same problem as Robodebt in Unit 5's last lesson: a program only knows the facts somebody wrote down. The difference is that here the cost is one confused cook and not a debt notice.

Command words

Here's something that's easy to forget when you're the one who wrote the program: it only understands the exact words you told it to check for. When someone types a command, the program is just checking command == "next", then command == "save", and so on down the line. There's no understanding happening, only comparing strings. So the person at the keyboard has to guess exactly which words you picked, unless you tell them. Let's tell them:

def show_help():
    print("Commands: next, previous, details, save, help, quit")

command = input("Choose a command: ").strip().lower()

.strip().lower() means capital letters and stray spaces don't matter. It does not make the computer understand English, though. If the program checks for next, then show me another one is just a different string, and it'll get the "I don't know that command" message.

If you've ever played an old text adventure game, the kind where you typed go north or take lamp, you might remember how frustrating it was to guess which verbs the game knew. Did it want take, get, or grab? Who knows! That's why it helps to keep the list of commands short, to use the same word for the same thing everywhere (don't have one screen use quit and another use exit), to pick plain words people might guess on their own, and to always have a help command that shows the whole list.

Clear displays

Borders and text art can be fun, but think about what a row of forty dashes sounds like through a screen reader ("dash dash dash dash...") or what it looks like when it wraps around on a narrow phone screen. Labels like EVENT, WHEN, and COST hold up a lot better. The same goes for color and emoji: they're fine as extras, but if the only way to tell an event is sold out is that it's red, some people won't be able to tell. A good test for any decoration is to take it away and see whether anything important went with it.

Display design is also the place where nearly everyone turns into a bricoleur, even people who plan everything else. It's really hard to know ahead of time whether a card is going to read well, so you print it, look at it, move a label, and print it again. That's not a failure to plan! It's just the right way to do this particular job.

  1. Create one triple-quoted heading or instruction block.
  2. Store the changing details in a dictionary.
  3. Use a multi-line f-string to display the dictionary with labels.
  4. Use join to display one list.
  5. Ask another person to identify the important facts and available actions without explanation.
