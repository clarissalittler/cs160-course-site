  • Use a playtest to revise, and map these patterns onto the Week 6 capstone.

Putting the pieces in one file

The last four lessons each looked at one piece by itself: a plan, some nested data, a display, a state change. This lesson puts the pieces into one file and, just as importantly, convinces you that the result actually works.

The good news is that assembling doesn't mean inventing anything new. A clear program tends to come in this order:

  1. Data describing the songs, places, items, choices, or scenes.
  2. Function definitions for display and actions.
  3. Initial state, like a current location, an empty list, or a running flag.
  4. A main loop that gathers input and coordinates the functions.

Why that order? Python reads your file from top to bottom, running each line as it goes. If the main loop tries to call a function before the def line for it has run, you get a NameError: as far as Python knows, there's no such function yet. It's a sensible order for a human reader too: here's what the program knows, here's what it can do, here's what's happening right now.

That four-part layout might sound like it only suits planners, but it isn't really a plan for how you write the program. It's how the finished file is arranged. A planner might fill in the parts in order. A bricoleur might start with a tiny loop that prints one thing, then add a function, then a bit of data, running it after every change. Both can end up with the same tidy file. The order is there to help the next person who reads it, and that person might be you, next week.

One assembled program: a checklist with an ending

A lot of programs run until someone types quit. Plenty also have a second way to stop: the job gets finished. A game is won, a form is complete, a checklist is all checked off. Your dungeon will need an ending like that, so here's a small program built around one. It's a camping checklist, with a comment marking each of the four parts:

# 1. Data
ITEMS = ["tent", "sleeping bag", "headlamp", "water filter"]

# 2. Functions
def show_checklist(items, packed):
    for item in items:
        if item in packed:
            print(f"  [packed]  {item}")
        else:
            print(f"  [ ]       {item}")

def pack(item, items, packed):
    if item not in items:
        return f"'{item}' isn't on the checklist."
    if item in packed:
        return f"You already packed the {item}."
    packed.append(item)
    return f"Packed the {item}."

def count_remaining(items, packed):
    remaining = 0
    for item in items:
        if item not in packed:
            remaining += 1
    return remaining

# 3. Initial state
packed = []
running = True

# 4. Main loop
print("CAMPING CHECKLIST. Commands: pack ITEM, list, quit")

while running:
    words = input("> ").strip().lower().split(" ", 1)
    command = words[0]

    if command == "pack" and len(words) == 2:
        print(pack(words[1], ITEMS, packed))
        if count_remaining(ITEMS, packed) == 0:
            print("Everything's packed. Have a great trip!")
            running = False
    elif command == "list":
        show_checklist(ITEMS, packed)
        print(f"{count_remaining(ITEMS, packed)} item(s) left to pack.")
    elif command == "quit":
        running = False
    else:
        print("Commands: pack ITEM, list, quit")

ITEMS is the checklist itself. It never changes while the program runs, which is why it's in capitals. packed starts out empty and grows as you go. Keeping them separate means "what's on the list" and "what I've done so far" can't get mixed up.

Each function has one job. show_checklist only reads the two lists. pack checks for the two ways a request could be wrong before it appends anything, the same way borrow_item did in Lesson 4. count_remaining is a counter: start at 0 and add 1 for every item that hasn't been packed yet.

There's one new detail: .split(" ", 1). Plain .split() would turn pack sleeping bag into three words, and then we'd have to glue sleeping bag back together. The two arguments say "split on spaces, but only once," so you get ["pack", "sleeping bag"]: the command, then everything else in one piece. If someone types just pack, words has one element, and the len(words) == 2 check sends them to the help line instead of crashing on words[1].

Now the ending. Right after a successful pack, the loop asks whether anything is left. If nothing is, it congratulates you and sets running to False, the same flag that quit uses. So there are two ways out of the loop, and they both go through one variable, which keeps the loop easy to reason about.

Testing the weird paths

A test table names a starting state, one action, and what you should see afterward. Here's one for the checklist:

Starting stateActionExpected result
Nothing packedpack tent"Packed the tent."; list now shows three items left.
Tent already packedpack tent"You already packed the tent."; nothing changes.
Any statepack canoeNot-on-the-checklist message; nothing changes.
Any statedanceThe help line; nothing changes.
Three items packedPack the last oneSuccess message, then the program ends on its own.

Look at which rows made the list. Only the first one is the program working the way you'd hope. The rest are the weird paths: a repeat, an item that doesn't exist, a nonsense command, and the ending. That's on purpose! The normal path is the one you'll test without even meaning to, because it's the one you run while writing the code. The weird paths are the ones nobody tries until a real user does, so they're the ones to write down. And the last row is the one people forget most often, because you have to get all the way to the end to see it.

Planners and bricoleurs tend to fill in a table like this in different ways, too. A planner writes the rows ahead of time, from the plan. A bricoleur pokes at the running program, tries weird things on purpose, and writes down each surprise as a row. Both are good ways to test! The important part is that the rows get written down, so you can run them again after you change something.

One practical gotcha: reset the state between tests that are supposed to start fresh. If you packed the tent in one test, the next test starts with the tent already packed, and "Packed the tent" turns into "You already packed the tent." It looks like a bug, but the program is just remembering the last test. This happens a lot in Colab, because cells share state, so rerun the cell that sets up the data first.

Finding the first wrong step

When something does go wrong, it's tempting to start changing code until the symptom goes away. Sometimes that works, but you usually don't learn why, and the bug has a way of coming back. A more reliable approach is to find the exact step where things first go wrong:

  1. Choose the shortest input sequence that reproduces the problem.
  2. Write the expected state and output after each input.
  3. Print or inspect the actual values after each input.
  4. Find the first row where expected and actual differ.
  5. Inspect the condition, lookup, return, or assignment responsible for that step.

Why the first wrong step? Because one mistake tends to cause a pile of others after it. If the program moved you to the wrong room on step 2, then everything it describes on steps 3, 4, and 5 will be wrong too, but there's only one bug. The usual suspects are inconsistent dictionary keys, a returned value nobody stored, a change made to the wrong list, and == where you meant =.

Playtesting

Testing tells you whether the program does what you meant. It can't tell you whether what you meant makes sense to anyone else. You've spent hours with this program, so you know the command is pack and not add, and you can't un-know it. Someone coming in fresh can show you what you can no longer see yourself.

Ask another person to complete one short task without coaching. Watch for the first place they pause, misread a label, or type something reasonable that the program rejects. Don't defend the interface during the test, however much you want to! That pause is exactly what you were looking for. A good revision might display the available commands, label an empty collection, replace a vague message, or state the goal earlier.

Notice that a playtest is bricolage, no matter which style you started with. You're putting the program in front of reality, watching what happens, and letting that tell you what to change next. Even the most careful plan meets real people eventually.

On to the dungeon

The Week 6 assignment is a tiny text adventure, and it uses every pattern from this unit:

  • the dictionary of connected spaces from Lesson 2 becomes a dictionary of connected rooms;
  • the labeled event card from Lesson 3 becomes a multi-line room display;
  • the advance function from Lesson 4, which returns a new position, becomes a movement function that returns a new room;
  • the borrow action, which changes a list directly, becomes picking up an item into your inventory; and
  • the checklist's ending check becomes the check for reaching your ending room.

So you've already seen every idea the dungeon needs. The starter supplies a lot of the structure. Your job is to adapt it, connect the pieces, trace what changes, and make one small path work from start to finish.

And you can build it in whichever style suits you. Plan the whole map, the item, the obstacle, and the ending on paper first, or get one room on the screen and grow the dungeon from there. Either way, keep it running as you go, and keep the smallest complete path working.

Reusing code

Starter code, copied code, and AI-generated code are all still your program once they're in your file. You should be able to trace the values they read, describe the state they change, and test their important paths. If a suggestion drags in a library, a class, or a technique you can't explain, take it out. Smaller code you understand beats bigger code you don't.
