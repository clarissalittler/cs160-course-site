Lesson 5 - Assemble, Test, and Revise

By the end of this lesson, you will be able to:

  • Arrange data, functions, initial state, and a main loop in a readable program.
  • Build and test one complete path before adding optional features.
  • Use expected and observed results to isolate a bug.
  • Transfer a general program pattern into a new creative context.

Assembly is not the same as starting over

The last four lessons each looked at one piece in isolation: a plan, some nested data, a display, a state change. None of them was a whole program. This lesson is about putting the pieces into one file and, just as importantly, convincing yourself that the result actually works.

The good news is that assembling doesn't mean inventing anything new. Whether you're building a playlist browser, a community guide, a lending kiosk, a recommendation tool, or an interactive story, a clear program tends to come in this order:

  1. Data describing the available songs, places, items, choices, or scenes.
  2. Function definitions for display and actions.
  3. Initial state such as a current selection, empty basket, score, or running flag.
  4. A main loop that gathers input and coordinates the functions.

Python has to see a definition before later code uses it, which is the practical reason for this order. Python reads your file from top to bottom, running each line as it goes, and if the main loop tries to call show_event before the def show_event line has run, you get a NameError: as far as Python knows, there's no such function yet. But it's also a sensible route for a reader: here's what the program knows, here's what it can do, here's what's happening right now.

Build one vertical slice

Suppose the program is a neighborhood-resource browser. Don't enter fifty resources and design every filter first. Build this path:

  1. Display one resource with clear labels.
  2. Accept next and select a second resource.
  3. Accept save and add that resource to a favorites list.
  4. Display the favorites.
  5. Quit cleanly.

Each step adds exactly one new thing, and each one leaves you with a program that runs. After step 1, you have a program that displays one card and stops. That's not much, but it works, and you know it works. After step 2 you can browse. And so on.

Run the program after every step! When something breaks, the last small change is a far better suspect than the whole file. If you write all five steps and then run it for the first time, and it doesn't work, the bug could be anywhere in forty lines. If you run it after every step, the bug is almost certainly in the five lines you just added.

One slice, assembled

Here's that resource browser with all four roles in one runnable block. Copy the whole block into one file or Colab cell. The records come first, then three functions, then the initial state, then the loop. It doesn't let you add records yet; two prepared records are enough to test the browsing path.

resources = [
    {"name": "Tool Library", "area": "North"},
    {"name": "Repair Café", "area": "Central"},
]

def show_resource(record):
    print(f"RESOURCE: {record['name']}")
    print(f"AREA: {record['area']}")

def next_resource(current, records):
    if current + 1 >= len(records):
        return 0
    return current + 1

def save_resource(record, favorites):
    name = record["name"]
    if name in favorites:
        return "Already saved."
    favorites.append(name)
    return f"Saved: {name}"

current = 0
favorites = []
running = True

while running:
    if len(resources) == 0:
        print("No resources are available.")
    else:
        show_resource(resources[current])
    print("Commands: next, save, favorites, quit")
    command = input("Choose: ").strip().lower()

    if command == "next" or command == "save":
        if len(resources) == 0:
            print("Add a resource to the data before browsing or saving.")
        elif command == "next":
            current = next_resource(current, resources)
        else:
            print(save_resource(resources[current], favorites))
    elif command == "favorites":
        if len(favorites) == 0:
            print("FAVORITES: empty")
        else:
            print("FAVORITES:", ", ".join(favorites))
    elif command == "quit":
        running = False
    else:
        print("Unknown command. Choose next, save, favorites, or quit.")

Try next, save, save, favorites, and quit, in that order. After next, current is 1, so the next display shows Repair Café. The first save changes favorites to ["Repair Café"]; the second returns "Already saved." without changing the list. favorites displays that one name, and quit changes running to False.

Follow one command through the pieces. The loop reads next, calls next_resource, and stores its returned index. On the next pass, that index chooses the record handed to show_resource. The display function only reads data. The save function changes a list directly. That's the distinction from Lesson 4, now doing work inside a complete program.

For two more checks, try an unknown command, then start a fresh run with resources = []. The empty case should explain what's missing, allow you to inspect the empty favorites, and still let you quit. Each independent run recreates the initial state.

In the dungeon, the current index becomes a location key, next_resource becomes a movement function, and the favorites list becomes inventory. The layout has more detail, but the loop still reads a command and hands the job to a function. You can find those roles in the assignment's starter before changing anything.

Another assembly: a checklist with an ending

The resource browser runs until someone types quit. Lots of programs have a second way to stop, though: the job gets finished. A game is won, a form is complete, a checklist is all checked off. Your dungeon will need one of those endings, so here's a small program built around one. It's a camping checklist, laid out in the same four parts, with a comment marking each:

# 1. Data
ITEMS = ["tent", "sleeping bag", "headlamp", "water filter"]

# 2. Functions
def show_checklist(items, packed):
    for item in items:
        if item in packed:
            print(f"  [packed]  {item}")
        else:
            print(f"  [ ]       {item}")

def pack(item, items, packed):
    if item not in items:
        return f"'{item}' isn't on the checklist."
    if item in packed:
        return f"You already packed the {item}."
    packed.append(item)
    return f"Packed the {item}."

def count_remaining(items, packed):
    remaining = 0
    for item in items:
        if item not in packed:
            remaining += 1
    return remaining

# 3. Initial state
packed = []
running = True

# 4. Main loop
print("CAMPING CHECKLIST. Commands: pack ITEM, list, quit")

while running:
    words = input("> ").strip().lower().split(" ", 1)
    command = words[0]

    if command == "pack" and len(words) == 2:
        print(pack(words[1], ITEMS, packed))
        if count_remaining(ITEMS, packed) == 0:
            print("Everything's packed. Have a great trip!")
            running = False
    elif command == "list":
        show_checklist(ITEMS, packed)
        print(f"{count_remaining(ITEMS, packed)} item(s) left to pack.")
    elif command == "quit":
        running = False
    else:
        print("Commands: pack ITEM, list, quit")

ITEMS is the fixed checklist (hence the capitals), and packed starts empty and grows, so "what's on the list" and "what have I done" can't get mixed up. Each function has one job: show_checklist only reads, pack checks two ways the request could be wrong before appending (the guard-first style of borrow_item), and count_remaining is the Unit 5 counter pattern.

The one new detail is .split(" ", 1). Plain .split() would turn pack sleeping bag into three words, ["pack", "sleeping", "bag"], and then we'd have to glue sleeping bag back together. The two arguments say "split on spaces, but at most once," so we get ["pack", "sleeping bag"]: the command, then everything else as one piece. If someone types just pack, there's nothing to split, words has one element, and the len(words) == 2 check sends them to the help line instead of crashing on words[1].

Now the ending. Right after a successful pack, the loop asks whether anything is left. If nothing is, it congratulates you and sets running to False, the same flag that quit uses. So there are two ways out of the loop, and they both go through one variable, which keeps the loop easy to reason about. The check only happens after a pack, since that's the only command that can finish the list.

Here's a short test table for it, in the format from the next section:

Starting stateActionExpected result
Nothing packedpack tent"Packed the tent."; list now shows three items left.
Tent already packedpack tent"You already packed the tent."; nothing changes.
Any statepack canoeNot-on-the-checklist message; nothing changes.
Three items packedPack the last oneSuccess message, then the program ends on its own.

The last row is the one people forget to test, because you have to get all the way to the end to see it. In the dungeon, that's the row that checks whether your ending actually happens.

Seeing that transfer matters more than memorizing any one finished project, because the next program you want to build won't be one of these three.

Test paths, not just lines

An interactive program has many possible sequences of commands. A compact test table protects the behaviors that matter:

Starting stateActionExpected result
Empty request queuePlay nextHelpful empty message; queue remains empty.
Two requestsPlay nextFirst title displayed and removed; second remains.
Item availableBorrow itMoves from available to borrowed.
Item already borrowedBorrow it againUnavailable message; no duplicate.
Any ordinary stateUnknown commandRecovery message; state remains unchanged.

Each row names the starting state, the action, and what you should see afterward. It's the Given/When/Then shape from Lesson 1, in a table, and it works for any project.

Look at which rows made the list. Only two of the five are the program working the way you'd hope. The other three are an empty queue, a repeat borrow, and a nonsense command: the edge cases. That's not an accident. The normal path is the one you'll test without even meaning to, because it's the one you run while writing the code. The weird paths are the ones nobody tries until a real user does, so they're the ones that need to be written down.

Reset state between independent tests

After a queue plays its first request, or a kiosk moves an object, later tests see changed data. If the next test is supposed to start fresh, rerun the setup code that creates the original lists and dictionaries. Otherwise an earlier test can affect a later one in ways that are maddening to track down, because the code is fine and the data is what's wrong.

Here's how that plays out. You test borrowing the umbrella, and it works. Then you test "borrow an available item" again with the umbrella, forgetting it's already borrowed, and get "Umbrella is not available." It looks like a bug! It isn't. The program remembered the first test. In Colab this happens a lot, because cells share state: rerunning just the loop cell keeps whatever the lists looked like from the last run. Rerun the cell that sets up the data first.

Debug the first wrong step

When something does go wrong, the temptation is to stare at the code and start changing things until the symptom goes away. Sometimes that works, but you usually don't learn why, and the bug has a way of coming back. A slower but much more reliable approach is to find the exact step where things first go wrong:

  1. Choose the shortest input sequence that reproduces the problem.
  2. Write the expected state and output after each input.
  3. Print or inspect the actual values after each input.
  4. Find the first row where expected and actual differ.
  5. Inspect the condition, lookup, return, or assignment responsible for that transition.

The usual suspects: inconsistent dictionary keys, a return value nobody stored, a mutation applied to the wrong list, == where you meant =, and a branch that checks for the wrong command. All of these are cheap to fix once you know which line. The hard part is finding the line, and the trace is how.

Why the first wrong step? Because one mistake tends to cause a pile of others after it. If the program moved you to the wrong room on step 2, then everything it describes on steps 3, 4, and 5 will be wrong too, but there's only one bug. Chasing the symptoms at step 5 sends you looking in the wrong place. The first row where expected and actual disagree points right at the cause.

A playtest reveals interface assumptions

Testing tells you whether the program does what you meant. It can't tell you whether what you meant makes sense to anyone else. You've spent hours with this program; you know that the command is save and not favorite, and you can't un-know it. Someone coming in fresh can show you what you can no longer see yourself.

Ask another person to complete one short task without coaching. Watch for the first place they pause, misread a label, or type something reasonable that the program rejects. Don't defend the interface during the test, however much you want to. The pause is the evidence you came for.

A good revision might display the available commands, label an empty collection, replace a vague message, normalize capitalization, or state the goal earlier. The program doesn't need to understand everything. It needs to make its small agreement with the user visible, and then keep it.

Transfer the patterns into the capstone

The Week 6 assignment uses a tiny text adventure because it gives all these patterns a playful home:

  • a dictionary of records becomes a dictionary of connected locations;
  • a current selection becomes the current location;
  • a saved-items list becomes inventory;
  • a function that advances a selection becomes a movement function;
  • a state-changing borrow action becomes a collect action; and
  • a labeled card becomes a multi-line location display.

So if you've followed the lending kiosk, the connections code, and the event card, you've already seen every idea the dungeon needs. The starter supplies a lot of that structure. Your job is to adapt it, connect the pieces, trace what changes, and make one small path work from start to finish.

Explain code you reuse

Starter code, copied code, and AI-generated code are all still your program once they're in your file. You should be able to trace the values they read, describe the state they change, and test their important paths. If a suggestion drags in a library, a class, a file format, or a technique the project doesn't need and you can't explain, take it out. Smaller code you understand beats bigger code you don't, every single time.
