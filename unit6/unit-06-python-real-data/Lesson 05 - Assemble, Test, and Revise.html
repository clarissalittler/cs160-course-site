Lesson 5 - Assemble, Test, and Revise

By the end of this lesson, you will be able to:

  • Arrange data, functions, initial state, and a main loop in a readable program.
  • Build and test one complete path before adding optional features.
  • Use expected and observed results to isolate a bug.
  • Transfer a general program pattern into a new creative context.

Assembly is not the same as starting over

Whether you are building a playlist browser, community guide, lending kiosk, recommendation tool, or interactive story, a clear program often appears in this order:

  1. Data describing the available songs, places, items, choices, or scenes.
  2. Function definitions for display and actions.
  3. Initial state such as a current selection, empty basket, score, or running flag.
  4. A main loop that gathers input and coordinates the functions.

Python must learn a variable or function before later code uses it. The order also gives a reader a sensible route from what the program knows, to what it can do, to what is happening now.

Build one vertical slice

Suppose the program is a neighborhood-resource browser. Do not enter fifty resources and design every filter first. Build this path:

  1. Display one resource with clear labels.
  2. Accept next and select a second resource.
  3. Accept save and add that resource to a favorites list.
  4. Display the favorites.
  5. Quit cleanly.

Run the program after every step. When something breaks, the most recent small change is a much better suspect than the entire file.

Test paths, not just lines

An interactive program has many possible sequences. A compact test table protects the behaviors that matter:

Starting stateActionExpected result
Empty request queuePlay nextHelpful empty message; queue remains empty.
Two requestsPlay nextFirst title displayed and removed; second remains.
Item availableBorrow itMoves from available to borrowed.
Item already borrowedBorrow it againUnavailable message; no duplicate.
Any ordinary stateUnknown commandRecovery message; state remains unchanged.

Each row names the starting state, action, and observable result. You can adapt the same structure to any project.

Reset state between independent tests

After a queue removes its first request, or a lending kiosk moves an object, later tests see changed data. If the next test is supposed to begin fresh, rerun the cell or setup code that creates the original lists and dictionaries. Otherwise, an earlier test can secretly affect a later one.

Debug the first wrong step

  1. Choose the shortest input sequence that reproduces the problem.
  2. Write the expected state and output after each input.
  3. Print or inspect the actual values after each input.
  4. Find the first row where expected and actual differ.
  5. Inspect the condition, lookup, return, or assignment responsible for that transition.

Common causes include inconsistent dictionary keys, an ignored return value, a mutation applied to the wrong list, comparing instead of assigning, and a branch that tests the wrong command.

A playtest reveals interface assumptions

Ask another person to complete one short task without coaching. Watch for the first place they pause, misread a label, or type something reasonable that the program rejects. Do not defend the interface during the test; the pause is useful evidence.

A good revision might display the available commands, label an empty collection, replace a vague message, normalize capitalization, or state the goal earlier. The program does not need to understand everything. It needs to make its small agreement with the user visible and consistent.

Transfer the patterns into the capstone

The Week 6 assignment uses a tiny text adventure because it gives all these patterns a playful home:

  • a dictionary of records becomes a dictionary of connected locations;
  • a current selection becomes the current location;
  • a saved-items list becomes inventory;
  • a function that advances a selection becomes a movement function;
  • a state-changing borrow action becomes a collect action; and
  • a labeled card becomes a multi-line location display.

The assignment starter supplies much of that structure. Your work is to adapt it, connect the pieces, trace what changes, and make one small path complete.

Explain code you reuse

Starter, copied, or AI-generated code remains part of your program. You should be able to trace the values it reads, describe the state it changes, and test its important paths. If a suggestion introduces a library, class, file format, or technique the project does not need and you cannot explain, remove it. Smaller understood code is stronger.

Assembly studio.

  1. Choose one program idea and list its data, functions, initial state, and loop.
  2. Describe the smallest complete path.
  3. Write five manual tests, including an empty state and unknown command.
  4. Watch one person attempt a short task and revise one observed problem.
  5. Map each part of your design to the corresponding part of the Week 6 capstone.

End of the Python sequence: You can now turn an idea into data, write reusable actions that operate on it, coordinate those actions in a loop, and revise the result from evidence. Unit 7 steps back from particular programs to compare algorithms and ask how their work grows.
