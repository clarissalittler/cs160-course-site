Lesson 5 - Assemble, Test, and Revise

By the end of this lesson, you will be able to:

  • Arrange data, functions, initial state, and a main loop in a readable program.
  • Build and test one complete path before adding optional features.
  • Use expected and observed results to isolate a bug.
  • Transfer a general program pattern into a new creative context.

Assembly is not the same as starting over

Whether you're building a playlist browser, a community guide, a lending kiosk, a recommendation tool, or an interactive story, a clear program tends to come in this order:

  1. Data describing the available songs, places, items, choices, or scenes.
  2. Function definitions for display and actions.
  3. Initial state such as a current selection, empty basket, score, or running flag.
  4. A main loop that gathers input and coordinates the functions.

Python has to see a definition before later code uses it, which is the practical reason for this order. But it's also a sensible route for a reader: here's what the program knows, here's what it can do, here's what's happening right now.

Build one vertical slice

Suppose the program is a neighborhood-resource browser. Don't enter fifty resources and design every filter first. Build this path:

  1. Display one resource with clear labels.
  2. Accept next and select a second resource.
  3. Accept save and add that resource to a favorites list.
  4. Display the favorites.
  5. Quit cleanly.

Run the program after every step! When something breaks, the last small change is a far better suspect than the whole file.

Test paths, not just lines

An interactive program has many possible sequences of commands. A compact test table protects the behaviors that matter:

Starting stateActionExpected result
Empty request queuePlay nextHelpful empty message; queue remains empty.
Two requestsPlay nextFirst title displayed and removed; second remains.
Item availableBorrow itMoves from available to borrowed.
Item already borrowedBorrow it againUnavailable message; no duplicate.
Any ordinary stateUnknown commandRecovery message; state remains unchanged.

Each row names the starting state, the action, and what you should see afterward. It's the Given/When/Then shape from Lesson 1, in a table, and it works for any project.

Reset state between independent tests

After a queue plays its first request, or a kiosk moves an object, later tests see changed data. If the next test is supposed to start fresh, rerun the setup code that creates the original lists and dictionaries. Otherwise an earlier test can affect a later one in ways that are maddening to track down, because the code is fine and the data is what's wrong.

Debug the first wrong step

  1. Choose the shortest input sequence that reproduces the problem.
  2. Write the expected state and output after each input.
  3. Print or inspect the actual values after each input.
  4. Find the first row where expected and actual differ.
  5. Inspect the condition, lookup, return, or assignment responsible for that transition.

The usual suspects: inconsistent dictionary keys, a return value nobody stored, a mutation applied to the wrong list, == where you meant =, and a branch that checks for the wrong command. All of these are cheap to fix once you know which line. The hard part is finding the line, and the trace is how.

A playtest reveals interface assumptions

Ask another person to complete one short task without coaching. Watch for the first place they pause, misread a label, or type something reasonable that the program rejects. Don't defend the interface during the test, however much you want to. The pause is the evidence you came for.

A good revision might display the available commands, label an empty collection, replace a vague message, normalize capitalization, or state the goal earlier. The program doesn't need to understand everything. It needs to make its small agreement with the user visible, and then keep it.

Transfer the patterns into the capstone

The Week 6 assignment uses a tiny text adventure because it gives all these patterns a playful home:

  • a dictionary of records becomes a dictionary of connected locations;
  • a current selection becomes the current location;
  • a saved-items list becomes inventory;
  • a function that advances a selection becomes a movement function;
  • a state-changing borrow action becomes a collect action; and
  • a labeled card becomes a multi-line location display.

The starter supplies a lot of that structure. Your job is to adapt it, connect the pieces, trace what changes, and make one small path work from start to finish.

Explain code you reuse

Starter code, copied code, and AI-generated code are all still your program once they're in your file. You should be able to trace the values they read, describe the state they change, and test their important paths. If a suggestion drags in a library, a class, a file format, or a technique the project doesn't need and you can't explain, take it out. Smaller code you understand beats bigger code you don't, every single time.

Assembly studio.

  1. Choose one program idea and list its data, functions, initial state, and loop.
  2. Describe the smallest complete path.
  3. Write five manual tests, including an empty state and unknown command.
  4. Watch one person attempt a short task and revise one observed problem.
  5. Map each part of your design to the corresponding part of the Week 6 capstone.

End of the Python sequence: You can now turn an idea into data, write reusable actions that work on it, coordinate those actions in a loop, and revise the result based on evidence. Unit 7 steps back from particular programs to compare algorithms and ask how their work grows as the input does.
