By the end of this lesson, you will be able to:

  • Arrange data, functions, initial state, and a main loop in a readable program.
  • Give a program a way to end when its job is done.
  • Test the unusual paths, and find the first step where a bug shows up.
  • Use a playtest to revise, and map these patterns onto the Week 6 capstone.

Putting the pieces in one file

The last four lessons each looked at one piece by itself: a plan, some nested data, a display, a change to the state. This lesson puts the pieces together in one file, and then, just as importantly, asks how you'd convince yourself that the result actually works.

The good news is that putting a program together doesn't mean inventing anything new. A clear program usually comes in this order:

  1. Data describing the songs, places, items, choices, or scenes.
  2. Function definitions for display and actions.
  3. Initial state, like a current location, an empty list, or a running flag.
  4. A main loop that gathers input and coordinates the functions.

Why that order? Because Python reads your file from top to bottom, running each line as it goes. If the main loop tries to call a function before the def line for it has run, you get a NameError, since as far as Python knows there's no such function yet. It's a sensible order for a person reading the file too: here's what the program knows, here's what it can do, and here's what's happening right now.

Now, this might sound like a layout only a planner could love, but it isn't really about the order you write things in. It's about how the finished file is arranged. A planner might fill in the four parts from top to bottom. A bricoleur might start with a tiny loop that prints one thing, then add a function, then a bit of data, running it after every change. Both can end up with the same tidy file at the end, and the order is there to help the next person who reads it, who might very well be you, next week.

One assembled program: a checklist with an ending

A lot of programs run until someone types quit, but plenty of them also have a second way to stop: the job gets finished. A game gets won, a form gets completed, a checklist gets all checked off. Your dungeon is going to need an ending like that, so here's a small program built around one. It's a checklist for packing for a camping trip, with comments marking each of the four parts:

# 1. Data
ITEMS = ["tent", "sleeping bag", "headlamp", "water filter"]

# 2. Functions
def show_checklist(items, packed):
    for item in items:
        if item in packed:
            print(f"  [packed]  {item}")
        else:
            print(f"  [ ]       {item}")

def pack(item, items, packed):
    if item not in items:
        return f"'{item}' isn't on the checklist."
    if item in packed:
        return f"You already packed the {item}."
    packed.append(item)
    return f"Packed the {item}."

def count_remaining(items, packed):
    remaining = 0
    for item in items:
        if item not in packed:
            remaining += 1
    return remaining

# 3. Initial state
packed = []
running = True

# 4. Main loop
print("CAMPING CHECKLIST. Commands: pack ITEM, list, quit")

while running:
    words = input("> ").strip().lower().split(" ", 1)
    command = words[0]

    if command == "pack" and len(words) == 2:
        print(pack(words[1], ITEMS, packed))
        if count_remaining(ITEMS, packed) == 0:
            print("Everything's packed. Have a great trip!")
            running = False
    elif command == "list":
        show_checklist(ITEMS, packed)
        print(f"{count_remaining(ITEMS, packed)} item(s) left to pack.")
    elif command == "quit":
        running = False
    else:
        print("Commands: pack ITEM, list, quit")

ITEMS is the checklist itself. It never changes while the program runs, which is why it's in capitals. packed starts out empty and grows as you go. Keeping them separate means "what's on the list" and "what I've already done" can't get mixed up with each other.

Each function has one job. show_checklist only reads the two lists. pack checks for the two ways a request could be wrong before it appends anything, the same way borrow_item did in Lesson 4. count_remaining is a counter: start at 0 and add 1 for every item that hasn't been packed yet.

There's one new detail: .split(" ", 1). Plain .split() would turn pack sleeping bag into three words, and then we'd have to glue sleeping bag back together. The two arguments say "split on spaces, but only once," so you get ["pack", "sleeping bag"]: the command, then everything else in one piece. If someone types just pack, words has one element, and the len(words) == 2 check sends them to the help line instead of crashing on words[1].

Now for the ending. Right after a successful pack, the loop checks whether anything's left. If nothing is, it congratulates you and sets running to False, which is the same flag that quit uses. So there are two ways out of the loop, but they both go through the same variable, which makes the loop a lot easier to think about.

Testing the weird paths

So how do we know this program works? One way is to write out a few tests, where each test has a starting state, one action, and what you expect to see afterward. Here are some for the checklist:

Starting stateActionExpected result
Nothing packedpack tent"Packed the tent."; list now shows three items left.
Tent already packedpack tent"You already packed the tent."; nothing changes.
Any statepack canoeNot-on-the-checklist message; nothing changes.
Any statedanceThe help line; nothing changes.
Three items packedPack the last oneSuccess message, then the program ends on its own.

Take a look at which rows made the list. Only the first one is the program working the way you'd hope. The rest are the weird cases: packing something twice, an item that isn't on the checklist, a nonsense command, and the ending. That's on purpose! You'll test the normal case without even meaning to, because it's what you run over and over while you're writing the code. The weird cases are the ones nobody tries until a real person does, so those are the ones worth writing down. And the last row is the one people forget most often, because you have to get all the way to the end to see it.

A planner will probably write rows like these ahead of time, straight from the plan. A bricoleur is more likely to poke at the running program, try weird things on purpose, and write down each surprise as a new row. Either way works fine! The important part is that the rows get written down, so that you can run them all again after you change something.

Here's one gotcha to watch out for: if a test is supposed to start fresh, you have to reset the state before you run it. Say you packed the tent in one test. The next test starts with the tent already packed, so instead of "Packed the tent." you get "You already packed the tent." That looks like a bug, but the program is just remembering the last test! This happens a lot in Colab, because the cells share their variables, so rerun the cell that sets up the data first.

Finding the first wrong step

When something does go wrong, it's really tempting to start changing code until the problem goes away. Sometimes that even works, but you usually don't learn why, and the bug has a way of coming back. A more reliable way is to find the exact step where things first go wrong:

  1. Choose the shortest input sequence that reproduces the problem.
  2. Write the expected state and output after each input.
  3. Print or inspect the actual values after each input.
  4. Find the first row where expected and actual differ.
  5. Inspect the condition, lookup, return, or assignment responsible for that step.

Why the first wrong step? Because one mistake tends to cause a whole pile of others after it. If the program moved you into the wrong room on step 2, then everything it tells you on steps 3, 4, and 5 is going to be wrong too, even though there's only one bug. In programs like these, the usual suspects are dictionary keys that don't quite match, a returned value that nobody stored, a change made to the wrong list, and == where you meant = (which compares, instead of storing anything).

Playtesting

Testing tells you whether the program does what you meant. What it can't tell you is whether what you meant makes any sense to somebody else. By now you've spent hours with your program. You know the command is pack and not add, and you can't un-know that. Someone coming to it fresh can show you what you can't see anymore.

So ask somebody to do one short task with your program, without any coaching from you, and watch for the first place they pause, misread a label, or type something perfectly reasonable that the program doesn't accept. It's really hard not to jump in and explain! Try not to, because that pause is exactly what you were looking for. Fixing it might mean showing the list of commands, labeling an empty list so it doesn't look broken, rewriting a vague message, or saying what the goal is earlier.

A playtest is bricolage no matter which style you started with. You put the program in front of a real person, watch what happens, and let that tell you what to change next, which is exactly what the bricoleur was doing all along.

On to the dungeon

The Week 6 assignment is a tiny text adventure, and it uses every pattern from this unit:

  • the dictionary of connected spaces from Lesson 2 becomes a dictionary of connected rooms;
  • the labeled event card from Lesson 3 becomes a multi-line room display;
  • the advance function from Lesson 4, which returns a new position, becomes a movement function that returns a new room;
  • the borrow action, which changes a list directly, becomes picking up an item into your inventory; and
  • the checklist's ending check becomes the check for reaching your ending room.

So you've already seen every idea the dungeon needs. The starter notebook gives you a lot of the structure, and your job is to adapt it, connect the pieces, keep track of what changes, and get one small path working from start to finish.

You can build it in whichever style suits you. You could plan the whole map, the item, the obstacle, and the ending on paper first, or you could get one room on the screen and grow the dungeon from there. Either way, run it often as you go, and keep that smallest complete path working.

Exploring and planning, one more time

This brings us back to the two styles from Lesson 1. Exploratory programming, the bricoleur's way, is still one of the best ways to figure out a new problem. Remember tinkering with the scam filter's threshold in Unit 5? Trying settings on test messages taught us a lot about how that rule behaves, and nobody got hurt when we got it wrong. But tinkering isn't a good way to figure out what the final version should be, especially when that version is going to run on lots of people. You can't tinker with Jordan's benefits and see what happens! Once you understand the problem, the final structure and the path through it need to be worked out on purpose: what the rule is, what it assumes, how it was tested, who it gets wrong, and what happens to them. In other words, exploring is how you come to understand the problem, and planning is how you decide what actually goes out into the world.

Your dungeon is the friendly version of this. Tinker all you like while you're figuring out what it should be, because the only person a bug can hurt is a player who can restart in a second. But before you hand it to a playtester, run through your test table on purpose, so that what goes out is the version you meant.

Reusing code

One last thing. Starter code, code you copied from somewhere, and code an AI wrote for you are all still your program once they're in your file. You should be able to trace the values they read, explain what state they change, and test the important paths through them. If a suggestion pulls in a library or a technique you can't explain, take it out. A smaller program you understand is worth a lot more than a bigger one you don't.

  2. Describe the smallest complete path, and how the program ends.
  3. Write five manual tests, including an empty state and unknown command.
  4. Watch one person attempt a short task and revise one observed problem.
  5. Map each part of your design to the corresponding part of the Week 6 capstone.
