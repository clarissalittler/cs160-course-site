Lesson 2 - Connect Data with Nested Dictionaries

By the end of this lesson, you will be able to:

  • Read values from a dictionary inside another dictionary.
  • Represent several related things with a consistent structure.
  • Represent connections as keys and values.
  • Use in and .get() when a key may be absent.

Records under one set of keys

Let's say you're making a little guide to a community center, the kind of program that could run on a screen by the front door. It needs to describe several spaces in the building. Now, we could make a separate variable for each space, but then nothing connects them, and a question like "which room is east of the lobby?" doesn't have anywhere to live. So instead, let's make one big dictionary whose keys are short names for the spaces, and whose values are records that all have the same shape:

SPACES = {
    "lobby": {
        "name": "Main Lobby",
        "description": "Information desk, water fountain, and front entrance.",
        "connections": {"east": "studio", "south": "courtyard"},
        "feature": "information desk",
        "open": True,
    },
    "studio": {
        "name": "Art Studio",
        "description": "Tables, sinks, drying racks, and north-facing windows.",
        "connections": {"west": "lobby"},
        "feature": "community mural",
        "open": True,
    },
    "courtyard": {
        "name": "Courtyard",
        "description": "Benches circle a small rain garden.",
        "connections": {"north": "lobby"},
        "feature": "rain garden",
        "open": False,
        "note": "Closed during icy weather",
    },
}

That's a lot of punctuation all at once, so let's take it apart. The whole thing is one dictionary, SPACES. It has three keys: "lobby", "studio", and "courtyard". The value stored under each key isn't a string or a number this time, it's a whole other dictionary. That's what "nested" means: a dictionary inside a dictionary. And one of the fields inside that, "connections", is a third, smaller dictionary. If you picture it as boxes inside of boxes inside of boxes, you won't go far wrong.

(Why is SPACES in all capital letters? It's a Python convention, not a rule. A name in all caps tells the reader "this gets set up once at the start, and the program isn't going to change it while it runs." Python won't actually stop you from changing it, but other programmers will be pretty surprised if you do.)

Back in Unit 5 we kept records in a list of dictionaries, and we found them by their position in the list. Here the outer structure is a dictionary instead, so every record gets a name we can look it up by. Why does that matter? Because these records are going to refer to each other. The lobby needs some way to say "the studio is east of me," and a short name like "studio" is a lot more reliable than "whatever happens to be at index 1," which could change the moment someone adds a new room to the front of the list.

This shape isn't really about buildings, by the way. Any time you've got several things of the same kind that point to each other, like stops on a bus line or scenes in a choose-your-own-adventure story, you can describe them the same way.

Read from the outside in

print(SPACES["lobby"])
print(SPACES["lobby"]["name"])
print(SPACES["lobby"]["connections"])
print(SPACES["lobby"]["connections"]["east"])

Each line here goes one level deeper than the line before it. The first prints the whole lobby record, all five fields. The second picks out just the "name" field, Main Lobby. The third gets the connections dictionary, {'east': 'studio', 'south': 'courtyard'}. And the last one reaches all the way in.

The trick to reading that last one is to go left to right: get the lobby record, then get its connections dictionary, then get whatever is stored under "east". Each pair of square brackets hands back a value, and the next pair of brackets works on that value. The answer is studio, which is itself a key in SPACES, so we could look that up too and keep going: SPACES["studio"]["name"] is Art Studio. That little hop, from one record to a key that names another record, is what the rest of this lesson is about.

If a long chain of brackets gets hard to read, it's totally fine to break it up with a temporary name, like lobby = SPACES["lobby"] and then lobby["connections"]["east"]. The next example does exactly that.

Storing connections

So the connections dictionary is like a little map. Let's use it to actually move around:

current_space = "lobby"
direction = "east"
connections = SPACES[current_space]["connections"]

if direction in connections:
    current_space = connections[direction]
    print("Now viewing:", SPACES[current_space]["name"])
else:
    print("That connection is not available.")

Let's trace through it. current_space starts out as "lobby", so connections is the lobby's connections dictionary. Is "east" one of its keys? Yes, so current_space becomes whatever's stored there, "studio", and we print Now viewing: Art Studio. If direction had been "north" instead, the in check would have failed (the lobby doesn't have a north connection) and we'd get the "not available" message instead of a KeyError.

Now, what's interesting is what isn't in this code. There's no special rule anywhere about the lobby's east side. The code just asks the current record what "east" means and follows the answer. So if you want to add a gift shop west of the courtyard, you add one record to SPACES and one entry to the courtyard's connections, and you don't touch this code at all. Compare that with writing if current_space == "lobby" and direction == "east" for every possible move. That's what a lot of people's first text adventure looks like, and it gets out of hand somewhere around the fifth room. Keeping the details in the data and the following-the-connection in the code is why this shape shows up so often, and once you've seen it you'll find it everywhere.

Required and optional facts

Every space has a name, a description, connections, a feature, and an open status. Only the courtyard has a note. So how should we look up a key that might not be there? Python gives you two options, and which one you want depends on what it would mean for the key to be missing:

space = SPACES["courtyard"]

print(space["name"])
print(space.get("note", "No special note"))

ordinary_space = SPACES["studio"]
print(ordinary_space.get("note", "No special note"))

The courtyard has a note, so the second line prints Closed during icy weather. The studio doesn't have one, so the last line prints No special note instead of crashing. The second argument to .get() is what comes back when the key is missing. It doesn't add the key to the dictionary, so the studio record is exactly the same afterward as it was before.

So which should you use when? Think about what a missing key would mean. A space with no name is a mistake in the data, and you want to hear about it, loudly, with a KeyError, instead of getting a quiet wrong answer that you don't notice until later. That's what square brackets give you. A space with no note, on the other hand, is just an ordinary space, and .get() lets that be ordinary. Your data dictionary from Unit 5 is a good place to write down which fields are which.

Consistent identifiers

Here's a sneaky problem: "Studio", "studio", and "art_studio" are three different keys. To Python a key is just a string, and two strings are only equal if every single character matches, capitalization included. Worse, if a connection names a key that doesn't exist, nothing complains when you write it! The program only breaks when someone actually walks that way, which could be weeks later and on somebody else's computer. This is why each record has both an internal key and a display name. "studio" is for the program, so keep it short, lowercase, and consistent. "Art Studio" is for people, so it can be as fancy as you like.

You can catch this kind of mistake yourself, before anyone walks into it, by looping over every space and every connection in it: two Unit 5 loops, one inside the other. Here's a checker like that. I've planted a mistake in this version of the map, so the studio's north connection says "Kitchen", and there's no such key.

SPACES = {
    "lobby": {"name": "Main Lobby", "connections": {"east": "studio", "south": "courtyard"}},
    "studio": {"name": "Art Studio", "connections": {"west": "lobby", "north": "Kitchen"}},
    "courtyard": {"name": "Courtyard", "connections": {"north": "lobby"}},
}

problems = 0

for space_id, space in SPACES.items():
    for direction, destination in space["connections"].items():
        if destination not in SPACES:
            print(f"{space_id} goes {direction} to '{destination}', which doesn't exist.")
            problems += 1

if problems == 0:
    print("Every connection leads somewhere real.")
else:
    print(f"Found {problems} broken connection(s).")

The outer loop visits every space, and .items() hands it the key and the record together, which is the tuple unpacking from Unit 5. The inner loop does the same thing one level down, with each direction and the key it leads to.

Then destination not in SPACES asks whether that key is one of the outer dictionary's keys. (Using in on a dictionary always checks the keys, never the values.) Every broken connection gets reported and counted. If you run it you'll see studio goes north to 'Kitchen', which doesn't exist. Fix the typo, run it again, and you get the all-clear.

Nobody using the guide will ever see this program run! Its whole job is to check the data that a different program depends on. That might seem like a weird thing to write a program for, but programmers write little checkers like this constantly, and you'll want one for your dungeon's map too.

A checker like this is especially handy if you're working like a bricoleur. A planner might draw the whole map on paper first, every room and every connection, and then type it in all at once. If you're growing the map a room at a time instead, it's really easy to add a connection that points at a room you haven't written yet (or one you renamed ten minutes ago), and this tells you right away.

Try it: Pick three related things that point to each other, like three stops on a bus line, three scenes in a story, or three rooms in your own home. Then:

  1. Give every record the same three or four required fields.
  2. Include one list or inner dictionary.
  3. Retrieve three facts using nested lookups.
  4. Use .get() for one truly optional fact.
  5. Adapt the connection checker so it checks every connection or identifier in your data.
