Lesson 2 - Connect Data with Nested Dictionaries

By the end of this lesson, you will be able to:

  • Read values from a dictionary inside another dictionary.
  • Represent several related things with a consistent structure.
  • Represent connections as keys and values.
  • Use in and .get() when a key may be absent.

Records under one set of keys

A community-center guide needs to describe several spaces. We could make a separate variable for each one, but then nothing connects them, and "which room is east of the lobby?" has no place to live. Instead, let's use an outer dictionary that maps short identifiers to records that all have the same shape:

SPACES = {
    "lobby": {
        "name": "Main Lobby",
        "description": "Information desk, water fountain, and front entrance.",
        "connections": {"east": "studio", "south": "courtyard"},
        "feature": "information desk",
        "open": True,
    },
    "studio": {
        "name": "Art Studio",
        "description": "Tables, sinks, drying racks, and north-facing windows.",
        "connections": {"west": "lobby"},
        "feature": "community mural",
        "open": True,
    },
    "courtyard": {
        "name": "Courtyard",
        "description": "Benches circle a small rain garden.",
        "connections": {"north": "lobby"},
        "feature": "rain garden",
        "open": False,
        "note": "Closed during icy weather",
    },
}

That's a lot of punctuation at once, so let's take it apart. The whole thing is one dictionary, SPACES. It has three keys: "lobby", "studio", and "courtyard". The value stored under each key isn't a string or a number this time, it's a whole other dictionary, which is what "nested" means: a dictionary inside a dictionary. And one of the fields inside that, "connections", is a third, smaller dictionary. If you picture it as boxes inside boxes, you won't go far wrong.

(Why is SPACES in all capital letters? It's a Python convention, not a rule: a name in all caps tells the reader "this is set up once at the start and the program isn't going to change it while it runs." Python won't stop you from changing it, but other programmers will be surprised if you do.)

In Unit 5 we kept records in a list of dictionaries, and found them by position. Here the outer structure is a dictionary instead, so every record gets a name we can look it up by. That matters because the records are going to refer to each other: the lobby needs some way to say "the studio is east of me," and a short identifier like "studio" is a lot more reliable than "whatever happens to be at index 1."

The outer keys name the spaces. Each value is a dictionary with the same core fields. This same shape could describe transit stops, screens in a website, scenes in a story, departments in a store, or stages in a process: anything where you have several things of one kind that refer to each other.

Read from the outside in

print(SPACES["lobby"])
print(SPACES["lobby"]["name"])
print(SPACES["lobby"]["connections"])
print(SPACES["lobby"]["connections"]["east"])

Each line goes one level deeper than the one before it. The first prints the whole lobby record, all five fields. The second picks out just the "name" field, Main Lobby. The third gets the connections dictionary, {'east': 'studio', 'south': 'courtyard'}. And the last one reaches all the way in.

Read the last one left to right: get the lobby record, then its connections dictionary, then whatever is stored under "east". Each pair of square brackets hands back a value, and the next pair of brackets works on that value. The answer is studio, which is itself a key in SPACES. So we could look that up too, and keep going: SPACES["studio"]["name"] is Art Studio. That little hop, from one record to a key that names another record, is what the rest of this lesson is about.

If a long chain of brackets gets hard to read, it's fine to break it up with a temporary name, like lobby = SPACES["lobby"] and then lobby["connections"]["east"]. The next example does exactly that.

Storing connections

The connections dictionary works like a little map, but the idea is bigger than physical space. A lesson could point to the next lesson; a menu choice could point to a screen; a transit stop could point to the next stop down the line.

current_space = "lobby"
direction = "east"
connections = SPACES[current_space]["connections"]

if direction in connections:
    current_space = connections[direction]
    print("Now viewing:", SPACES[current_space]["name"])
else:
    print("That connection is not available.")

Let's trace it. current_space starts as "lobby", so connections is the lobby's connections dictionary. Is "east" one of its keys? Yes, so current_space becomes whatever's stored there, "studio", and we print Now viewing: Art Studio. If direction had been "north", the in check would have failed (the lobby has no north connection) and we'd get the "not available" message instead of a KeyError.

Notice what's not in this code: there's no special rule about the lobby's east side. The code asks the current record what "east" means and follows the answer. The data holds the details that vary, and the same few lines follow any connection in any map. Want to add a gift shop west of the courtyard? You add one record to SPACES and one entry to the courtyard's connections, and you don't touch this code at all. Compare that with writing if current_space == "lobby" and direction == "east" for every possible move, which is how a lot of people's first text adventure looks, and which gets out of hand around the fifth room. That's the trick, and it's why this data shape shows up so often. Once you've seen it you'll find it everywhere!

Required and optional facts

Every space has a name, description, connections, feature, and open status. Only the courtyard has a note. Square brackets are right when the key has to be there, because if it isn't, you want to find out with a loud KeyError rather than a quiet wrong answer. .get() is right when absence is ordinary and means something:

space = SPACES["courtyard"]

print(space["name"])
print(space.get("note", "No special note"))

ordinary_space = SPACES["studio"]
print(ordinary_space.get("note", "No special note"))

The courtyard has a note, so the second line prints Closed during icy weather. The studio doesn't, so the last line prints No special note instead of crashing. The second argument to .get() is what comes back when the key is missing. It doesn't add the key to the dictionary, so the studio record is exactly the same afterward as it was before.

So which should you use when? Ask what it would mean for the key to be missing. A space with no name is a mistake in the data, and you want to hear about it. A space with no note is just an ordinary space. Your data dictionary from Unit 5 is where you write that decision down.

Consistent identifiers

"Studio", "studio", and "art_studio" are three different keys. To Python a key is just a string, and two strings are equal only if every character matches, capitalization included. If a connection names an identifier that doesn't exist, nothing complains when you write it. The program only fails when someone actually walks that way, which could be weeks later and in somebody else's hands. So keep internal keys short, lowercase, and consistent, and let the display names be as expressive as you like. That's why each record has both: "studio" is for the program, "Art Studio" is for people.

You can check for this kind of mistake yourself, before anyone walks into it, by looping over every space and every connection in it: two Unit 5 loops, one inside the other. Here's a checker like that. I've planted a mistake in this version of the map: the studio's north connection says "Kitchen", and there's no such key.

SPACES = {
    "lobby": {"name": "Main Lobby", "connections": {"east": "studio", "south": "courtyard"}},
    "studio": {"name": "Art Studio", "connections": {"west": "lobby", "north": "Kitchen"}},
    "courtyard": {"name": "Courtyard", "connections": {"north": "lobby"}},
}

problems = 0

for space_id, space in SPACES.items():
    for direction, destination in space["connections"].items():
        if destination not in SPACES:
            print(f"{space_id} goes {direction} to '{destination}', which doesn't exist.")
            problems += 1

if problems == 0:
    print("Every connection leads somewhere real.")
else:
    print(f"Found {problems} broken connection(s).")

The outer loop visits every space, and .items() hands it the key and the record together—that's the tuple unpacking from Unit 5. The inner loop does the same thing one level down, with each direction and the identifier it leads to.

Then destination not in SPACES asks whether that identifier is one of the outer dictionary's keys. (in on a dictionary always checks the keys, never the values.) Every broken link gets reported and counted. Run it and you'll see studio goes north to 'Kitchen', which doesn't exist. Fix the typo, run it again, and you get the all-clear.

Nobody using the guide will ever see this program run! Its whole job is to check the data that a different program depends on, which is a really normal kind of program to write. You'll want one for your dungeon's map too.

This is also a good place to notice the two styles from Lesson 1 at work. A planner might sketch the whole map on paper first, every room and every connection, and then type it in. A bricoleur might write one room, run it, add a second room and a connection, run it again, and let the map grow. Both end up with the same kind of nested dictionary! And a checker like this one is a gift to the bricoleur in particular: when you're adding rooms on the fly, it's easy to leave a connection pointing at a room you haven't written yet, and the checker tells you right away.
