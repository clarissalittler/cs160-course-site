Lesson 4 - Make Actions Change State

By the end of this lesson, you will be able to:

  • Identify values that make up a program's changing state.
  • Use a returned value to update state.
  • Recognize when a function changes a list or dictionary directly.
  • Trace how one command moves through a main loop and helper function.

What state is

Back in Lesson 1 we said an interactive program has input, state, processing, and output. Lessons 2 and 3 were mostly about the data and the output. This lesson is about the part in the middle: how an action actually changes what the program remembers, and the two quite different ways Python lets a function do that. Different programs remember different things while they run:

ProgramPossible state
Playlist browserCurrent song index, queue, whether audio is playing.
Lending kioskAvailable items, borrowed items, whether the menu is running.
Study timerCurrent phase, completed rounds, paused or active.
Interactive storyCurrent scene, collected clues, earlier choices.

State isn't a special Python type. It's just the ordinary values whose current contents affect what happens next, like the integer that decides which song "next" goes to. A handy test: if you paused the program halfway through, what would you have to write down to pick up exactly where you left off? Whatever's on that list is the state.

That pause-and-write-it-down question is a planner's tool: you can answer it before writing a line of code. Bricoleurs tend to discover state the other way around. They run the program, notice that it forgot something it needed ("wait, why is the key back on the floor?"), and realize that thing has to be remembered. Either route works, and plenty of programmers use both: plan the state you can see coming, and add the state you discover along the way.

Returning an updated value

def advance(current_index, songs):
    if len(songs) == 0:
        return current_index, "The playlist is empty."

    if current_index + 1 >= len(songs):
        return 0, "Returning to the first song."

    return current_index + 1, "Moving to the next song."


songs = ["Low Tide", "Night Bus", "Paper Stars"]
current_index = 0

current_index, message = advance(current_index, songs)
print(message)
if len(songs) > 0:
    print("NOW SELECTED:", songs[current_index])

Let's trace it. current_index starts at 0, which is "Low Tide". We call advance(0, songs). The playlist isn't empty, and 0 + 1 is 1, which is less than 3, so we skip both ifs and return 1, "Moving to the next song." The program prints the message and then NOW SELECTED: Night Bus. Call it again and you'd get index 2, Paper Stars. Call it a third time and 2 + 1 is 3, which would be past the end of the list, so the second if wraps back around to 0. That's the off-by-one boundary from Unit 5, handled on purpose.

The function returns two values, an index and a message, using the tuple trick from Unit 5. The caller unpacks them and stores the new index back into current_index. That last part matters more than it looks. If the caller runs advance(current_index, songs) and ignores the result, the selection doesn't change, and nothing warns you. The function did its job; the caller just dropped the answer on the floor.

Why doesn't the function just change current_index itself? Because inside the function, current_index is the function's own local name. Assigning a new number to it only changes the function's copy of the name, and the caller never hears about it. So for a plain number or string, returning the new value is how you get it back out.

Changing a collection directly

def borrow_item(title, available, borrowed):
    if title not in available:
        return f"{title} is not available."

    available.remove(title)
    borrowed.append(title)
    return f"Borrowed: {title}"


available = ["Field Guide", "Umbrella", "Chess Set"]
borrowed = []

print(borrow_item("Umbrella", available, borrowed))
print("AVAILABLE:", available)
print("BORROWED:", borrowed)

Here's the other way. This function doesn't return new lists. It changes the two lists it was handed: one loses a title, the other gains it. This is the aliasing from Unit 5 doing useful work. Inside the function, available is another name for the same list that's called available outside, so the change is visible everywhere. Call it again with "Umbrella" and it takes the unavailable path, so there's no duplicate.

So why does this work when changing current_index didn't? Because available.remove(title) doesn't reassign a name. It reaches through the name and changes the list itself, and that's the same list the caller has. Methods like .append() and .remove(), and assigning to a key or an index, change the object. Plain = on a name only changes which value the name points to.

Which approach is better? Neither, really, and you'll see both all the time. Returning a value is easier to follow, because everything that changes is right there in the assignment. Mutating is handy when a function needs to update several related collections at once, like moving an item from one list to another. The important thing is to know which one a function does. A good habit is to say so in the function's name or a comment, so nobody has to guess.

Here's a pair of functions that show the difference. They look like they do the same thing, and they don't:

def save_wrong(favorites, title):
    favorites = favorites + [title]

def save_right(favorites, title):
    favorites.append(title)

favorites = []
save_wrong(favorites, "Night Bus")
print(favorites)
save_right(favorites, "Night Bus")
print(favorites)

The first print shows [], and the second shows ['Night Bus']. What happened?

In save_wrong, the expression favorites + [title] builds a brand-new list, and then = points the function's own local name at it. The caller's list never gets touched, and when the function ends, the new list just gets thrown away. In save_right, .append() reaches through the name and changes the list the caller actually handed over.

If you ever have a function that "obviously" adds something to a list, and the list is still empty afterward, check for this first. It's a really common bug, and Python won't give you an error message for it. As far as Python can tell, building a new list and giving it a name is exactly what you asked for!

Changing nested records

events = {
    "repair_cafe": {"title": "Repair Café", "seats": 2},
    "poetry_walk": {"title": "Poetry Walk", "seats": 1},
}

event = events["repair_cafe"]

if event["seats"] > 0:
    event["seats"] -= 1
    print("Reserved one seat.")
else:
    print("No seats remain.")

print(events["repair_cafe"])

event is another name for the inner dictionary that lives inside events. Change its seat count and you've changed the nested structure. Same idea as the lending kiosk, dictionary edition. The line event = events["repair_cafe"] didn't copy anything; it just gave us a shorter name for a record that's still inside events. So when we print events["repair_cafe"] at the end, the seat count shows 1.

This is the kind of thing that makes a text adventure work. When the player picks up a key, the program can remove it from the room's record in the rooms dictionary, and from then on that room is described without the key in it. The world remembers.

The main loop

running = True

while running:
    print("Commands: borrow, show, quit")
    command = input("Choose: ").strip().lower()

    if command == "borrow":
        title = input("Item title: ").strip()
        print(borrow_item(title, available, borrowed))
    elif command == "show":
        print("AVAILABLE:", available)
        print("BORROWED:", borrowed)
    elif command == "quit":
        running = False
    else:
        print("That command is not available.")

This is the same shape as the pseudocode from Lesson 1, now in real Python. The running flag starts out True, and the only way it becomes False is the quit branch, so the loop keeps going, one command at a time, until someone asks to leave. Every other branch does its thing and then falls through to the bottom of the loop, back around to the menu.

The main loop reads like a table of contents: it figures out which action was requested and hands the actual work to a function. When a loop like this starts doing the detailed work itself, it gets long and hard to test, so keep the jobs in the functions and let the loop direct traffic.
