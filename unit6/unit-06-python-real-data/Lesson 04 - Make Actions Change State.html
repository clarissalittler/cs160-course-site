Lesson 4 - Make Actions Change State

By the end of this lesson, you will be able to:

  • Identify values that make up a program's changing state.
  • Use a returned value to update state.
  • Recognize when a function changes a list or dictionary directly.
  • Trace how one command moves through a main loop and helper function.

What state is

Back in Lesson 1 we said an interactive program has input, state, processing, and output. Lessons 2 and 3 were mostly about the data and the output. This lesson is about the part in the middle: how an action actually changes what the program remembers. It turns out Python gives a function two pretty different ways to do that, and mixing them up causes one of the most confusing bugs you'll run into. First, though, here's what a few different programs might need to remember while they run:

ProgramPossible state
Playlist browserCurrent song index, queue, whether audio is playing.
Lending kioskAvailable items, borrowed items, whether the menu is running.
Study timerCurrent phase, completed rounds, paused or active.
Interactive storyCurrent scene, collected clues, earlier choices.

State isn't a special kind of Python value. It's just the ordinary values whose current contents affect what happens next, like the integer that decides which song "next" goes to. Here's a handy test for figuring out what a program's state is: if you paused the program halfway through and had to write down enough to pick up exactly where you left off, what would you write down? Whatever's on that list is the state.

That's a question you can answer before writing a single line of code, so it's a natural tool for planners. Bricoleurs usually find their state the other way around. They run the program, notice that it forgot something ("wait, why is the key back on the floor?"), and realize that thing needs to be remembered. Most people end up doing some of both, planning the state they can see coming and adding the state they discover along the way.

Returning an updated value

def advance(current_index, songs):
    if len(songs) == 0:
        return current_index, "The playlist is empty."

    if current_index + 1 >= len(songs):
        return 0, "Returning to the first song."

    return current_index + 1, "Moving to the next song."


songs = ["Low Tide", "Night Bus", "Paper Stars"]
current_index = 0

current_index, message = advance(current_index, songs)
print(message)
if len(songs) > 0:
    print("NOW SELECTED:", songs[current_index])

Let's trace through it. current_index starts at 0, which is "Low Tide". We call advance(0, songs). The playlist isn't empty, and 0 + 1 is 1, which is less than 3, so we skip both ifs and return 1, "Moving to the next song." The program prints the message and then NOW SELECTED: Night Bus. If we called it again we'd get index 2, Paper Stars. Call it a third time and 2 + 1 is 3, which is past the end of the list, so the second if wraps back around to 0. That's the off-by-one boundary from Unit 5, handled on purpose.

The function returns two values, an index and a message, using the tuple trick from Unit 5. The caller unpacks them and stores the new index back into current_index. That last part is more important than it looks! If the caller just runs advance(current_index, songs) on its own line and doesn't store the result anywhere, the selection never changes, and nothing warns you about it. The function did its job, and then the answer got thrown away.

So why doesn't the function just change current_index itself? Because inside the function, current_index is the function's own local name. Assigning a new number to it only changes what the function's copy of the name points to, and the caller never hears about it. So for a plain number or string, returning the new value is how you get it back out of the function.

Changing a collection directly

def borrow_item(title, available, borrowed):
    if title not in available:
        return f"{title} is not available."

    available.remove(title)
    borrowed.append(title)
    return f"Borrowed: {title}"


available = ["Field Guide", "Umbrella", "Chess Set"]
borrowed = []

print(borrow_item("Umbrella", available, borrowed))
print("AVAILABLE:", available)
print("BORROWED:", borrowed)

Here's the other way to do it. This function doesn't return anything new. It changes the two lists it was handed: one list loses a title, and the other one gains it. This is the aliasing from Unit 5, except that this time it's doing something useful for us. Inside the function, available is just another name for the same list that's called available outside, so the change shows up everywhere. If you call it again with "Umbrella", it takes the "not available" path, so you don't end up with a duplicate.

Wait, so why does this work when changing current_index didn't? Because available.remove(title) doesn't point the name at something new. It reaches through the name and changes the list itself, and that's the same list the caller has. Methods like .append() and .remove(), and assigning to a key or an index, change the object. Using plain = on a name only changes which value the name points to.

So which way is better? Neither, really, and you'll see both all the time. Returning a value is easier to follow, because everything that changes is right there in the assignment where you can see it. Changing a list directly is handy when a function needs to update several related collections at once, like moving an item from one list to another. What matters is knowing which one a function does, so it's a good habit to say so in the function's name or in a comment, so nobody has to guess.

Here's a pair of functions that make the difference really obvious. They look like they do the same thing, and they don't:

def save_wrong(favorites, title):
    favorites = favorites + [title]

def save_right(favorites, title):
    favorites.append(title)

favorites = []
save_wrong(favorites, "Night Bus")
print(favorites)
save_right(favorites, "Night Bus")
print(favorites)

The first print shows [], and the second shows ['Night Bus']. What happened?

In save_wrong, the expression favorites + [title] builds a brand-new list, and then = points the function's own local name at it. The caller's list never gets touched, and when the function ends, the new list just gets thrown away. In save_right, .append() reaches through the name and changes the list the caller actually handed over.

If you ever write a function that "obviously" adds something to a list, and the list is still empty afterward, check for this first. It's a really common bug, and Python won't give you an error message for it, because as far as Python can tell, building a new list and giving it a name is exactly what you asked for!

Changing nested records

events = {
    "repair_cafe": {"title": "Repair Café", "seats": 2},
    "poetry_walk": {"title": "Poetry Walk", "seats": 1},
}

event = events["repair_cafe"]

if event["seats"] > 0:
    event["seats"] -= 1
    print("Reserved one seat.")
else:
    print("No seats remain.")

print(events["repair_cafe"])

The line event = events["repair_cafe"] doesn't copy anything. It just gives us a shorter name for a record that's still sitting inside events. So when we change the seat count through event, we've changed the nested structure, and when we print events["repair_cafe"] at the end, the seat count shows 1. It's the same idea as the lending kiosk, just with dictionaries instead of lists.

This is exactly the kind of thing that makes a text adventure work. When the player picks up a key, the program can remove it from that room's record in the rooms dictionary, and from then on the room gets described without the key in it.

The main loop

running = True

while running:
    print("Commands: borrow, show, quit")
    command = input("Choose: ").strip().lower()

    if command == "borrow":
        title = input("Item title: ").strip()
        print(borrow_item(title, available, borrowed))
    elif command == "show":
        print("AVAILABLE:", available)
        print("BORROWED:", borrowed)
    elif command == "quit":
        running = False
    else:
        print("That command is not available.")

This is the same shape as the pseudocode from Lesson 1, except now it's real Python. The running flag starts out True, and the only thing that ever makes it False is the quit branch, so the loop keeps going, one command at a time, until someone asks to leave. Every other branch does its thing and then falls through to the bottom of the loop and back around to the menu.

Notice that the main loop doesn't do much of the actual work itself. It figures out which command was typed and then hands the job off to a function, a bit like a table of contents pointing you to the right chapter. You could put all the work right inside the loop, but then the loop gets really long, and it gets much harder to test any one action by itself.
