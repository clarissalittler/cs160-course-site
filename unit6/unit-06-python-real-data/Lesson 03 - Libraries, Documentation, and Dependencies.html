Lesson 3 - Libraries, Documentation, and Dependencies

Our goals for this lesson—by the end you'll be able to:

  • Distinguish a module, package, Standard Library component, and third-party dependency.
  • Import and use a small Standard Library function.
  • Read a function signature, short description, parameters, and return-value documentation.
  • Identify source, version, maintenance, license, privacy, and trust questions raised by a dependency.

Most software is assembled, not written from nothing

You didn't write print(). You didn't write csv.DictReader, and you certainly didn't write Python's file system. Nearly all software is built on layers of code that already existed. Some vocabulary: a module is an importable Python file or component, a package organizes modules, and a library is the broader, looser term for a collection of reusable code—people use it pretty informally.

The Python Standard Library ships with Python itself. Modules such as csv, random, statistics, pathlib, and sqlite3 are right there waiting for you—normally no separate installation required.

Import a module and qualify its names

import statistics

wait_times = [12, 18, 9, 25, 16]
print(statistics.mean(wait_times))
print(statistics.median(wait_times))

statistics.mean names both the module and the function, and that little qualification is doing real work: a reader can see at a glance where the operation came from.

You may also see:

from statistics import mean
print(mean(wait_times))

This is shorter, but now the source is invisible at each call. And avoid from statistics import * entirely—dumping every public name into your program invites collisions and makes it surprisingly hard to tell where anything came from.

Documentation is part of the interface

A simplified function signature looks something like this:

statistics.mean(data)

When you read documentation, you're hunting for answers to four questions:

  1. What job does the function promise? Calculate the arithmetic mean.
  2. What arguments does it expect? An iterable of numerical values.
  3. What does it return? One numerical mean.
  4. What exceptions or limits matter? An empty dataset raises an error; mixed or unsupported types may not make sense.

An example you copy from the docs is evidence of one call that works—not a complete specification. Change its values, feed it an empty collection, and connect each argument back to the written signature.

Use a library without surrendering the concept

statistics.mean(values) saves you code, but you should still know what a mean is: total the values, divide by the count. That knowledge is what lets you interpret empty data, double-check a surprising result, and decide whether a median tells the story better.

def report_wait_times(wait_times):
    if len(wait_times) == 0:
        print("No wait-time observations are available.")
        return

    print(f"Observations: {len(wait_times)}")
    print(f"Mean: {statistics.mean(wait_times):.1f} minutes")
    print(f"Median: {statistics.median(wait_times):.1f} minutes")

The library does the arithmetic. Your program still has to supply everything else—the empty-data behavior, the units, the labels, the interpretation.

Third-party packages add installation and trust

A third-party package is distributed separately from Python. Installers such as pip can fetch one for you—but installing things may simply not be allowed on a school or workplace computer. Browser notebooks sometimes come with popular packages preloaded, or let you install temporarily.

Required work in this unit sticks to the Standard Library on purpose, so it runs in Colab, OnlineGDB, or a basic local Python installation without anyone needing administrator access. Later data notebooks may hand you third-party tools in an environment that's already set up.

A dependency is part of your program's risk

Before adopting a dependency, it's worth interrogating it a little:

  • Source: Is this the intended project, or an imitation with a similar name?
  • Maintenance: Is it actively maintained, and are security reports addressed?
  • Version: Which version does the program expect? Could an update change behavior?
  • Compatibility: Does it support the Python and operating-system versions students can access?
  • License: What reuse and attribution conditions apply?
  • Privacy and network access: Does it send data elsewhere or download additional components?
  • Necessity: Does the benefit justify adding another thing that can fail?

“Open source” means the source code is available under some license. That's all it means—not secure, not maintained, not ethical, not suitable for every purpose. Each of those has to be checked separately.

Versions make claims time-dependent

Documentation may be describing a newer version than the one you're actually running. When a call behaves differently from an example, write down the Python version, the package version if relevant, the complete error, and the smallest piece of code that reproduces the problem. “It doesn't work” becomes a useful report the moment another person can recreate it.

AI-generated and copied code are dependencies, too

Code suggested by a person, a website, or an AI system needs the same scrutiny: source review, tests, and attribution where required. Don't paste in code that handles files, credentials, or network requests without understanding what it reads, writes, or transmits. If you can't explain a line, isolate it and investigate before you build anything on top of it.
