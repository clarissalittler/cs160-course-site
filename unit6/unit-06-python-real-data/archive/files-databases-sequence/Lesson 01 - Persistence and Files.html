Lesson 1 - Persistence and Files

What you'll be able to do by the end of this lesson:

  • Explain the difference between in-memory state and persistent data.
  • Read and write a UTF-8 text file with a context manager.
  • Predict how read, write, and append modes affect an existing file.
  • Handle a missing file as an expected first-run condition.

Memory disappears; a file can remain

Back in Unit 5, our catalog lived in a list, and that list lived inside the running Python process. The moment the process ends—the program finishes, the tab closes, the power blinks—every variable in it is gone. Persistent data is data stored somewhere that's meant to outlive a single run: a file, a database, or a remote service.

Persistence changes a program's whole story. The first run may have no saved data at all. A later run may load old data written by a different version of the program. Files get moved, mangled, half-downloaded, shared with someone who reads them differently than you intended, &c. Once your program remembers things, you have to start thinking about time.

Write a text file

notes = ["check bus schedule", "bring headphones", "pack a snack"]

with open("trip_notes.txt", "w", encoding="utf-8") as output_file:
    for note in notes:
        output_file.write(note + "\n")

print("Saved trip_notes.txt")

open() hands back a file object. The with statement wraps it in a context manager—a promise that when the indented block ends, Python closes the file, even if something goes wrong partway through. The name output_file is just there so the code has something to call the open file.

Mode "w" means write from the beginning. If the file already exists, its old contents are replaced—not moved somewhere safe, replaced. If it doesn't exist, Python creates it. "\n" is a newline character; leave it out and every note runs together on one line.

Read a text file

loaded_notes = []

with open("trip_notes.txt", "r", encoding="utf-8") as input_file:
    for line in input_file:
        loaded_notes.append(line.rstrip("\n"))

print(loaded_notes)

Mode "r" means read. Looping over a file produces one line at a time, and each line usually arrives still wearing its final newline. .rstrip("\n") peels off exactly that newline and nothing else. A general .strip() would also delete leading and trailing spaces someone may have put there on purpose—maybe you want that, maybe you don't.

Append adds without replacing

with open("trip_notes.txt", "a", encoding="utf-8") as output_file:
    output_file.write("charge phone\n")

Mode "a" appends at the end. Before you try it, predict the file's contents after these runs:

  1. Run the original "w" program once.
  2. Run the append program twice.
  3. Run the original "w" program again.

That last write-mode run erases both appended lines. Picking a mode is a small but consequential choice, so use variable names and confirmation messages that make it obvious which operation you meant.

Paths describe where a file lives

"trip_notes.txt" is a relative path: it points at a file in whatever directory the program happens to be running in. Browser-based notebooks and online interpreters often give you temporary storage that doesn't live where—or as long as—files on your own computer do. Print or inspect your environment's file list, and download anything you want to keep. I've lost work to a vanished runtime before; I don't recommend the feeling.

A path like "data/trip_notes.txt" means a file inside a data folder. A path that works on one computer can fail on another if it bakes in a private username, a drive letter, or a folder that only exists on your machine. Relative project paths are usually the easiest kind to share.

A missing file can be a normal state

def load_notes(filename):
    notes = []

    try:
        with open(filename, "r", encoding="utf-8") as input_file:
            for line in input_file:
                notes.append(line.rstrip("\n"))
    except FileNotFoundError:
        print(f"No saved file named {filename}; starting with an empty list.")

    return notes

notes = load_notes("trip_notes.txt")
print(f"Loaded {len(notes)} notes.")

try runs code that might fail. except FileNotFoundError catches only that one named failure—it doesn't paper over every possible bug, which is just what you want. On a first run, an empty list is a perfectly reasonable result, and the message tells you what happened instead of leaving you to wonder.

Encoding and line endings are agreements

Text has to be translated between human-readable characters and the bytes that actually sit on disk. Naming encoding="utf-8" makes that agreement explicit, and UTF-8 covers an enormous range of the world's writing systems. Operating systems also disagree about how a line should end (of course they do); Python's text mode normally translates between the conventions for you. Explicit encoding plus ordinary newline handling makes shared projects far more predictable.

Persistence creates responsibility

A value in memory may vanish in seconds. A saved file can be copied, backed up, emailed, or opened years later by someone you've never met. So before saving, ask: does the program really need this data? If the machine is shared, who else can read the file? What does the filename itself reveal? How would someone delete it? “The program remembers” is only a feature when people understand what's being remembered and have some control over it.
