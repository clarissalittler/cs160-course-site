Lesson 5 - Software as an Evolving Artifact

This lesson should leave you able to:

  • Turn a requirement into a concrete acceptance example.
  • Separate loading, processing, display, and saving responsibilities.
  • Use repeatable tests to protect behavior during refactoring.
  • Maintain a small change log and review copied or AI-generated code responsibly.

“It ran once” is a beginning

Real software changes. A file gains a column. A user asks for a new filter. A label you thought was crystal clear confuses someone. A library update changes behavior underneath you. A teammate has to understand code you wrote months ago. Software engineering is, in large part, the set of practices that let a program stay useful through all of that.

Requirements need acceptance examples

A requirement such as “the program can filter resources by area” is helpful but incomplete—filter how? show what? An acceptance example makes success something you can actually observe:

Given three records, two with area North and one with area Central,
when the user filters for North,
then the program displays the two North records, reports “2 matches,” and does not display the Central record.

Specify the empty result too: filtering for South displays “No matching resources” without changing or deleting records.

Separate responsibilities

A single hundred-line menu function may well run, but every change to it risks breaking something unrelated. Give the major jobs names:

def load_resources(filename):
    # Read CSV, convert fields, and return records.
    pass

def save_resources(filename, resources):
    # Write all records using the documented schema.
    pass

def filter_by_area(resources, requested_area):
    matches = []
    for resource in resources:
        if resource["area"].lower() == requested_area.lower():
            matches.append(resource)
    return matches

def show_resources(resources):
    # Display labeled records or an explicit empty state.
    pass

def show_menu(record_count):
    # Display state and available actions.
    pass

This is separation of concerns. Loading is the only part that knows about the file format. Filtering knows the selection rule. Display knows how to talk to a person. The main menu just coordinates the others.

Tests protect behavior

A regression is old behavior that breaks after a change—the program used to do this correctly, and now it doesn't. A repeatable test set is how you catch them:

sample = [
    {"name": "Tool Library", "area": "North", "cost": 0.0},
    {"name": "Repair Cafe", "area": "Central", "cost": 0.0},
    {"name": "Bike Workshop", "area": "North", "cost": 10.0},
]

assert len(filter_by_area(sample, "North")) == 2
assert len(filter_by_area(sample, "north")) == 2
assert len(filter_by_area(sample, "South")) == 0
assert len(filter_by_area([], "North")) == 0

print("Filter tests passed.")

assert condition stops with an AssertionError if the condition is false. These are small automated checks, not a complete testing framework—and their value is precisely that they can be rerun after every revision.

File behavior needs tests too: missing file, empty file, one valid row, malformed numeric field, save then reload, and a filename you don't have permission to write. Some environments make the permission test hard to set up; when that happens, document what you could and couldn't test.

Refactor without changing promised behavior

Refactoring means changing the structure of code without intentionally changing what it does from the outside. You might extract repeated display code into a function, rename a variable that keeps confusing people, or separate a calculation from the input code around it. Run the same acceptance examples before and after. If the results changed, you have a decision to make: did you find a bug, introduce one, or actually change a requirement?

Readable documentation has several levels

  • Descriptive names explain values and actions locally.
  • Comments explain non-obvious reasons and assumptions.
  • A function contract explains inputs, result, effects, and failure behavior.
  • A README explains purpose, setup, files, how to run, and known limitations.
  • A data dictionary explains fields, types, units, missing values, and provenance.

Comments that merely repeat the syntax go stale fast. Document why cost = None is preserved, not the fact that cost is assigned.

Version history is an explanation over time

Version control systems such as Git record changes, who made them, and why. You don't need a GitHub account to practice the underlying discipline, though—dated copies or a lightweight change log will do:

Version/dateChangeReasonEvidence
0.1added area filtercatalog needed neighborhood searchfour filter tests pass
0.2explicit empty-result messagetester thought blank output was a crashacceptance example passes

A useful change note says what and why—not “stuff” or “final final version.” (We've all written those. We've all regretted them.)

Code review is a conversation about evidence

A reviewer can check whether the requirements are covered, the names communicate intent, errors preserve data, file operations are safe, and the tests include boundaries. Constructive feedback points to a behavior and its consequence: “When there are no records, the average divides by zero; add an empty-state test” gives the author somewhere to go. “This is bad” does not.

Copied or AI-generated code remains your responsibility

Record where any substantial borrowed code came from and follow its license or the course rules. For AI-generated code: record the prompt or assistance when required, inspect every file and network operation, remove any technique you can't explain, and test against the stated requirements. A confident explanation from a tool is not evidence that the program is correct or safe—tools are very good at sounding sure.

Maintenance studio. Take a working collection or file program and:

  1. write three acceptance examples, including an empty or failure case;
  2. separate at least three responsibilities into functions;
  3. create at least four repeatable checks;
  4. refactor one unclear or repeated section;
  5. ask another person for one evidence-based review comment;
  6. record the revision in a change log; and
  7. cite any substantial copied or generated code.

End of Unit 6: You can now preserve records in files, audit a CSV, use documentation and dependencies deliberately, recognize a basic database query, and revise software while tests protect its behavior. That's a lot. Unit 7 steps back from any one program to compare algorithms and ask what computation can and cannot do efficiently—or at all.
