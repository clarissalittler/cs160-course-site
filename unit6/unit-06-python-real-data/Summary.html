Unit 6 Summary

Unit 6 moved beyond a program that works once. Persistent files survive a run; CSV records require types, quality rules, and provenance; libraries save work while adding dependencies; SQL expresses familiar collection questions in database form; and tests plus version history let software change without abandoning evidence.

What to carry forward

  • with open(...) closes a file when the block ends. Read, write, and append modes have different consequences.
  • Relative paths are easier to share; browser-based environments may provide temporary storage.
  • Name UTF-8 encoding and treat a missing file as an expected first-run state when appropriate.
  • csv.DictReader maps headers to text values. Convert types once while loading.
  • Missing, malformed, and inconsistent values need documented actions and a visible quality log.
  • A data dictionary explains fields; provenance explains source, date, collection method, license, units, and omissions.
  • The Standard Library ships with Python; third-party dependencies add installation, version, maintenance, license, privacy, and trust questions.
  • Documentation describes a function's signature, parameters, return, limits, and failure behavior.
  • Python loops and SQL can both select rows, select fields, sort, and aggregate.
  • Basic SQL includes SELECT, FROM, WHERE, ORDER BY, COUNT, and AVG. Parameterized queries keep data separate from SQL code.
  • Acceptance examples make requirements observable; repeatable tests reveal regressions.
  • Separation of concerns, refactoring, code review, documentation, and change logs make software maintainable.
  • Copied or AI-generated code remains the programmer's responsibility to understand, test, secure, cite, and revise.

Readiness check

Can you load a missing or valid file without destroying evidence, explain every CSV conversion, produce the same filter in Python and SQL, rerun tests after a refactor, and state what the program saves and trusts?
