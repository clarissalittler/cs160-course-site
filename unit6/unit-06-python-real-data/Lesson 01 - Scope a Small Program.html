Lesson 1 - Scope a Small Program

By the end of this lesson, you will be able to:

  • Describe an interactive program as input, state, processing, and output.
  • Write a short sample interaction before writing code.
  • Separate the smallest complete path from optional ideas.
  • Turn a feature into an observable test.

Begin with one ordinary interaction

Here's a thing that happens to nearly everyone the first time they sit down to write a program of their own, as opposed to an exercise someone else designed: you open a blank file, you have a fun idea in your head, and you have no idea what the first line should be. The idea is a feeling. Python wants instructions. This lesson is about the steps in between.

The trick I'd suggest is to not start with code at all. Start with a person using the finished thing. Imagine a music-request kiosk at a community event, a little laptop on a table where people can ask for songs. Before deciding anything about how the code works, write down what one successful use should look like:

MUSIC REQUEST DESK
1. Add a song
2. Show the queue
3. Play the next song
4. Quit
> 1
Song title: Dancing in the Moonlight
Added to the queue.
> 2
1. Dancing in the Moonlight
> 3
Now playing: Dancing in the Moonlight
> 4
Thanks for helping with the music.

A made-up transcript like this is sometimes called a sample interaction, and it's the cheapest prototype there is. You don't need to know any Python to write one, and you can hand it to a friend and ask "is this what you'd expect?" before you've written a single line.

That transcript is already a plan. Look at what it tells us the program needs: a menu, a way to read a choice, a list of requested songs, a loop, and actions that add, display, and remove songs. Now look at what it doesn't need yet: accounts, streaming audio, voting, album art, a connection to Spotify. Those might be fun later (and I'd encourage you to try!). They're not the program.

Input, state, processing, and output

PartMusic-kiosk exampleAnother example
InputA menu choice or song title.A café order, quiz answer, or search word.
StateThe current request queue.A basket, score, selected screen, or list of results.
ProcessingAdd a title, choose the first title, or reject an unavailable action.Calculate, compare, filter, or update.
OutputThe menu, queue, confirmation, or error message.A receipt, recommendation, status panel, or story response.

Input is what arrives right now. State is what the running program has to remember from one moment to the next. Processing reads both and may change the state. Output tells a person what happened.

Let's run the kiosk transcript through those four. When someone types 1 and then Dancing in the Moonlight, that's input. The processing is "add this title to the end of the queue," which changes the state: the queue went from empty to having one song in it. The output is Added to the queue. Then when someone types 2, the input is different, the processing only reads the state without changing it, and the output is the list of songs. Same four parts every time around the loop.

State is the one people tend to forget about, because you can't see it in the transcript directly. It's the thing that makes typing 2 show a different answer before and after someone typed 1. If you find yourself thinking "but how does the program know that?", the answer is almost always "it's in the state." This is a way of thinking about any interactive program at all, not just kiosks, and once you've seen it you'll notice it in every app on your phone: your messaging app's state is your conversations, a game's state is your position and score and inventory, &c.

Protect the smallest complete path

A vertical slice is one thin path through the whole program, top to bottom. For the kiosk, it might be:

  1. Display the menu.
  2. Add one request.
  3. Show that request.
  4. Play and remove it.
  5. Quit cleanly.

The name comes from picturing the program as layers stacked on top of each other: the menu on top, the choices in the middle, the data at the bottom. A vertical slice cuts straight down through all of them, instead of finishing one whole layer (say, a gorgeous menu with twelve options) before any of the layers underneath exist.

Get that path working before you add anything else. I can't stress this enough: the most common way small projects die is by starting five features and finishing none. You end up with a program where adding songs half-works, voting half-works, and the playlist display half-works, and because none of them is finished, you can't even show anyone what you were going for. A slice that works all the way through, even if it's small, is something you can run, test, show a friend, and build on.

Notice that a second request is just test data, not a new feature, while voting and user accounts are whole new features. Every addition creates more paths that can break and more things a user has to learn. So the slice should be boring on purpose, and the interesting ideas can wait until it runs.

Requirements should be observable

"The queue works" is hard to test, because what does works mean? A concrete example is better:

Given a queue containing two songs,
when the program plays the next song,
then it displays the first title and the queue contains only the second title.

This says what should be visible before and after one action, which is something you can actually check. Given is the starting state, when is the one action, and then is what you should be able to see afterward. Nothing in it is about how the code works inside. That's on purpose: it describes the behavior, so it's still a good test even if you rewrite the code completely.

Notice how much the concrete version pins down that "the queue works" doesn't. It says which song should play (the first one, not the last one or a random one) and it says the song should be removed, not just displayed. Those are exactly the details that are easy to get wrong. The same shape works for a recommendation, a shopping basket, a branching scene, or anything else.

Pseudocode gives the loop a shape

set the request queue to an empty list
set running to true

while running:
    display the menu
    ask for a choice

    if the choice is add:
        ask for a title and add it to the queue
    otherwise if the choice is show:
        display every request
    otherwise if the choice is play next:
        display and remove the first request
    otherwise if the choice is quit:
        set running to false
    otherwise:
        explain the available choices

Pseudocode is a program written in plain language instead of Python: the structure of the real thing, with the fussy details left out. There aren't any rules for it, you just write the steps clearly enough that you could translate them later. Look at how closely this follows the transcript we started with. Each menu option became one branch, the queue became a list, and "keep going until they quit" became a while loop with a running flag, the same kind of loop from Unit 4.

Pseudocode isn't busywork you throw away. It lets you check the sequence before punctuation and exact syntax start demanding your attention. In my experience nearly every bug in a program like this is a logic bug in one of those branches, and it's a lot easier to spot a logic bug in fifteen lines of English than in forty lines of Python.

Same four parts, different program

Let's try the input/state/processing/output idea on a real program, and one that isn't a menu at all. Say a potluck wants to know which dish people liked best. Everyone types in a vote, and when they're done, the program prints a tally:

votes = {}

print("POTLUCK VOTE: type the dish you liked best.")
print("Press Enter on an empty line when everyone has voted.")

vote = input("Vote: ").strip().lower()
while vote != "":
    if vote in votes:
        votes[vote] += 1
    else:
        votes[vote] = 1
    vote = input("Vote: ").strip().lower()

if len(votes) == 0:
    print("No votes were cast.")
else:
    winner = None
    for dish, count in votes.items():
        print(f"{dish}: {count}")
        if winner is None or count > votes[winner]:
            winner = dish
    print(f"Most votes: {winner} ({votes[winner]})")

Before you read the details, try sorting it into the four parts yourself.

The input is one vote at a time. The state is the votes dictionary, which maps each dish to how many votes it has so far. The processing cleans up each vote and adds one to the right count. The output is the tally and the winner.

So it's shaped completely differently from the music desk, and it still has the same four parts!

The loop is the sentinel pattern from Unit 4, where a negative number meant "I'm done entering donations." Here, an empty line means "done." There are two input calls, and you need both of them: one before the loop, so there's a vote to check the first time through, and one at the bottom, to get the next vote. Forget the second one and the loop runs forever.

The counting works like the counters from Unit 5, except that every dish needs its own count, so the counts live in a dictionary. Seen this dish before? Add one. Haven't? Start it at 1.

Every vote also goes through .strip().lower() first. That way Lentil Soup and lentil soup (with a sneaky trailing space) end up as the same key. Without it, Python would treat them as two different dishes, and the soup would split its own vote. Poor soup.

The last part finds the dish with the most votes, using the same idea as the min/max lesson in Unit 5: don't make up a starting value, start from the first real one. winner begins as None, meaning "no winner yet," and the first dish the loop sees takes the spot. After that, a dish only takes over if its count is strictly bigger.

So here's a fun question: what happens in a tie? Dictionaries remember the order their keys were added, and > never switches on an equal count, so a tie goes to whichever dish got its first vote earliest. That means this program has a tie-breaking rule, even though nobody sat down and decided on one! It's just a side effect of how the loop happens to be written. (We'll come back to rules like that at the end of the unit.)

Planning studio. Choose a small request queue, packing checklist, recommendation kiosk, resource finder, or interactive scene. Then:

  1. Write a five-to-eight-action sample interaction.
  2. Circle the inputs and underline every value that must change.
  3. Describe the smallest complete path.
  4. Write two Given/When/Then checks.
  5. Put every other idea under an “only after the basic path works” heading.
  6. Change the potluck program so a tie is announced as a tie (for example, Tie: lentil soup and cornbread (2 each)) instead of just picking one.
