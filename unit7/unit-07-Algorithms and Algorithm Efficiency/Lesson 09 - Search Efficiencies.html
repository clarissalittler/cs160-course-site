Lesson 09 - Search Efficiencies

At the end of this lesson, you will be able to:

  • Classify Linear Search and Binary Search using Big-O notation.
  • Compare the worst-case performance of both search algorithms as list size grows.

How Fast Is Linear Search?

Let's take our shiny new Big-O tool and point it at the search algorithms we learned earlier in this unit.

Imagine you've got an unsorted pile of tests and you're looking for one particular student's paper. In the best case, it's sitting right on top—one comparison and you're done. In the worst case, it's at the very bottom of the pile (or it's not there at all), and you have to look at every single paper to find out. On average, you'll get lucky sometimes and unlucky other times, so you'll end up checking about half the papers.

Here's that broken down:

Scenario Work for n items Big-O
Best Case f(n) = 1 O(1)
Average Case f(n) = n/2 O(n)
Worst Case f(n) = n O(n)

Notice that in Big-O terms, the average case (n/2) and the worst case (n) are both O(n). Remember, Big-O doesn't care about constants—it only cares about the shape of the growth. Half of n still grows at the same rate as n; it's just shifted down a bit.

And yeah, the best case is O(1)—constant time—but you can't count on getting lucky every time. Basing your rating of an algorithm on a rare best-case scenario would be misleading. So we say:

Linear Search is O(n)—linear. Kind of makes sense that "linear search" is a "linear" algorithm, right?

There's a useful pattern here that shows up a lot in algorithm analysis: the best case usually isn't very informative (it's too rare to rely on), and the average case and worst case often end up in the same Big-O class.

How Fast Is Binary Search?

Binary Search works very differently. Remember, it relies on the list being sorted, and it repeatedly jumps to the middle of the remaining items—throwing away half the list with each comparison.

In the best case, the item you want happens to be right in the middle on the first check. One comparison, done. But as usual, we care about the worst case.

Let's trace through Binary Search on a list of 1,000 items. Each comparison cuts the remaining items roughly in half:

Items Left to Search Comparisons So Far
1,000 0
500 1
250 2
125 3
62 4
31 5
15 6
7 7
3 8
1 9
0 10

Ten comparisons. For a list of one thousand items. That's absurdly efficient.

The math behind this is the logarithm. Specifically, log base 2. The question "how many times do I have to divide n by 2 to get down to 1?" is exactly what log₂(n) answers. For 1,000 items, log₂(1000) is about 9.96, which we round up to 10. That matches our table perfectly.

So: Binary Search is O(log n)—logarithmic.

The Showdown: Linear vs. Binary

Let's put these two side by side and watch what happens as the list size grows. This is where it gets really fun.

List Size Linear Search (worst case) Binary Search (worst case)
10,000 10,000 14
100,000 100,000 17
1,000,000 1,000,000 20
1,000,000,000 1,000,000,000 30

Read that last row one more time. One billion items. Linear Search might need to check all one billion of them. Binary Search? Thirty comparisons. Thirty. That's the power of logarithmic growth—it barely notices when you make the input a thousand times bigger.

Something to think about:

Binary Search is dramatically faster than Linear Search—but it has a requirement that Linear Search doesn't. What is it? And does that requirement have its own cost? (Hint: think about what we just spent several lessons analyzing.)

Key Takeaways

  • Linear Search is O(n)—work grows in direct proportion to the list size.
  • Binary Search is O(log n)—work grows incredibly slowly, even for enormous lists.
  • The difference is staggering at scale: 1 billion comparisons vs. 30.
  • Big-O classification helps us see these differences clearly—without getting bogged down in exact operation counts.
