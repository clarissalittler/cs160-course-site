Unit 7 Summary

Wrap Up

This unit was all about algorithms—what they are, how we use them to search and sort data, and (crucially) how we figure out which ones are actually good. Here's a recap of everything we covered.

Algorithms

An algorithm is a step-by-step set of instructions for solving a problem. That's it—nothing fancier than that. A recipe is an algorithm. Driving directions are an algorithm. The interesting part is that algorithms are the heart of computer science: every program you've ever used is, at bottom, a collection of algorithms working together.

A good algorithm is unambiguous (every step is clear), finite (it eventually stops), and correct (it actually solves the problem). Sounds obvious, but getting all three right is harder than you'd think.

Searching: Linear vs. Binary

Linear Search is the simplest approach—start at the beginning and check each item, one by one, until you find what you're looking for or run out of items. It works on any list, sorted or not, but it can be slow for big lists.

Binary Search is much faster, but it has a catch: the list has to be sorted first. It works by jumping to the middle, checking whether the target is higher or lower, and throwing away half the remaining items with each comparison. For a billion items, Binary Search needs at most about 30 comparisons. Linear Search might need all billion.

Sorting: Selection Sort & Insertion Sort

Selection Sort repeatedly finds the smallest unsorted item and swaps it into its correct position. Simple to understand, consistent in its behavior—it always does the same number of comparisons regardless of the input order.

Insertion Sort takes each item and slides it into the right spot within the already-sorted portion of the list. It can be very fast on nearly-sorted data (barely any work to do), but in the worst case it does just as much work as Selection Sort.

Both algorithms sort items "in place"—they don't need a second copy of the list—so they're equally space-efficient.

Algorithm Analysis: Counting Operations

We can't just time algorithms with a stopwatch, because the results depend on your hardware. Instead, we count operations—comparisons, copies, swaps—to get a measurement that's independent of any particular computer.

Since different inputs can produce different operation counts, we focus on the worst case: the input arrangement that forces the algorithm to do the most work. This gives us a reliable upper bound—a guarantee that the algorithm will never be slower than this.

Big-O: Classifying Growth Rates

Big-O notation is a way of describing how an algorithm's work grows as the input gets bigger. We don't care about exact counts—we care about the shape of the growth curve.

  • O(1)—Constant: Work doesn't grow at all. Rare and wonderful.
  • O(log n)—Logarithmic: Work grows very slowly. Binary Search lives here.
  • O(n)—Linear: Work grows in proportion to the input. Linear Search lives here.
  • O(n²)—Quadratic: Work grows as the square of the input. Selection Sort and Insertion Sort live here. Gets painful fast.

The takeaway: not all algorithms are created equal, and the difference between a good algorithm and a bad one can mean the difference between "done instantly" and "still running next week."
