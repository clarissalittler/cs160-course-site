Lesson 4 - Tuples, Dictionaries, and Records

This lesson should leave you able to:

  • Create, index, and unpack tuples and explain their immutability.
  • Use tuples for fixed groups, multiple-value returns, loop unpacking, and compound dictionary keys.
  • Create, read, add, and update dictionary entries.
  • Use a dictionary as one record and a list of dictionaries as a table of records.
  • Choose between a tuple and dictionary based on the meaning and expected evolution of the data.

Tuples keep a fixed group together

A tuple is an ordered collection, usually written with parentheses. It's the right fit when a small number of values form one fixed unit:

point = (3, 5)
color = (40, 120, 200)
book_pair = ("Parable of the Sower", "Octavia Butler")

print(point[0])
print(point[1])
print(len(point))

Like strings and lists, tuples are indexed from 0 and support slicing, looping, membership, and len(). But unlike a list, a tuple is immutable: once it's created, its elements can't be replaced, appended, or removed.

point = (3, 5)
point[0] = 9  # TypeError: a tuple does not support item assignment

Immutability is a way of communicating intent: these values belong together as one fixed description. It doesn't make the information permanently safe or correct, mind you—the variable point can still be assigned a different tuple later.

Parentheses and the one-element tuple

Parentheses often just group an expression, so it's really the comma that creates a tuple:

not_a_tuple = (5)
one_item_tuple = (5,)

print(type(not_a_tuple))
print(type(one_item_tuple))

(5) is just the integer 5 wearing grouping parentheses. (5,) is a one-element tuple. Yes, the punctuation looks strange—precisely because tuples are normally useful when they contain several related values, so the one-element case doesn't get elegant syntax.

Packing and unpacking

Creating a tuple packages—or packs—several values together. Unpacking goes the other direction, assigning the elements to separate names in one statement:

point = (3, 5)
x, y = point

print(f"x is {x}")
print(f"y is {y}")

The number of names has to match the number of elements. x, y, z = point raises a ValueError, because a two-element tuple can't fill three names.

Unpacking also gives you a delightfully concise swap:

left = "tea"
right = "coffee"
left, right = right, left
print(left, right)

Python first packs the right-side values, then unpacks them into the left-side names.

Functions can return a tuple

A function returns one value—but that one value may be a tuple containing several parts:

def quotient_and_remainder(total, group_size):
    quotient = total // group_size
    remainder = total % group_size
    return quotient, remainder

full_boxes, items_left = quotient_and_remainder(53, 12)
print(f"Full boxes: {full_boxes}")
print(f"Items left: {items_left}")

return quotient, remainder constructs a two-element tuple, and the caller immediately unpacks it into descriptive names. You'll see this pattern whenever two results naturally belong to one calculation.

Loop unpacking makes fixed records readable

events = [
    ("Repair Cafe", "Saturday", 0.0),
    ("Bike Workshop", "Tuesday", 10.0),
    ("Seed Swap", "Sunday", 0.0),
]

for name, day, cost in events:
    print(f"{name} | {day} | ${cost:.2f}")

Each list element is a tuple, and every time through the loop it gets unpacked into name, day, and cost. Compare that with writing event[0], event[1], and event[2] everywhere—this version is much kinder to the reader.

Many Python tools produce values that are meant to be unpacked: enumerate() gives you an index and an element, zip() pairs up elements from collections, dictionary .items() produces key-value pairs, and database query rows are commonly tuple-like.

titles = ["Kindred", "Parable of the Sower", "Dawn"]

for number, title in enumerate(titles, start=1):
    print(f"{number}. {title}")

Tuples can be dictionary keys

Dictionary keys have to be immutable and hashable. A tuple whose elements are also hashable can serve as a compound key:

temperatures = {
    (2026, 7, 8): 72,
    (2026, 7, 9): 76,
    (2026, 7, 10): 74,
}

print(temperatures[(2026, 7, 9)])

The key is a fixed (year, month, day) triple. A list can't serve as a dictionary key because it could change after insertion.

Dictionaries look up fields by meaning

A tuple asks you to remember what each position means. A dictionary instead attaches a meaningful key to every value:

resource = {
    "name": "Northside Tool Library",
    "neighborhood": "Arbor Lodge",
    "cost": 0.0,
    "wheelchair_entry": True,
}

print(resource["name"])
print(resource["cost"])

The keys are strings; the values are whatever types they need to be. resource["cost"] explains a lot more than resource[2] would, and the gap only widens as a record grows.

Add, update, and handle missing fields

resource["phone"] = "555-0142"
resource["cost"] = 5.0

print("email" in resource)
print(resource.get("email", "not provided"))

for key, value in resource.items():
    print(f"{key}: {value}")

Assignment adds a new key or replaces an existing value. Looking up a missing key directly raises a KeyError, while .get(key, fallback) hands back the fallback instead. .items() supplies key-value pairs, which the loop unpacks into two variables—the same tuple unpacking from earlier in the lesson.

One dictionary record; a list of records

resources = [
    {"name": "Tool Library", "area": "North", "cost": 0.0},
    {"name": "Repair Cafe", "area": "Central", "cost": 0.0},
    {"name": "Bike Workshop", "area": "North", "cost": 10.0},
]

for resource in resources:
    print(f"{resource['name']} — ${resource['cost']:.2f}")

The outer list answers “which record?” and the inner dictionary answers “which field?” This nested shape turns up all over the place: configuration files, APIs, data loaded from CSV or JSON.

Choose the representation that explains the data

RepresentationGood fitTradeoff
Tuplesmall fixed group whose position is conventional: coordinates, RGB color, database row, paired return valuesreaders must know what each position means
Dictionaryrecord with named fields, optional fields, or a schema likely to evolvemore syntax and mutable state
Listordered collection expected to grow, shrink, or changeposition alone does not name record fields

A tuple is not an inferior dictionary, and a dictionary is not a superior tuple—they answer different questions. A point expressed as (x, y) is compact and conventional. A community-resource record benefits from named fields because its meaning and schema matter to many readers.

A schema is still an agreement

Whether a record is positional or named, write down what it means. For a dictionary, a small data dictionary records each key, its type or unit, its definition, whether it's required, and its missing-value rule. For a tuple, state the order explicitly: (name: str, day: str, cost_usd: float). The model should expose its assumptions rather than asking future readers—quite possibly future you—to reverse-engineer them.
