Lesson 4 - Tuples, Dictionaries, and Records

This lesson should leave you able to:

  • Create, index, and unpack tuples and explain their immutability.
  • Use tuples for fixed groups, multiple-value returns, loop unpacking, and compound dictionary keys.
  • Create, read, add, and update dictionary entries.
  • Use a dictionary as one record and a list of dictionaries as a table of records.
  • Choose between a tuple and dictionary based on the meaning and expected evolution of the data.

Every list we built in the last two lessons had something in common: all the elements were the same kind of thing. A list of neighborhood names, a list of temperatures, a list of donation amounts. That's what lists are best at, many of the same sort of item, where you might have three today and three hundred tomorrow.

But a lot of information doesn't look like that. A book has a title and an author. An event has a name, a day, and a cost. Those aren't three of the same thing, they're three different facts that describe one thing, and they belong together. This lesson is about two ways Python lets you keep facts like that together: tuples, which go by position, and dictionaries, which go by name.

Tuples keep a fixed group together

A tuple is an ordered collection, usually written with parentheses. It's the right fit when a few values form one fixed unit: a point has an x and a y, a color has a red, a green, and a blue. (The name comes from math, by way of the ends of words like double, triple, quadruple, and quintuple. Mathematicians got tired of making up new words and started saying "an n-tuple" for a group of n things. You'll hear both "TOO-pull" and "TUH-pull," and nobody agrees which is right.)

point = (3, 5)
color = (40, 120, 200)
book_pair = ("Parable of the Sower", "Octavia Butler")

print(point[0])
print(point[1])
print(len(point))

Like strings and lists, tuples index from 0 and support slicing, looping, membership, and len(). Unlike a list, a tuple is immutable: once it's made, its elements can't be replaced, added to, or removed.

point = (3, 5)
point[0] = 9  # TypeError: a tuple does not support item assignment

So why have a collection you can't change, when lists already exist? It's a fair question. Because sometimes "can't change" is exactly what you want to say. A tuple tells the reader that these values belong together as one fixed description, and that no code anywhere is going to swap out the y coordinate behind your back. Remember the aliasing surprise from Lesson 2, where changing a list through one name changed it through the other? That can't happen with a tuple, for the same reason it can't happen with a string. (The variable point can still be assigned a whole different tuple later. Immutability is a property of the tuple, not of the name.)

Parentheses and the one-element tuple

Parentheses often just group an expression, as in (2 + 3) * 4, so it's really the comma that makes a tuple:

not_a_tuple = (5)
one_item_tuple = (5,)

print(type(not_a_tuple))
print(type(one_item_tuple))

(5) is just the integer 5 in parentheses. (5,) is a one-element tuple. Yes, it looks strange. Python had already promised that parentheses around an expression just group it, so (5) had to keep meaning 5, and something else had to mark the tuple. Tuples are mostly useful when they hold several values, so the one-element case ended up with awkward syntax, and nobody loves it.

Packing and unpacking

Making a tuple packs several values together. Unpacking goes the other way: it assigns each element to its own name, in one statement:

point = (3, 5)
x, y = point

print(f"x is {x}")
print(f"y is {y}")

Python lines up the names on the left with the elements on the right, in order: the first name gets the first element, the second name gets the second. The number of names has to match the number of elements. x, y, z = point raises a ValueError, because two values can't fill three names.

Unpacking also gives you a swap in one line. Here's the problem it solves. Say you want to exchange the values of two variables. The obvious attempt, left = right followed by right = left, doesn't work: after the first line both variables hold "coffee", and the tea is gone for good. The traditional fix is to park one value in a temporary variable first, temp = left, then left = right, then right = temp. In Python you can skip all that:

left = "tea"
right = "coffee"
left, right = right, left
print(left, right)

Python packs the right side into a tuple first, then unpacks it into the names on the left. Since the tuple ("coffee", "tea") gets built before either variable changes, nothing is lost. In most languages you'd need the temporary variable, and Python programmers are rather proud of not needing one.

Functions can return a tuple

Back in Unit 4 we said that a function returns exactly one value, and that's still true. But that one value can be a tuple with several parts inside it, which is how Python gets away with "returning two things":

def quotient_and_remainder(total, group_size):
    quotient = total // group_size
    remainder = total % group_size
    return quotient, remainder

full_boxes, items_left = quotient_and_remainder(53, 12)
print(f"Full boxes: {full_boxes}")
print(f"Items left: {items_left}")

53 items in boxes of 12 fills 4 boxes with 5 left over. return quotient, remainder builds the two-element tuple (4, 5) (no parentheses needed), and the caller unpacks it right away into descriptive names. You'll see this whenever two results naturally come out of one calculation. You could write two separate functions, one for the quotient and one for the remainder, but they'd be doing the same division twice, and the person calling them would have to remember to call both.

Loop unpacking makes fixed records readable

Here's where tuples and lists start working together. A list is good at holding many things; a tuple is good at holding one thing's facts. So a list of tuples is a list of small records:

events = [
    ("Repair Cafe", "Saturday", 0.0),
    ("Bike Workshop", "Tuesday", 10.0),
    ("Seed Swap", "Sunday", 0.0),
]

for name, day, cost in events:
    print(f"{name} | {day} | ${cost:.2f}")

Each element of the list is a tuple, and each time through the loop it gets unpacked into name, day, and cost. Compare that with writing event[0], event[1], and event[2] everywhere. This version is much easier on the reader, because the names tell you what each piece means right there in the loop, and you don't have to keep flipping back to remember which position was the day.

Lots of Python tools produce values that are meant to be unpacked: enumerate() gives you an index and an element, zip() pairs up elements from two collections, dictionary .items() gives key-value pairs, and rows from a database usually come back tuple-shaped. Here's enumerate(), which is a nicer way to get the numbered display we built with range(len(...)) in Lesson 2:

titles = ["Kindred", "Parable of the Sower", "Dawn"]

for number, title in enumerate(titles, start=1):
    print(f"{number}. {title}")

Each time through, enumerate() hands the loop a pair like (1, "Kindred"), and the loop unpacks it. The start=1 is there because people count from 1 even though Python counts from 0.

Dictionaries look up fields by name

Tuples work great when the positions are a well-known convention. Everybody knows a point is (x, y) and not (y, x). But what about a record with a name, a neighborhood, a cost, and whether it has a wheelchair-accessible entrance? Is the cost at position 2 or 3? You'd have to go look it up every time, and so would everyone else who reads your code. A tuple makes you remember what each position means. A dictionary attaches a name to every value instead:

resource = {
    "name": "Northside Tool Library",
    "neighborhood": "Arbor Lodge",
    "cost": 0.0,
    "wheelchair_entry": True,
}

print(resource["name"])
print(resource["cost"])

A dictionary is written with curly braces, and each entry is a key, a colon, and a value. The keys here are strings; the values are whatever type they need to be. You look things up with square brackets, just like indexing, except you put a key in the brackets instead of a position. resource["cost"] says a lot more than resource[2] would, and the gap only widens as a record grows.

The name "dictionary" is pretty literal. In a paper dictionary, you look up a word and get its definition. In a Python dictionary, you look up a key and get its value. Other languages call the same idea a map, a hash map, or an associative array, so if you run into those words later, it's this.

Add, update, and handle missing fields

resource["phone"] = "555-0142"
resource["cost"] = 5.0

print("email" in resource)
print(resource.get("email", "not provided"))

for key, value in resource.items():
    print(f"{key}: {value}")

Assigning to a key adds it if it's new and replaces the value if it isn't. So the first line adds a phone number the record didn't have before, and the second changes the cost from 0.0 to 5.0. Like lists, dictionaries are mutable.

Looking up a key that isn't there raises a KeyError, the dictionary version of the IndexError from Lesson 1. You have two ways to avoid it. "email" in resource asks whether the key exists, the same "ask first" idea as membership on a list. Or .get(key, fallback) hands you the fallback instead of crashing, which is handy when a missing field has a sensible default. And .items() produces key-value pairs, which the loop unpacks into two variables, the same tuple unpacking from earlier in this lesson.

Tuples can be dictionary keys

Now that we've seen dictionaries, we can put tuples and dictionaries together. Dictionary keys have to be immutable. (The technical term is hashable, and I'm going to let "immutable" stand in for it for now.) A tuple of immutable things can serve as a compound key:

temperatures = {
    (2026, 7, 8): 72,
    (2026, 7, 9): 76,
    (2026, 7, 10): 74,
}

print(temperatures[(2026, 7, 9)])

The key is a fixed (year, month, day) triple. A list can't be a key, because a list could change after it went in, and then the dictionary would have no way to find the entry again.

Here's roughly why. A dictionary is fast because it doesn't search through every entry to find your key. Instead, it uses the key's value to work out where the entry should be stored, a bit like a coat check where the number on your ticket tells the attendant exactly which hook to go to. Now imagine the number on your ticket could change after you checked your coat. The attendant would go to the hook for the new number, find nothing there, and your coat would be lost on some other hook. Immutable keys guarantee the ticket number never changes. That's also why strings make such good keys: they're immutable, just like we talked about in Lesson 1.

One dictionary record; a list of records

One dictionary describes one thing. Most programs have to keep track of lots of things, so we do what we did with tuples: put the records in a list.

resources = [
    {"name": "Tool Library", "area": "North", "cost": 0.0},
    {"name": "Repair Cafe", "area": "Central", "cost": 0.0},
    {"name": "Bike Workshop", "area": "North", "cost": 10.0},
]

for resource in resources:
    print(f"{resource['name']} — ${resource['cost']:.2f}")

The outer list answers "which record?" and the inner dictionary answers "which field?" If you picture a spreadsheet, each dictionary is a row and the keys are the column headers. And every pattern from Lesson 3 still works: the loop above is a traversal, and a filter for everything in the North area is just a traversal with an if resource["area"] == "North" inside it.

This shape is everywhere: configuration files, web APIs, data loaded from spreadsheets or JSON. When you see a list of dictionaries, you're looking at a table. It's also exactly what you'll build for the Week 5 assignment. Hold onto that; we'll lean on it hard in Unit 8!

Choose the representation that explains the data

RepresentationGood fitTradeoff
Tuplesmall fixed group whose position is conventional: coordinates, RGB color, database row, paired return valuesreaders must know what each position means
Dictionaryrecord with named fields, optional fields, or a schema likely to evolvemore syntax and mutable state
Listordered collection expected to grow, shrink, or changeposition alone does not name record fields

A tuple isn't a worse dictionary and a dictionary isn't a better tuple. They answer different questions. A point as (x, y) is compact and everybody knows the convention. A community-resource record wants named fields, because its meaning matters to a lot of readers and the fields are likely to change over time. If next month someone decides the directory should also record whether each place has a bike rack, adding a "bike_rack" key to a dictionary is easy. Adding a fifth position to a tuple means finding and fixing every line of code that unpacks four.

A schema is still an agreement

Whatever representation you pick, write down what it means. That description is called a schema. For a dictionary, a small data dictionary lists each key, its type or unit, what it means, whether it's required, and what a missing value looks like. (Yes, "data dictionary" and "Python dictionary" are two different uses of the same word. Sorry. The term is older than Python.) Here's what one might look like for the resource record from earlier:

KeyType / unitMeaningRequired?If missing
namestrpublic name of the resourceyesrecord is not added
neighborhoodstrPortland neighborhood where it's locatedyesrecord is not added
costfloat, US dollarstypical cost of one visit; 0.0 means freenoNone, meaning nobody has checked yet
wheelchair_entryboolhas at least one step-free entrancenoNone, meaning unknown

Look at the cost row: it says that 0.0 means "free" and None means "we don't know." Without that written down, the next person to touch the code might use 0.0 for both, and suddenly the directory is telling people a place is free when nobody ever checked. (Lesson 5 is going to dig into that difference.) For a tuple, state the order: (name: str, day: str, cost_usd: float). The model should show its assumptions, rather than leaving a future reader (very possibly you) to reverse-engineer them from the code.
