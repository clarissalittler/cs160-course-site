Lesson 4 - Tuples, Dictionaries, and Records

This lesson should leave you able to:

  • Create, index, and unpack tuples and explain their immutability.
  • Use tuples for fixed groups, multiple-value returns, loop unpacking, and compound dictionary keys.
  • Create, read, add, and update dictionary entries.
  • Use a dictionary as one record and a list of dictionaries as a table of records.
  • Choose between a tuple and dictionary based on the meaning and expected evolution of the data.

Tuples keep a fixed group together

A tuple is an ordered collection, usually written with parentheses. It's the right fit when a few values form one fixed unit: a point has an x and a y, a color has a red, a green, and a blue.

point = (3, 5)
color = (40, 120, 200)
book_pair = ("Parable of the Sower", "Octavia Butler")

print(point[0])
print(point[1])
print(len(point))

Like strings and lists, tuples index from 0 and support slicing, looping, membership, and len(). Unlike a list, a tuple is immutable: once it's made, its elements can't be replaced, added to, or removed.

point = (3, 5)
point[0] = 9  # TypeError: a tuple does not support item assignment

So why have a collection you can't change, when lists already exist? It's a fair question. Because sometimes "can't change" is exactly what you want to say. A tuple tells the reader that these values belong together as one fixed description, and that no code anywhere is going to swap out the y coordinate behind your back. (The variable point can still be assigned a whole different tuple later. Immutability is a property of the tuple, not of the name.)

Parentheses and the one-element tuple

Parentheses often just group an expression, as in (2 + 3) * 4, so it's really the comma that makes a tuple:

not_a_tuple = (5)
one_item_tuple = (5,)

print(type(not_a_tuple))
print(type(one_item_tuple))

(5) is just the integer 5 in parentheses. (5,) is a one-element tuple. Yes, it looks strange. Tuples are mostly useful when they hold several values, so the one-element case ended up with awkward syntax, and nobody loves it.

Packing and unpacking

Making a tuple packs several values together. Unpacking goes the other way: it assigns each element to its own name, in one statement:

point = (3, 5)
x, y = point

print(f"x is {x}")
print(f"y is {y}")

The number of names has to match the number of elements. x, y, z = point raises a ValueError, because two values can't fill three names.

Unpacking also gives you a swap in one line:

left = "tea"
right = "coffee"
left, right = right, left
print(left, right)

Python packs the right side into a tuple first, then unpacks it into the names on the left. In most languages you'd need a temporary variable to do this, and Python programmers are rather proud of not needing one.

Functions can return a tuple

A function returns exactly one value. But that one value can be a tuple with several parts inside it, which is how Python gets away with "returning two things":

def quotient_and_remainder(total, group_size):
    quotient = total // group_size
    remainder = total % group_size
    return quotient, remainder

full_boxes, items_left = quotient_and_remainder(53, 12)
print(f"Full boxes: {full_boxes}")
print(f"Items left: {items_left}")

return quotient, remainder builds a two-element tuple (no parentheses needed), and the caller unpacks it right away into descriptive names. You'll see this whenever two results naturally come out of one calculation.

Loop unpacking makes fixed records readable

events = [
    ("Repair Cafe", "Saturday", 0.0),
    ("Bike Workshop", "Tuesday", 10.0),
    ("Seed Swap", "Sunday", 0.0),
]

for name, day, cost in events:
    print(f"{name} | {day} | ${cost:.2f}")

Each element of the list is a tuple, and each time through the loop it gets unpacked into name, day, and cost. Compare that with writing event[0], event[1], and event[2] everywhere. This version is much easier on the reader.

Lots of Python tools produce values that are meant to be unpacked: enumerate() gives you an index and an element, zip() pairs up elements from two collections, dictionary .items() gives key-value pairs, and rows from a database usually come back tuple-shaped.

titles = ["Kindred", "Parable of the Sower", "Dawn"]

for number, title in enumerate(titles, start=1):
    print(f"{number}. {title}")

Tuples can be dictionary keys

Dictionary keys have to be immutable. (The technical term is hashable, and I'm going to let "immutable" stand in for it for now.) A tuple of immutable things can serve as a compound key:

temperatures = {
    (2026, 7, 8): 72,
    (2026, 7, 9): 76,
    (2026, 7, 10): 74,
}

print(temperatures[(2026, 7, 9)])

The key is a fixed (year, month, day) triple. A list can't be a key, because a list could change after it went in, and then the dictionary would have no way to find the entry again.

Dictionaries look up fields by name

A tuple makes you remember what each position means. A dictionary attaches a name to every value instead:

resource = {
    "name": "Northside Tool Library",
    "neighborhood": "Arbor Lodge",
    "cost": 0.0,
    "wheelchair_entry": True,
}

print(resource["name"])
print(resource["cost"])

The keys here are strings; the values are whatever type they need to be. resource["cost"] says a lot more than resource[2] would, and the gap only widens as a record grows.

Add, update, and handle missing fields

resource["phone"] = "555-0142"
resource["cost"] = 5.0

print("email" in resource)
print(resource.get("email", "not provided"))

for key, value in resource.items():
    print(f"{key}: {value}")

Assigning to a key adds it if it's new and replaces the value if it isn't. Looking up a key that isn't there raises a KeyError; .get(key, fallback) hands you the fallback instead. And .items() produces key-value pairs, which the loop unpacks into two variables, the same tuple unpacking from earlier in this lesson.

One dictionary record; a list of records

resources = [
    {"name": "Tool Library", "area": "North", "cost": 0.0},
    {"name": "Repair Cafe", "area": "Central", "cost": 0.0},
    {"name": "Bike Workshop", "area": "North", "cost": 10.0},
]

for resource in resources:
    print(f"{resource['name']} — ${resource['cost']:.2f}")

The outer list answers "which record?" and the inner dictionary answers "which field?" This shape is everywhere: configuration files, web APIs, data loaded from spreadsheets or JSON. When you see a list of dictionaries, you're looking at a table. Hold onto that; we'll lean on it hard in Unit 8!

Choose the representation that explains the data

RepresentationGood fitTradeoff
Tuplesmall fixed group whose position is conventional: coordinates, RGB color, database row, paired return valuesreaders must know what each position means
Dictionaryrecord with named fields, optional fields, or a schema likely to evolvemore syntax and mutable state
Listordered collection expected to grow, shrink, or changeposition alone does not name record fields

A tuple isn't a worse dictionary and a dictionary isn't a better tuple. They answer different questions. A point as (x, y) is compact and everybody knows the convention. A community-resource record wants named fields, because its meaning matters to a lot of readers and the fields are likely to change over time.

A schema is still an agreement

Whatever representation you pick, write down what it means. For a dictionary, a small data dictionary lists each key, its type or unit, what it means, whether it's required, and what a missing value looks like. For a tuple, state the order: (name: str, day: str, cost_usd: float). The model should show its assumptions, rather than leaving a future reader (very possibly you) to reverse-engineer them from the code.
