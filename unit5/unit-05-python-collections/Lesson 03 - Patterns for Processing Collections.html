Lesson 3 - Patterns for Processing Collections

By the time you finish this lesson, you should be able to:

  • Recognize traversal, transformation, filtering, counting, accumulation, and min/max patterns.
  • Build a new list rather than accidentally destroying source data.
  • Separate collection processing from keyboard input and formatted display.
  • Test collection code with empty, one-item, typical, and boundary cases.

Most collection programs use a few recurring patterns

A playlist, a search page, a gradebook, a shopping cart, and a transit app look like completely different programs, but under the hood they keep doing the same handful of things:

  • Traverse: visit every item.
  • Transform: produce a changed value for every item.
  • Filter: keep only items that match a condition.
  • Aggregate: combine many items into one result, such as a count or total.
  • Find an extreme: locate the smallest or largest item by some measure.

Think about how cooking works. Nobody invents chopping, sautéing, or simmering from scratch every time they make dinner. A recipe says "dice an onion and sauté it," and if you already know those techniques, you can focus on the part of the recipe that's actually new. These patterns are the programming version of that. A gradebook's "what's the class average?" is an aggregate. A shopping cart's "show me only what's on sale" is a filter. A transit app's "when's the next bus?" is finding an extreme.

Once you can recognize which one you're doing, you can start from the logic and let the syntax follow. That's a big shift from staring at an empty editor wondering what to type, and it's the shift that makes programming start to feel comfortable. So in this lesson we're going to go through each pattern with a small example, and pay attention to what stays the same from one to the next.

Traversal: perform one job for every item

hours = [1.5, 2.0, 0.5, 3.0]

for value in hours:
    print(f"Recorded study time: {value:.1f} hours")

The loop doesn't change the list. It just visits each element and does something with it, here printing it with a label and a unit. This is the simplest of the patterns and every other one is built on top of it: they all visit every element, they just do something more interesting at each stop.

Transformation: build a corresponding collection

temperatures_f = [32, 50, 68, 77]
temperatures_c = []

for fahrenheit in temperatures_f:
    celsius = (fahrenheit - 32) * 5 / 9
    temperatures_c.append(celsius)

print(temperatures_c)

This should look familiar: it's the same shape as the MEET-AT-NOON example from Lesson 1, just with a list instead of a string. Start with an empty result, look at each element, add a transformed version to the result. Here, 32 becomes 0.0, 50 becomes 10.0, 68 becomes 20.0, and 77 becomes 25.0, each one appended in turn.

So there's one Celsius value for every Fahrenheit value, in the same order. Building a new list keeps the original around for comparison or reuse. Maybe you want to print both columns side by side, or maybe another part of the program still expects Fahrenheit. Replacing the elements in place is sometimes the right call, but it should be a decision, not something that happens by accident.

Filtering: build a collection of matches

all_locations = ["online", "library", "online", "student center"]
in_person_locations = []

for location in all_locations:
    if location != "online":
        in_person_locations.append(location)

print(in_person_locations)

A filter looks almost exactly like a transformation. The difference is the if: instead of appending something for every element, we only append the ones that pass a test. So the result can be shorter than the original, and it might be empty. Here we get ["library", "student center"].

A filter doesn't change what's in the source; it produces a selected view of it. In a real interface, we should say what filter is active and how many matches came back. And if there are no matches, say "No matching locations" instead of printing nothing and leaving the user to wonder whether the program is broken. You've probably had the experience of searching a website, getting a blank page, and not knowing whether there really were no results or the site just didn't load. That's what we're trying not to do to people.

Counting and accumulating

donations = [5.00, 12.50, 3.00, 20.00]
total = 0.0
large_donation_count = 0

for amount in donations:
    total += amount
    if amount >= 10:
        large_donation_count += 1

print(f"Total: ${total:.2f}")
print(f"Donations of at least $10: {large_donation_count}")

An accumulator is a variable that builds up a result as the loop goes. Let's watch total: it starts at 0.0, becomes 5.0, then 17.5, then 20.5, then 40.5. Meanwhile large_donation_count only goes up on the passes where the amount is at least 10, which happens twice. Notice that we did two patterns at once in a single loop. That's common! Real programs mix and match these.

An accumulator starts at an identity value (0 for addition) and updates once per relevant element. "Identity" just means the value that doesn't change anything: adding 0 to a number leaves it alone, so 0 is the right thing to start a sum with. If you were multiplying things together, you'd start at 1 instead, since starting at 0 would make the whole answer 0. And if you're building up a string, you start with the empty string, "", which is exactly what we did in Lesson 1. A counter is just an accumulator that adds 1 whenever a condition is true.

Python has sum() and len() built in, so why am I making you write the loop yourself? Once, so you can watch the state change happen. And after that, because the built-ins only cover the common summaries. "How many donations were at least $10" isn't one of them, and neither is most of what a real program needs to count.

Minimum and maximum without a made-up starting value

wait_times = [18, 7, 24, 11]

if len(wait_times) == 0:
    print("No wait times were recorded.")
else:
    shortest = wait_times[0]
    longest = wait_times[0]

    for minutes in wait_times:
        if minutes < shortest:
            shortest = minutes
        if minutes > longest:
            longest = minutes

    print(f"Range: {shortest} to {longest} minutes")

The idea here is "best so far." Before the loop, the best we've seen is the first element, so both shortest and longest start at 18. Then we look at each wait time and ask: is this one shorter than the shortest so far? Longer than the longest? At 7, shortest becomes 7. At 24, longest becomes 24. At 11, neither changes. By the end, "best so far" is just "best," and we print a range of 7 to 24 minutes.

Start from a real element, not from 0 or 999999. I don't trust made-up starting values: they work right up until the data changes, and then they fail in a way that's hard to spot, because a "shortest wait time" of 0 looks like a real answer. Start shortest at 0 and no real wait time will ever be less than it, so the program reports 0 no matter what the data says. Start it at 999999 and you're fine until someone's measuring something in milliseconds. The first element never has that problem, because it's actually in the data. The empty-list check is there because an empty list has no first element to start from.

Put processing in a function

def average(numbers):
    if len(numbers) == 0:
        return None

    total = 0
    for number in numbers:
        total += number
    return total / len(numbers)

result = average([4, 7, 10])
if result is None:
    print("No average is available.")
else:
    print(f"Average: {result:.1f}")

The function takes data and returns a result. It doesn't ask for keyboard input, and it doesn't decide what the whole report looks like. This makes it more reusable and testable. Because average doesn't care where the numbers came from, you can hand it any list you like and check the answer, without typing anything in by hand every time:

  • average([]) should return None.
  • average([8]) should return 8.
  • average([4, 7, 10]) should return 7.

Each of these tests checks something distinct. The empty list is the case most likely to crash. The one-element list is the smallest case that should work, and it's where off-by-one mistakes tend to show up. The three-element list is an ordinary case where you can check the answer in your head. Empty, one, and a typical few is a good habit for testing any collection code.

So why return None for the empty list instead of 0? None means "no result," which is a different thing from 0. After all, 0 might be a real average: a list of temperatures on a cold day, or a list of scores where everyone skipped the assignment. If the function returned 0 for "there was no data," the code that called it would have no way to tell those two situations apart. Returning None makes the caller deal with the difference, which is exactly what the if result is None check does.

Filters and summaries are choices about attention

A "top results" function decides what people get to see. An average squeezes a whole spread of values into one number. A maximum points at an extreme. These are views into data but aren't the whole picture, a thread we'll pick up in our data science module! For example, an average wait time of 15 minutes sounds fine, but it could be hiding one person who waited two hours. A search that only shows the top ten results decides, for most people, that result number eleven doesn't exist.

So when you show a summary, label the measure, the unit, the number of records, and any active filter. And ask whether the missing values or excluded records all lean in one direction. If all the records with no wait time recorded came from one clinic, the average isn't really describing that clinic at all.
