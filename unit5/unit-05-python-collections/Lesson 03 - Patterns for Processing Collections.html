Lesson 3 - Patterns for Processing Collections

By the time you finish this lesson, you should be able to:

  • Recognize traversal, transformation, filtering, counting, accumulation, and min/max patterns.
  • Build a new list rather than accidentally destroying source data.
  • Separate collection processing from keyboard input and formatted display.
  • Test collection code with empty, one-item, typical, and boundary cases.

Most collection programs use a few recurring moves

A playlist, a search page, a gradebook, a shopping cart, and a transit app look like completely different programs, but under the hood they keep doing the same handful of things:

  • Traverse: visit every item.
  • Transform: produce a changed value for every item.
  • Filter: keep only items that match a condition.
  • Aggregate: combine many items into one result, such as a count or total.
  • Find an extreme: locate the smallest or largest item by some measure.

Once you can recognize which one you're doing, you can start from the logic and let the syntax follow. That's a big shift from staring at an empty editor wondering what to type, and it's the shift that makes programming start to feel comfortable.

Traversal: perform one job for every item

hours = [1.5, 2.0, 0.5, 3.0]

for value in hours:
    print(f"Recorded study time: {value:.1f} hours")

The loop doesn't change the list. It just visits each element and does something with it.

Transformation: build a corresponding collection

temperatures_f = [32, 50, 68, 77]
temperatures_c = []

for fahrenheit in temperatures_f:
    celsius = (fahrenheit - 32) * 5 / 9
    temperatures_c.append(celsius)

print(temperatures_c)

There's one Celsius value for every Fahrenheit value, in the same order. Building a new list keeps the original around for comparison or reuse. Replacing the elements in place is sometimes the right call, but it should be a decision, not something that happens by accident.

Filtering: build a collection of matches

all_locations = ["online", "library", "online", "student center"]
in_person_locations = []

for location in all_locations:
    if location != "online":
        in_person_locations.append(location)

print(in_person_locations)

A filter doesn't change what's in the source; it produces a selected view of it. In a real interface, we should say what filter is active and how many matches came back. And if there are no matches, say "No matching locations" instead of printing nothing and leaving the user to wonder whether the program is broken.

Counting and accumulating

donations = [5.00, 12.50, 3.00, 20.00]
total = 0.0
large_donation_count = 0

for amount in donations:
    total += amount
    if amount >= 10:
        large_donation_count += 1

print(f"Total: ${total:.2f}")
print(f"Donations of at least $10: {large_donation_count}")

An accumulator starts at an identity value (0 for addition) and updates once per relevant element. A counter is just an accumulator that adds 1 whenever a condition is true. Python has sum() and len() built in, so why am I making you write the loop yourself? Once, so you can watch the state change happen. And after that, because the built-ins only cover the common summaries. "How many donations were at least $10" isn't one of them, and neither is most of what a real program needs to count.

Minimum and maximum without a made-up starting value

wait_times = [18, 7, 24, 11]

if len(wait_times) == 0:
    print("No wait times were recorded.")
else:
    shortest = wait_times[0]
    longest = wait_times[0]

    for minutes in wait_times:
        if minutes < shortest:
            shortest = minutes
        if minutes > longest:
            longest = minutes

    print(f"Range: {shortest} to {longest} minutes")

Start from a real element, not from 0 or 999999. I don't trust made-up starting values: they work right up until the data changes, and then they fail in a way that's hard to spot, because a "shortest wait time" of 0 looks like a real answer. The empty-list check is there because an empty list has no first element to start from.

Put processing in a function

def average(numbers):
    if len(numbers) == 0:
        return None

    total = 0
    for number in numbers:
        total += number
    return total / len(numbers)

result = average([4, 7, 10])
if result is None:
    print("No average is available.")
else:
    print(f"Average: {result:.1f}")

The function takes data and returns a result. It doesn't ask for keyboard input, and it doesn't decide what the whole report looks like. That's the same separation from Unit 4, and it's what makes testing easy:

  • average([]) should return None.
  • average([8]) should return 8.
  • average([4, 7, 10]) should return 7.

None means "no result," which is a different thing from 0. After all, 0 might be a real average.

Filters and summaries are choices about attention

A "top results" function decides what people get to see. An average squeezes a whole spread of values into one number. A maximum points at an extreme. None of these is dishonest, but each one leaves something out, and what's left out can change the story. So when you show a summary, label the measure, the unit, the number of records, and any active filter. And ask whether the missing values or excluded records all lean in one direction.
