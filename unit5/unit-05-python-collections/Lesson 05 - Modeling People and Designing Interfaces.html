Lesson 5 - Modeling People and Designing Interfaces

When you finish this lesson, you should be able to:

  • Distinguish required, optional, unknown, and not-applicable data.
  • Critique a schema for unnecessary collection and categories that exclude reasonable cases.
  • Design a text interface with clear labels, state, errors, navigation, and exits.
  • Run a small usability test and turn an observation into a revision.

Correct storage does not guarantee a usable tool

A program can store every record correctly and still fail the people using it. A menu might not say what the options are. An error might wipe out someone's work. A screen reader might read out a column of unlabeled numbers. A form might demand information that's unknown, irrelevant, or far too sensitive for what the tool actually does.

Human–computer interaction, or HCI, is the field that studies how people and computing systems deal with each other. I think it's tempting to treat it as polish you add once the programming is done, but it isn't. The names, prompts, categories, feedback, and navigation are part of what the system does, every bit as much as the loops underneath.

Required, optional, unknown, and not applicable are different

Consider a record for a community event:

event = {
    "name": "Neighborhood Repair Cafe",
    "location": "Library meeting room",
    "cost": 0.0,
    "end_time": None,
    "registration_url": None,
}

None says that no value is present. It doesn't say why, and the why matters:

  • Required: the tool cannot perform its stated job without the value.
  • Optional: useful when supplied, but the record remains valid without it.
  • Unknown: a value exists in the world but has not been learned or verified.
  • Not applicable: the field does not make sense for this record.

Using an empty string or 0 for all four of these throws away information. A $0 event and an event whose cost nobody has found out yet are different things, and if you store them the same way, no later code can ever tell them apart.

Do not collect a field merely because you can

Data minimization means collecting only what you need for a stated purpose. A catalog of favorite albums doesn't need legal names, birth dates, or precise locations. A resource directory might need a neighborhood; it doesn't need a home address. And every field you collect is work: it has to be explained, protected, corrected, and eventually deleted. The cheapest field to keep safe is the one you never asked for.

Ask before adding a field:

  • What user goal requires it?
  • Could a less sensitive value serve the same goal?
  • Who can see it?
  • How can someone correct it?
  • When should it be removed?

Fixed categories leave remainders

A menu makes data tidy by limiting the choices, but people and situations don't always fit the choices. "Choose exactly one language." "Everyone has a first and last name." "Every address has a US ZIP code." Each of these simplifies the code by making the system less true.

There are several honest ways out: allow multiple selections, offer an explicit self-description option, add a free-text note, or don't collect the field at all. "Other" can help, but it can also end up labeling a lot of people as exceptions to whatever the system assumed was normal. There's no universal schema, and I'd be suspicious of anyone who claimed to have one. The design has to follow the real purpose and the real people it touches.

Make a text interface predictable

def show_menu(record_count):
    print()
    print("COMMUNITY RESOURCE CATALOG")
    print(f"Current records: {record_count}")
    print("1. Add a resource")
    print("2. Display all resources")
    print("3. Search by area")
    print("4. Show summary")
    print("5. Quit")

def show_resource(resource):
    print(f"Name: {resource['name']}")
    print(f"Area: {resource['area']}")
    print(f"Cost: ${resource['cost']:.2f}")
    print(f"Notes: {resource.get('notes', 'not provided')}")

This interface tells the user:

  • where the user is,
  • what state exists now,
  • which actions are available,
  • which number selects each action, and
  • how to leave.

The important structure is in words and labels, not in color, position, or a decorative box. Keyboard input is enough to run the menu, and the output comes in the same order for every record.

Errors should preserve dignity and progress

choice = input("Choose 1 through 5: ").strip()

while choice not in ["1", "2", "3", "4", "5"]:
    print(f"'{choice}' is not a menu option. Your records have not changed.")
    choice = input("Choose 1 through 5: ").strip()

Compare "Invalid user input" with a message that names the accepted choices and confirms that the data is safe. The second one actually helps someone recover. And skip the jokes that are only funny when it's somebody else who made the mistake.

Accessibility is a set of testable behaviors

For a small text tool, check whether:

  • every action works from the keyboard;
  • prompts and results have descriptive labels;
  • meaning does not depend only on color, emoji, spacing, or animation;
  • the reading order matches the program's logical order;
  • errors explain how to recover without discarding work;
  • the program does not impose a short time limit;
  • a user can review what was entered before a consequential action.

No checklist covers every access need. What a checklist gives you is concrete places to start, and reasons to test with people instead of assuming.

Usability testing means observing, not defending

Ask another person, or use a provided persona, to complete a task like "add a resource and find every free option." Don't explain the interface while they work, however strong the urge gets. (It gets strong. I promise.) Note where they pause, pick an option you didn't expect, misread a label, or wonder whether something was saved. Then change one design decision and test again.

One person doesn't stand in for all users, and a persona is no substitute for the people actually affected. The habit to build is treating confusion as evidence about the design, not as evidence that the user did something wrong.

Interface and schema review. Sketch or implement a text-first catalog with add, display, filter, summary, and quit actions. Then:

  1. Mark every field required or optional and identify any unknown/not-applicable case.
  2. Remove one field the program does not need.
  3. Add labeled output and an explicit empty-result message.
  4. Test every action without a mouse.
  5. Ask another person to complete one task.
  6. Record one observation and the revision it caused.
