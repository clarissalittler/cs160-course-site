Lesson 5 - Modeling People and Designing Interfaces

When you finish this lesson, you should be able to:

  • Distinguish required, optional, unknown, and not-applicable data.
  • Critique a schema for unnecessary collection and categories that exclude reasonable cases.
  • Design a text interface with clear labels, state, errors, navigation, and exits.
  • Run a small usability test and turn an observation into a revision.

Beyond storing the data

Have you ever filled out a form online that wouldn't take your name? Maybe it had a hyphen, or an apostrophe, or it was one word instead of two, or it was longer than whoever built the form expected. Or a form that wanted a phone number when you didn't have one, and wouldn't let you continue without it. The program behind that form was probably storing everything it accepted just fine, but it only accepted a limited number of cases.

That's the idea this lesson is built around. A program can store every record correctly and still fail the people using it. A menu might not say what the options are. An error might wipe out someone's work. A screen reader might read out a column of unlabeled numbers. A form might demand information that's unknown, irrelevant, or far too sensitive for what the tool actually does.

Human–computer interaction, or HCI, is the field that studies how people and computing systems deal with each other. I think it's tempting to treat it as polish you add once the programming is done, but it isn't. The names, prompts, categories, feedback, and navigation are part of what the system does, every bit as much as the loops underneath. In the last four lessons we built the data structures; in this one we look at them from the other side of the screen.

Required, optional, unknown, and not applicable

Consider a record for a community event:

event = {
    "name": "Neighborhood Repair Cafe",
    "location": "Library meeting room",
    "cost": 0.0,
    "end_time": None,
    "registration_url": None,
}

None says that no value is present. It doesn't say why, and the why matters:

  • Required: the tool cannot perform its stated job without the value.
  • Optional: useful when supplied, but the record remains valid without it.
  • Unknown: a value exists in the world but has not been learned or verified.
  • Not applicable: the field does not make sense for this record.

Let's apply those to the event. The name is required: an event listing with no name is useless. The registration URL might be not applicable, because this is a drop-in event where you just show up and there's nothing to register for. The end time might be unknown: the event does end at some point, the organizers just haven't said when. Both of those are stored as None in the record above, and nothing in the code can tell you that they mean different things. A person reading the listing, though, would want to know the difference between "no registration needed" and "we don't know how to register yet."

Using an empty string or 0 for all four of these throws away even more information. A $0 event and an event whose cost nobody has found out yet are different things, and if you store them the same way, no later code can ever tell them apart. This is the same problem as returning 0 instead of None from average() back in Lesson 3, just with people on the other end of it. Someone who can't afford a $20 event and shows up because the directory said "$0.00" is going to have a bad afternoon, and no amount of debugging would have caught it, because the code did exactly what it was told.

How do you keep the difference in a program? The simplest honest answer is to decide on a rule and write it in your data dictionary, like we did at the end of Lesson 4: "None in cost means unknown; 0.0 means free." For fields where not applicable and unknown really need to be told apart, you can store a short explanation string instead, like "drop-in, no registration".

Collecting less

When you design a record, it's tempting to throw in every field you can think of, just in case. Birthday? Might be useful someday. Home address? Why not. Data minimization is the opposite habit: collecting only what you need for a stated purpose. A catalog of favorite albums doesn't need legal names, birth dates, or precise locations. A resource directory might need a neighborhood; it doesn't need a home address.

Every field you collect is work: it has to be explained, protected, corrected, and eventually deleted. And every field you collect can leak. In Unit 10 we'll run into data breaches, where a company's stored records end up in the wrong hands. The damage from a breach depends almost entirely on what was stored. A leaked list of people's favorite albums is embarrassing; a leaked list of people's home addresses and birth dates is dangerous. And a field you never collected can't leak at all, no matter how badly the rest of the security goes.

Ask before adding a field:

  • What user goal requires it?
  • Could a less sensitive value serve the same goal?
  • Who can see it?
  • How can someone correct it?
  • When should it be removed?

When people don't fit the categories

A menu makes data tidy by limiting the choices, but people and situations don't always fit the choices. "Choose exactly one language." "Everyone has a first and last name." "Every address has a US ZIP code." Each of these makes the code simpler, since there's only one case to handle, but the price is that the system now believes something about people that isn't true for all of them. A bilingual person has to pick one. A person with one name, which is common in parts of Indonesia and elsewhere, has to invent a second. Someone with an address in another country can't finish the form at all.

This comes up so often with names in particular that a programmer named Patrick McKenzie wrote a well-known list in 2010 called "Falsehoods Programmers Believe About Names": that everyone has exactly one full name, that names don't change, that names fit in a certain number of characters, that names are written in one particular alphabet, &c. Every item on the list is an assumption somebody baked into a real system. (If you're thinking this sounds a lot like the Unicode lesson back in Unit 1, it is! Unicode fixed the problem of storing the world's names; it didn't fix the problem of programs that assume what a name should look like.)

So what do you do instead? There are several honest ways out: allow multiple selections, offer an explicit self-description option, add a free-text note, or don't collect the field at all. "Other" can help, but it can also end up labeling many people as exceptions to whatever the system assumed was normal. Which one fits depends on what the tool is for and who's going to use it. A language field for a library's book club and a language field for a hospital's interpreter requests probably shouldn't look the same, and I'd be suspicious of anyone who claimed to have one schema that works everywhere.

Predictable interfaces

Now let's switch from the data to the screen. For the Week 5 assignment you'll build a small menu-driven program, so here's what a reasonable menu and record display might look like:

def show_menu(record_count):
    print()
    print("COMMUNITY RESOURCE CATALOG")
    print(f"Current records: {record_count}")
    print("1. Add a resource")
    print("2. Display all resources")
    print("3. Search by area")
    print("4. Show summary")
    print("5. Quit")

def show_resource(resource):
    print(f"Name: {resource['name']}")
    print(f"Area: {resource['area']}")
    cost = resource.get("cost")
    if cost is None:
        print("Cost: unknown")
    elif cost == 0:
        print("Cost: free")
    else:
        print(f"Cost: ${cost:.2f}")
    print(f"Notes: {resource.get('notes', 'not provided')}")

The cost display follows the missing-value rule from our data dictionary: None or an absent cost means "unknown," while 0.0 means "free." We check for None before using numeric formatting, because None isn't a number. Try records with no cost key, with None, with 0.0, and with 5.0. The notes use the .get() fallback from Lesson 4, so a record with no notes shows "not provided". What makes this display useful is what it tells the user:

  • where the user is,
  • what state exists now,
  • which actions are available,
  • which number selects each action, and
  • how to leave.

Each of those answers a question a person would otherwise have to guess at. The title says which program this is. "Current records: 3" tells them whether their last add worked. The numbered list means they never have to wonder what to type, and "5. Quit" means they're never stuck. The blank line from the first print() separates each menu from whatever came before, so the screen doesn't turn into one long wall of text.

You might wonder why the display is so plain. There's no color, no decorative box, nothing that depends on where things sit on the screen; everything important is in the words and labels. Keyboard input is enough to run the menu, and the output comes in the same order for every record. Why does that matter? Think about someone using a screen reader, which reads the text out loud from top to bottom: "Name, Area, Cost, Notes" in the same order every time is easy to follow by ear, and a fancy ASCII-art table of lines and dashes is not.

Recovering from errors

People are going to type the wrong thing. They'll hit 6 on a five-item menu, or type "two" instead of "2," or lean on the keyboard by accident. Mistakes happen! But what does the program do next?:

choice = input("Choose 1 through 5: ").strip()

while choice not in ["1", "2", "3", "4", "5"]:
    print(f"'{choice}' is not a menu option. Your records have not changed.")
    choice = input("Choose 1 through 5: ").strip()

This is the validation loop from Unit 4, with a list membership test from Lesson 2 as the condition. Notice that the choices are strings, "1" and not 1, because input() always gives back a string. Comparing strings also means the program doesn't crash if someone types a letter, which it would if we tried to convert their input with int() first.

Compare "Invalid user input" with a message that repeats what they typed, names the accepted choices, and confirms that the data is safe. The latter option is clearly more helpful if more verbose for you to write.

On accessibility

"Make it accessible" can sound vague, like a feeling you're supposed to have about your program. It's much more useful to turn it into questions you can actually check. For a small text tool, check whether:

  • every action works from the keyboard;
  • prompts and results have descriptive labels;
  • meaning does not depend only on color, emoji, spacing, or animation;
  • the reading order matches the program's logical order;
  • errors explain how to recover without discarding work;
  • the program does not impose a short time limit;
  • a user can review what was entered before a consequential action.

Something you'll notice is that almost everything on that list helps everyone, not just disabled users. Clear labels help someone who's tired or distracted. Recoverable errors help someone who fat-fingered a key. There's a name for this, the curb cut effect. Disability activists in Berkeley in the early 1970s fought for small ramps cut into curbs so wheelchair users could cross the street, and it turned out those ramps are also great for anyone pushing a stroller, dragging a suitcase, or having a hard day on their knees.

That list won't cover every access need, of course. People's needs vary more than any checklist can predict. What it does give you is somewhere concrete to start, and the rest you find out by testing with real people, which is where we're going next.

Usability testing

Here's a problem you can't solve by thinking harder: you already know how your program works. You wrote the menu, so of course "3. Search by area" is obvious to you. You can't un-know that, which means you're the worst possible person to judge whether it's clear to someone else. The only way around it is to watch someone else try.

Ask another person, or use a provided persona, to complete a task like "add a resource and find every free option." Don't explain the interface while they work, however strong the urge gets. (It gets strong. I promise.) Note where they pause, pick an option you didn't expect, misread a label, or wonder whether something was saved. Then change one design decision and test again. Just one, so you can tell whether that change is what helped.

One person doesn't stand in for all users, and a persona is no substitute for the people who'll really use the tool. But when your tester gets confused, what does that tell you? It's tempting to decide they did something wrong, but they're the only evidence you've got about how the design reads to someone who didn't build it. If someone typed "free" at a menu that wanted a number, that's not them being silly. That's them telling you your menu didn't make it clear how to search by cost.

Try it: Sketch or implement a text-first catalog with add, display, filter, summary, and quit actions. Then:

  1. Mark every field required or optional and identify any unknown/not-applicable case.
  2. Remove one field the program does not need.
  3. Add labeled output and an explicit empty-result message.
  4. Test every action without a mouse.
  5. Ask another person to complete one task.
  6. Record one observation and the revision it caused.
