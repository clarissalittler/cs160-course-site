Lesson 5 - Modeling People and Designing Interfaces

When you finish this lesson, you should be able to:

  • Distinguish required, optional, unknown, and not-applicable data.
  • Critique a schema for unnecessary collection and categories that exclude reasonable cases.
  • Design a text interface with clear labels, state, errors, navigation, and exits.
  • Run a small usability test and turn an observation into a revision.

Correct storage does not guarantee a usable tool

A program can store every record correctly and still fail the people using it. A menu might not say what the options are. An error might erase someone's work. A screen reader might announce unlabeled values with no context to hang them on. A form might demand information that is unknown, irrelevant, or too sensitive for the task at hand.

Human–computer interaction—HCI for short—studies how people interact with computing systems. It isn't decoration applied after the programming is done. The names, prompts, categories, feedback, and navigation are part of the system's behavior, just as much as the loops underneath.

Required, optional, unknown, and not applicable are different

Consider a record for a community event:

event = {
    "name": "Neighborhood Repair Cafe",
    "location": "Library meeting room",
    "cost": 0.0,
    "end_time": None,
    "registration_url": None,
}

None says that no value is currently present—but the schema should say why:

  • Required: the tool cannot perform its stated job without the value.
  • Optional: useful when supplied, but the record remains valid without it.
  • Unknown: a value exists in the world but has not been learned or verified.
  • Not applicable: the field does not make sense for this record.

Using an empty string or 0 for all four of these cases destroys information. A $0 event is not the same thing as an event whose cost nobody has learned yet.

Do not collect a field merely because you can

Data minimization means collecting only what's needed for a stated purpose. A catalog of favorite albums doesn't need legal names, birth dates, or precise locations. A resource directory may need a neighborhood, but it doesn't need a user's home address. And every field you collect creates work: it has to be explained, protected, corrected, and eventually deleted.

Ask before adding a field:

  • What user goal requires it?
  • Could a less sensitive value serve the same goal?
  • Who can see it?
  • How can someone correct it?
  • When should it be removed?

Fixed categories leave remainders

A menu makes data tidy by limiting the choices, but real people and real situations don't always fit the choices. “Choose exactly one language,” “every person has a first and last name,” “every address has a US ZIP code”—each of these may simplify the code by making the system less truthful.

There are several honest responses: allow multiple selections, offer an explicit self-description option, add a free-text note, or decline to collect the field at all. “Other” can help, but it can also end up labeling many people as deviations from whatever the system assumed was normal. There is no universal schema—the design has to follow the real purpose and the real people affected.

Make a text interface predictable

def show_menu(record_count):
    print()
    print("COMMUNITY RESOURCE CATALOG")
    print(f"Current records: {record_count}")
    print("1. Add a resource")
    print("2. Display all resources")
    print("3. Search by area")
    print("4. Show summary")
    print("5. Quit")

def show_resource(resource):
    print(f"Name: {resource['name']}")
    print(f"Area: {resource['area']}")
    print(f"Cost: ${resource['cost']:.2f}")
    print(f"Notes: {resource.get('notes', 'not provided')}")

This interface tells the user:

  • where the user is,
  • what state exists now,
  • which actions are available,
  • which number selects each action, and
  • how to leave.

The important structure lives in words and labels, not only in color, horizontal position, or a decorative box. Keyboard input is enough to operate the menu. The output order stays consistent from record to record, too.

Errors should preserve dignity and progress

choice = input("Choose 1 through 5: ").strip()

while choice not in ["1", "2", "3", "4", "5"]:
    print(f"'{choice}' is not a menu option. Your records have not changed.")
    choice = input("Choose 1 through 5: ").strip()

Compare “Invalid user input” with a message that names the accepted choices and confirms that the current data is safe. The second one actually helps the user recover. Skip the jokes that are only funny when it's someone else making the mistake.

Accessibility is a set of testable behaviors

For a small text tool, check whether:

  • every action works from the keyboard;
  • prompts and results have descriptive labels;
  • meaning does not depend only on color, emoji, spacing, or animation;
  • the reading order matches the program's logical order;
  • errors explain how to recover without discarding work;
  • the program does not impose a short time limit;
  • a user can review what was entered before a consequential action.

No checklist represents every access need. What a checklist gives you is a set of concrete starting points—and reasons to test with people rather than assume.

Usability testing means observing, not defending

Ask another person—or use a provided persona—to complete a task such as “add a resource and find every free option.” Don't explain the interface while they work, however strong the urge gets (and I promise, it gets strong). Note where they pause, choose an unexpected option, misread a label, or wonder whether something was saved. Then revise one design decision and test again.

One person doesn't represent all users, and a persona is no substitute for the people actually affected. The habit worth building is treating confusion as evidence about the design—not evidence that the user failed.

Interface and schema review. Sketch or implement a text-first catalog with add, display, filter, summary, and quit actions. Then:

  1. Mark every field required or optional and identify any unknown/not-applicable case.
  2. Remove one field the program does not need.
  3. Add labeled output and an explicit empty-result message.
  4. Test every action without a mouse.
  5. Ask another person to complete one task.
  6. Record one observation and the revision it caused.
