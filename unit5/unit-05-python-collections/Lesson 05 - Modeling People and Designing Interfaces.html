Lesson 5 - Modeling People and Designing Interfaces

At the end of this lesson, you will be able to:

  • Distinguish required, optional, unknown, and not-applicable data.
  • Critique a schema for unnecessary collection and categories that exclude reasonable cases.
  • Design a text interface with clear labels, state, errors, navigation, and exits.
  • Run a small usability test and turn an observation into a revision.

Correct storage does not guarantee a usable tool

A program can store every record correctly and still fail its users. A menu may not say what options exist. An error may erase work. A screen reader may announce unlabeled values with no context. A form may demand information that is unknown, irrelevant, or too sensitive for the task.

Human–computer interaction, often shortened to HCI, studies how people interact with computing systems. It is not decoration applied after programming. The names, prompts, categories, feedback, and navigation are part of the system's behavior.

Required, optional, unknown, and not applicable are different

Consider a record for a community event:

event = {
    "name": "Neighborhood Repair Cafe",
    "location": "Library meeting room",
    "cost": 0.0,
    "end_time": None,
    "registration_url": None,
}

None means no value is currently present, but the schema should say why:

  • Required: the tool cannot perform its stated job without the value.
  • Optional: useful when supplied, but the record remains valid without it.
  • Unknown: a value exists in the world but has not been learned or verified.
  • Not applicable: the field does not make sense for this record.

Using an empty string or 0 for all four cases destroys information. A $0 event is not the same as a cost that is unknown.

Do not collect a field merely because you can

Data minimization means collecting only what is needed for a stated purpose. A catalog of favorite albums does not need legal names, birth dates, or precise locations. A resource directory may need a neighborhood but not a user's home address. Every collected field creates work: it must be explained, protected, corrected, and eventually deleted.

Ask before adding a field:

  • What user goal requires it?
  • Could a less sensitive value serve the same goal?
  • Who can see it?
  • How can someone correct it?
  • When should it be removed?

Fixed categories leave remainders

A menu makes data tidy by limiting choices, but real people and situations may not fit. “Choose exactly one language,” “every person has a first and last name,” or “every address has a US ZIP code” may simplify code by making the system less truthful.

Possible responses include allowing multiple selections, an explicit self-description option, a free-text note, or declining to collect the field. “Other” can help but can also label many people as deviations from the system's assumed norm. There is no universal schema; the design should follow the real purpose and affected people.

Make a text interface predictable

def show_menu(record_count):
    print()
    print("COMMUNITY RESOURCE CATALOG")
    print(f"Current records: {record_count}")
    print("1. Add a resource")
    print("2. Display all resources")
    print("3. Search by area")
    print("4. Show summary")
    print("5. Quit")

def show_resource(resource):
    print(f"Name: {resource['name']}")
    print(f"Area: {resource['area']}")
    print(f"Cost: ${resource['cost']:.2f}")
    print(f"Notes: {resource.get('notes', 'not provided')}")

This interface communicates:

  • where the user is,
  • what state exists now,
  • which actions are available,
  • which number selects each action, and
  • how to leave.

Important structure is expressed in words and labels, not only color, horizontal position, or a decorative box. Keyboard input is enough to operate the menu. Output order is consistent across records.

Errors should preserve dignity and progress

choice = input("Choose 1 through 5: ").strip()

while choice not in ["1", "2", "3", "4", "5"]:
    print(f"'{choice}' is not a menu option. Your records have not changed.")
    choice = input("Choose 1 through 5: ").strip()

Compare “Invalid user input” with a message that names the accepted choices and confirms the current data is safe. The second helps the user recover. Avoid jokes that are funny only when someone else makes a mistake.

Accessibility is a set of testable behaviors

For a small text tool, check whether:

  • every action works from the keyboard;
  • prompts and results have descriptive labels;
  • meaning does not depend only on color, emoji, spacing, or animation;
  • the reading order matches the program's logical order;
  • errors explain how to recover without discarding work;
  • the program does not impose a short time limit;
  • a user can review what was entered before a consequential action.

No checklist represents every access need. It provides concrete starting points and reasons to test with people rather than assuming.

Usability testing means observing, not defending

Ask another person—or use a provided persona—to complete a task such as “add a resource and find every free option.” Do not explain the interface while they work. Record where they pause, choose an unexpected option, misread a label, or wonder whether something was saved. Then revise one design decision and test again.

One person does not represent all users, and a persona is not a substitute for affected people. The important habit is treating confusion as evidence about the design rather than evidence that the user failed.

Interface and schema review. Sketch or implement a text-first catalog with add, display, filter, summary, and quit actions. Then:

  1. Mark every field required or optional and identify any unknown/not-applicable case.
  2. Remove one field the program does not need.
  3. Add labeled output and an explicit empty-result message.
  4. Test every action without a mouse.
  5. Ask another person to complete one task.
  6. Record one observation and the revision it caused.
