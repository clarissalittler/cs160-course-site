Unit 5 Summary

In this unit we moved from single values to models of the world. Strings, lists, and tuples are all sequences. Tuples keep a fixed group together; dictionaries attach a name to every value; and a list of dictionaries is a small table of records. Loop by loop, the same jobs kept coming back: traverse, transform, filter, count, total, unpack, find an extreme. And at the end we asked a different kind of question about all of it: do the fields and the interface make sense to the people the records describe and the people using the tool?

Then the last lesson turned the question around. Every one of those programs has a single person using it, who can notice a mistake and try again. When a program applies one rule to a whole list of people, a mistake that's rare for any one person becomes certain across thousands, and nobody is watching each case. The Robodebt rule was a division, a comparison, and a loop, and it sent debt notices to people who didn't owe anything, because of an assumption about how income arrives. A scam filter can wrongly flag a message or let a scam slip through, and those two mistakes land on different people. Choosing between them isn't only a programming decision.

If you look back over the unit, a few ideas kept coming back in different clothes. Immutability showed up with strings, then again with tuples, then again as the reason dictionary keys work at all. "Start with an empty result and build it up" showed up as building a string, then as transforming and filtering a list. And the difference between "nothing" and "zero" came up with None in average(), then again with unknown costs in an event record. Those aren't just Python details, either. Whatever language you program in next, you'll find some version of immutability, building up a result in a loop, and a value that means "nothing here."

What to carry forward

  • Indexes begin at 0; negative indexes count backward; slices include the start and exclude the stop.
  • Strings are immutable sequences. Methods return new strings, so keep the exact text a person entered when its form matters.
  • Lists are ordered and mutable. Treat empty collections and missing elements as expected states, not surprises.
  • Two names can refer to the same list, so a change through one name shows up through the other.
  • Collection patterns include traversal, transformation, filtering, aggregation, counting, and min/max.
  • A tuple is an ordered immutable sequence, good for compact fixed groups.
  • Tuple unpacking assigns elements to separate names. It shows up in multiple-value returns, enumerate(), zip(), dictionary .items(), and database rows.
  • A tuple of immutable values can be a compound dictionary key.
  • Functions keep calculations separate from input and display, which makes empty and boundary tests easy to repeat.
  • A dictionary maps keys to values. A list of dictionaries represents several records with named fields.
  • A schema or data dictionary explains types, units, meanings, required fields, and missing-value rules.
  • Choose tuples for fixed conventional positions and dictionaries when named or changing fields explain the record better.
  • Data minimization, recoverable errors, keyboard access, descriptive labels, predictable navigation, and usability testing are part of technical quality, not extra credit.
  • A record is a selective model of a person or situation, not the thing itself.
  • A rule that's right 99% of the time is wrong for thousands of people once it runs on hundreds of thousands.
  • Every rule carries assumptions about the people it's applied to; the program only knows the facts someone wrote down.
  • A yes/no rule can wrongly flag a case or let one slip through. Count them separately, and ask who bears each.
  • Before a rule runs on everyone, ask whether people can see why they were flagged, who has to prove what, and whether a person can step in.

Readiness check

Can you create and unpack a tuple, explain a multiple-value return, and say when fixed positions are clearer than named fields? Can you explain why a catalog is a list of dictionary records, state its schema, filter without changing the source, summarize a numeric field, handle zero matches, and spot a field that shouldn't be collected in the first place? And the real test of all of it: can another person complete the intended task from the labels alone? Finally, can you look at a rule that's applied automatically to many people, name an assumption inside it, and say who gets each kind of mistake?
