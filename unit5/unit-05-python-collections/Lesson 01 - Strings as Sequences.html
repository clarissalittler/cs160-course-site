Text is an ordered collection

Up to now a string has probably felt like one solid lump: "Portland" is just "Portland". You make one, you print it, you glue it onto other strings with + or drop it into an f-string, and that's about all. But think about what you do with text when you're proofreading something. You don't take the sentence in as a single blob, you go word by word and sometimes letter by letter, looking for the one that's wrong.

Python can do the same thing, because it also sees a string as a sequence: an ordered collection of characters that you can visit one at a time. Once you can get at the individual pieces, a whole range of things opens up. A program can inspect text, transform it, count things in it, search it, &c.

This is also the first collection we've worked with, a single value that holds many values inside it. Almost everything in this lesson (indexes, slices, looping over the pieces) carries over nearly unchanged to lists and tuples in the next few lessons, so if you get comfortable with it here, you'll already know a good chunk of the next two lessons.

city = "Portland"
print(len(city))
print(city[0])
print(city[1])
print(city[-1])

len(city) is 8. An index is a position in the sequence, and Python starts counting positions at 0, the same convention as range() and for the same reason: the first element is zero steps from the start. So city[0] is "P" and city[1] is "o". A negative index counts from the other end, so city[-1] is the last character, "d".

If starting at 0 still feels unnatural, you're in good company. People have argued about it for decades, and a few languages (Lua, MATLAB, and Fortran, for example) start counting at 1 instead. Python went with 0, following C and a lot of the languages that came after it, so that's what we'll do too. It stops feeling strange faster than you'd think.

Negative index-8-7-6-5-4-3-2-1

Ask for an index that doesn't exist, like city[8], and Python raises an IndexError. Since counting starts at 0, the last valid index is always len(city) - 1, not len(city). It's the string version of the off-by-one error from Unit 3.

Why doesn't Python just hand back an empty string, or None, and move on? Because asking for the ninth letter of an eight-letter word almost always means something is wrong in your logic, and Python would rather tell you loudly, right now, on the line where it happened, than let a made-up value sneak through and cause a much weirder problem twenty lines later. Keep that in mind for the next section, because slices behave differently.

Slices select a section

A lot of the time you don't want one character, you want a chunk: the year out of a date like "2026-09-22", the area code off a phone number, the first few letters of a name to build a username. A slice grabs a whole section at once. You give it a start index and a stop index, and, just like range(), the stop is excluded:

city = "Portland"
print(city[0:4])   # Port
print(city[4:8])   # land
print(city[:4])    # Port
print(city[4:])    # land
print(city[::2])   # P r l n, with no spaces in the actual result

Leave out the start and Python assumes "from the beginning"; leave out the stop and it assumes "through the end." A third number is a step, so city[::2] takes indexes 0, 2, 4, and 6 and gives you "Prln". That last one is less common to use but when you need it, you need it.

So why exclude the stop? It seems like it'd be more natural for city[0:4] to include index 4. But look at what you get by leaving it out: city[0:4] and city[4:8] fit together with no overlap and no gap, so city[:4] + city[4:] is always the whole string back again. And the length of a slice is just stop minus start, so city[0:4] has 4 characters. It's the same bargain range() makes, and once you've gotten used to it in one place you get it for free in the other.

Here's a small oddity: a slice that runs past the end just stops at the end without complaint, while a single out-of-range index raises an error. Open an interpreter and try both to confirm that I'm telling the truth: try city[30] vs. city[0:30]! Can you think of why the Python language might work that way? Is it an inconsistency of design, which do happen, or does it have some utility?

Traverse a string

When you want to look at every character but don't care about its position, you can loop over the string directly:

word = "signal"
vowel_count = 0

for character in word:
    if character in "aeiou":
        vowel_count += 1

print(f"{word} contains {vowel_count} vowels.")

Let's walk through it. The first time through the loop, character is "s", which isn't a vowel, so nothing happens. The second time it's "i", which is, so vowel_count goes from 0 to 1. Then "g" and "n" (nothing), then "a" (up to 2), then "l" (nothing). We've run out of characters, so the loop ends and the program prints that signal contains 2 vowels. There's no index anywhere in this code, and we didn't have to know how long the word was ahead of time. The loop takes care of all of that.

We're using in in two different ways here, although the similarities to English usage might help explain the distinction. The first is the loop structure where each time through the loop, character gets the next element of word. The second, the in operator, lets you ask whether one value shows up anywhere inside a collection. So character in "aeiou" is a Boolean-valued expression that means "return True if character is one of aeiou".

Now, sometimes the position does matter: you want to report where something was found, or compare a character to the one right before it. Use range(len(word)) only when that's the case:

for index in range(len(word)):
    print(f"Index {index} contains {word[index]}")

len(word) is 6, so range(6) gives us 0 through 5, which are exactly the valid indexes. That's not a coincidence, that's the whole reason range() and indexing both start at 0 and leave out the end!

Strings do not change in place

Here's a thing that might seem a little weird! Strings are immutable in Python: you can't reach in and change one character. Try word[0] = "S" and Python refuses. Why build a language that way? It's a reasonable thing to ask, and the answer is partly history and partly efficiency. If strings can never change, Python can safely hand out one copy of "hello" to every part of the program that uses it, without worrying that one part will scribble on it and break the others. (Immutability will also turn out to be why strings can be used to look things up in a dictionary, which we'll get to in Lesson 4.) What you do instead is build a new string:

message = "meet at noon"
new_message = ""

for character in message:
    if character == " ":
        new_message += "-"
    else:
        new_message += character.upper()

print(new_message)  # MEET-AT-NOON

new_message starts out as the empty string, "", a string with nothing in it. Each time through the loop we tack one more character onto the end: a dash if the original character was a space, the uppercase version otherwise. So after the first pass it's "M", then "ME", then "MEE", and so on until it's "MEET-AT-NOON". Strictly speaking each += makes a brand-new string rather than changing the old one, which might sound wasteful. For text the size of a message or a name, it's not something you'll ever notice.

This is a pattern you'll use all the time: start with an empty result, look at each element, and add a transformed version to the result. We'll see it again with lists in Lesson 3, where it gets a name.

Methods provide common transformations

Some transformations come up so often that Python just has them built in. They're methods, which are functions that belong to a value and get called with a dot. You've already seen one: character.upper() in the last example. You can read raw_reply.strip() as "hey, raw_reply, give me a copy of yourself with the extra spaces trimmed off the ends."

raw_reply = "  Yes Please  "
normalized_reply = raw_reply.strip().lower()

print(raw_reply)
print(normalized_reply)
print(normalized_reply.startswith("yes"))
print(normalized_reply.replace("please", ""))

The second line chains two methods, and you read it left to right: first strip the spaces, then lowercase whatever came out of that. The result is "yes please". Why bother? Because a person answering a question might type yes, Yes, YES, or Yes Please with a stray space on the end, and they all mean the same thing. Normalizing the text into one standard form means the rest of your program only has to check for one version instead of a dozen.

Here are the methods we'll use most: .strip(), .lower(), .upper(), .replace(), .startswith(), .endswith(), and .split(). Every one of them returns a new string and leaves the original alone, which follows from immutability: they couldn't change the original even if they wanted to. Keep that original around when its exact form matters, like a person's chosen capitalization or punctuation.

One Python element is not always one visible symbol

For simple English examples, "character" is a fine word for what an index gives you. Human writing systems have a wonderful amount of variety, though, and that means how we represent them on computers changes. Do you remember earlier in this class when we talked about Unicode and code points? That matters again! For example, an accented letter like é might be stored as one code point or as a plain e followed by a combining accent mark. (Unicode allows the second form so that you can put accents and other marks on any letter, in any language, without needing a separate code point for every possible combination.) Many emoji are built from several code points joined together, so a family emoji can be four people connected by invisible glue. Which means Python's indexing can cut right through the middle of something a reader sees as one symbol. (Try it! Paste a family emoji into len() and see what number comes back.)

None of this is a reason to avoid strings. It's a reason to know where the simple model stops. A rule like "a name must be at most 20 characters" behaves differently across languages, and lowercasing every name may not match how a real person writes theirs. Normalizing a temporary copy for comparison is fine. Rewriting the data that records someone's identity is a different matter.
