Lesson 6 - When One Rule Applies to Everyone

By the end of this lesson, you will be able to:

  • Apply a rule function to every record in a collection and count the results.
  • Explain how running a rule on many people turns rare mistakes into certain ones.
  • Identify an assumption built into a simple rule and the people it fails.
  • Distinguish a wrongly flagged case from one that slipped through, and explain who bears each kind of mistake.
  • Ask what a person needs in order to understand, question, or appeal an automated decision.

One user at a time

Think back over the programs in this unit: the temperature readings, the library and event records, the resource catalog with its menu, and the information tool you're building for the Week 5 assignment. They all have one thing in common, which is that there's exactly one person using them at a time.

That person is right there when something goes wrong. If your menu doesn't understand what they typed, they see a confused message, sigh, and try again. If a record comes out wrong, they notice and fix it. So the total cost of the bug is maybe ten seconds and a little grumbling.

A lot of the programs that matter most in the world don't work like that at all. They take one rule and apply it to everybody at once: every tax return, every job application, every text message arriving on every phone. Nobody is sitting there watching each case go by. The people on the receiving end usually never see the code, and a lot of the time they don't even know a program was involved.

Back in Unit 4 we said that an if statement is a policy, and we asked who picks the thresholds, which borderline cases are likely to come up, and whether a person can appeal. This lesson asks what changes when that same if runs on everyone. The strange thing, as you'll see, is that the code barely changes at all. Almost everything that changes is outside the program.

From one call to a whole list

Here's a tiny version of the kind of check an agency might run. Each record has an amount someone reported and an amount the agency estimated, and the rule is: if the reported amount is lower than the estimate, flag it for review.

def needs_review(record):
    return record["reported"] < record["estimated"]

records = [
    {"name": "A. Rivera", "reported": 900, "estimated": 850},
    {"name": "B. Okafor", "reported": 400, "estimated": 400},
    {"name": "C. Nguyen", "reported": 0, "estimated": 1000},
]

flagged = 0
for record in records:
    if needs_review(record):
        print("Flagged:", record["name"])
        flagged += 1

print(f"{flagged} of {len(records)} records flagged.")

You've seen every piece of this before. needs_review is a Boolean function like the ones from Unit 4, and the loop is the traverse-and-count pattern from Lesson 3. With three records you can check the answer by eye: only C. Nguyen gets flagged.

Now suppose the list has 400,000 records in it. What do you have to change in the code?

Nothing! It's the same three-line loop. That's a big part of why organizations automate checks like this in the first place. Once the rule is written, the computer will happily apply it to every record, all night long, far faster than an entire office full of people could.

Here's the problem, though. Say the rule is right 99% of the time. That sounds pretty good, and on three test records it'll probably look perfect. But 1% of 400,000 is 4,000. So a mistake that's rare for any one person is certain to happen thousands of times once the rule runs on everybody.

And since nobody is looking at individual cases, those 4,000 records don't look any different from the rest. The program flags them exactly the same way it flags all the others. That's why, for a rule that runs on everybody, "does it usually work?" isn't a good enough question. You also have to ask who it gets wrong, and what happens to them.

Robodebt: the assumptions inside a rule

Let me tell you about a real case. From 2016 to 2019, the Australian government ran an automated system, which came to be known as "Robodebt," to check whether people getting welfare payments had reported their income correctly.

People on benefits reported their income every two weeks (a fortnight, in Australian terms). The tax office, though, mostly knew each person's income for the whole year. So the system took each person's yearly income, spread it evenly across the fortnights, and compared that average with what they'd reported.

If the average was higher, the system decided they'd under-reported, and it sent them a debt notice.

Here's a simplified version of that rule in Python, run on two people who each earned $26,000 in a year:

FORTNIGHTS_PER_YEAR = 26

def averaged_income(annual_income):
    return annual_income / FORTNIGHTS_PER_YEAR

def looks_underreported(person):
    estimate = averaged_income(person["annual_income"])
    return estimate > person["reported_per_fortnight"]

people = [
    {
        "name": "Sam",
        "story": "steady part-time job all year",
        "annual_income": 26000,
        "reported_per_fortnight": 1000,
    },
    {
        "name": "Jordan",
        "story": "full-time for six months, then laid off",
        "annual_income": 26000,
        "reported_per_fortnight": 0,
    },
]

for person in people:
    estimate = averaged_income(person["annual_income"])
    print(f"{person['name']} ({person['story']})")
    print(f"  Averaged estimate: ${estimate:.2f} per fortnight")
    print(f"  Reported each fortnight on benefits: ${person['reported_per_fortnight']:.2f}")
    if looks_underreported(person):
        print("  RESULT: debt notice sent")
    else:
        print("  RESULT: no action")

Running it gives:

Sam (steady part-time job all year)
  Averaged estimate: $1000.00 per fortnight
  Reported each fortnight on benefits: $1000.00
  RESULT: no action
Jordan (full-time for six months, then laid off)
  Averaged estimate: $1000.00 per fortnight
  Reported each fortnight on benefits: $0.00
  RESULT: debt notice sent

Sam earned about the same amount every fortnight, so the average describes Sam pretty well, and the rule gets it right.

Jordan is a different story. Jordan earned $2,000 a fortnight for half the year, then got laid off, went on benefits, and honestly reported earning nothing. The average says Jordan earned $1,000 every fortnight, including the ones on benefits, so the rule concludes that Jordan was hiding income. Jordan gets a debt notice for money they never owed.

What kind of bug is this? It isn't a typo, and nothing crashes. Every line does exactly what it says. The bug is the assumption hiding inside annual_income / FORTNIGHTS_PER_YEAR: that income shows up evenly all year long.

That's true for Sam. It's false for seasonal workers, people with irregular hours, and people who lost a job partway through the year—which is to say, it's false for a lot of the people most likely to need benefits in the first place!

It's the problem from Lesson 5 all over again, the one about forms that assume everybody fits the same boxes, except now nobody gets to fill out the form at all. The rule simply decides, and it has people's rent money on the line. Nobody told this program how real paychecks work.

The way the system was run made it worse. Instead of a caseworker double-checking the math, people who got a notice had to prove they didn't owe the money, often by digging up payslips from years earlier. Hundreds of thousands of people got debts. In 2019 the government conceded in court that averaging alone wasn't a lawful basis for a debt, and it later agreed to a settlement worth more than a billion Australian dollars. A Royal Commission (a formal national inquiry) reported in 2023 and called the scheme "a crude and cruel mechanism, neither fair nor legal."

One thing that wasn't involved in any of this is artificial intelligence. Everything in this story is Unit 4 Python. What went wrong was that no person was looking at each case anymore. A caseworker reading Jordan's file would probably have noticed "oh, they got laid off in June," and the program had no way to notice that.

Two ways to be wrong

A rule that answers yes or no can be wrong in two different ways. It can say yes when it should've said no, so that one got wrongly flagged. Or it can say no when it should've said yes, so that one slipped through. The thing I really want you to see is that those two mistakes usually land on different people, so you have to count them separately.

Let's try it with something you've almost certainly dealt with: scam texts. Here's a very simple filter. It gives each message a "suspicion score," one point for every suspicious phrase in it, and flags any message whose score reaches a threshold.

To check a filter, you need some messages where you already know the right answer. So I went through and labeled each one by hand as a scam or not. (Real filters get checked the same way, by the way. Before anyone can count a filter's mistakes, somebody has to decide what the right answers were.)

SUSPICIOUS_WORDS = ["urgent", "prize", "verify", "gift card", "act now", "password"]

messages = [
    {"text": "URGENT: verify your password or your account closes today", "scam": True},
    {"text": "You won a prize! Claim your gift card now", "scam": True},
    {"text": "Your package is waiting, pay the $1.99 fee at this link", "scam": True},
    {"text": "Reminder: the library closes early on Friday", "scam": False},
    {"text": "Urgent: school is closed tomorrow because of ice", "scam": False},
    {"text": "Can you pick up milk on the way home?", "scam": False},
    {"text": "Raffle results are in, you won the prize basket!", "scam": False},
    {"text": "Bank alert: act now to verify a charge of $480", "scam": True},
]

def suspicion_score(text):
    lowered = text.lower()
    score = 0
    for phrase in SUSPICIOUS_WORDS:
        if phrase in lowered:
            score += 1
    return score

def count_outcomes(messages, threshold):
    caught = 0
    slipped_through = 0
    wrongly_flagged = 0
    correctly_passed = 0
    for message in messages:
        flagged = suspicion_score(message["text"]) >= threshold
        if flagged and message["scam"]:
            caught += 1
        elif not flagged and message["scam"]:
            slipped_through += 1
        elif flagged and not message["scam"]:
            wrongly_flagged += 1
        else:
            correctly_passed += 1
    return caught, slipped_through, wrongly_flagged, correctly_passed

caught, slipped, wrong, passed = count_outcomes(messages, 1)
print(f"Caught scams:      {caught}")
print(f"Scams slipped by:  {slipped}")
print(f"Wrongly flagged:   {wrong}")
print(f"Correctly passed:  {passed}")

suspicion_score is a counter from Lesson 3 with a string check in the middle. phrase in lowered asks whether one string shows up anywhere inside another, so "gift card" in "claim your gift card now" is True. Lowercasing first means URGENT still matches "urgent".

count_outcomes runs the filter on every message and compares its answer with the label.

Each message can come out four ways: a scam that's caught, a scam that slips through, a real message that's wrongly flagged, or a real message that's correctly let through. So there are four counters, and the function hands all four back as a tuple. With a threshold of 1 (any single suspicious phrase is enough), you get:

Caught scams:      3
Scams slipped by:  1
Wrongly flagged:   2
Correctly passed:  2

Go back to the list of messages and find the ones it got wrong. The two wrongly flagged messages are the school closing (it says "urgent") and the raffle results (they say "prize"). The scam that slipped through is the package fee, which doesn't use any of our suspicious phrases at all.

Now think about who each mistake lands on. When the school's message goes to spam, a parent doesn't find out school is closed. When the package scam slips through, someone might pay a fake fee. Those are different harms, to different people, and a single score like "the filter got 5 out of 8 right" would hide both of them.

Turning the knob

So should one suspicious phrase really be enough to flag a message? Let's try a few thresholds and count. Add this to the bottom of the program:

for threshold in range(1, 4):
    caught, slipped, wrong, passed = count_outcomes(messages, threshold)
    print(f"Threshold {threshold}: caught {caught}, slipped by {slipped}, wrongly flagged {wrong}")
Threshold 1: caught 3, slipped by 1, wrongly flagged 2
Threshold 2: caught 3, slipped by 1, wrongly flagged 0
Threshold 3: caught 1, slipped by 3, wrongly flagged 0

Bumping the threshold up to 2 clears both wrongly flagged messages without missing any extra scams, at least on these eight. Bumping it to 3 makes the filter so cautious that most of the scams get through.

That's the general pattern, and it's kind of frustrating! A stricter rule wrongly flags fewer things and lets more slip through, and a looser rule does the reverse. You almost never get to make both kinds of mistake go away at once, so somebody has to decide which kind matters more.

So who should make that decision? It's really a question about whose mistakes we're willing to live with, which means it usually shouldn't be up to the programmer alone. The school, the people being targeted by scams, and everyone else reading their texts all have a stake in it.

No threshold catches the package-fee scam, though. The filter can only see what it was told to look for. To catch it you'd have to change the phrase list, and any phrase you add will probably catch some legitimate message too. (Imagine adding "fee", and then think about the library's overdue notices.)

What you just did, trying a few settings, counting the mistakes for each, and keeping the best one, is going to come back in a big way in Unit 9. A lot of machine learning is this same process done automatically, with billions of knobs instead of one. (And with far more than eight test messages! Unit 8 has a lot to say about how much you can trust a tiny sample.)

Who decides, and who can push back?

The questions from Unit 4 still apply, but when a rule runs on lots of people a few more come up. Here are the ones I'd ask about any program like that:

  • Who gets wrongly flagged, and who's harmed when something slips through? Are those the same people who chose the rule?
  • What has to be true about a person's life for the rule to get their case right? Who doesn't fit that picture?
  • Does a flagged person find out why, and can they appeal? Jordan got a debt notice, not the arithmetic behind it.
  • Is there a person who can look at an individual case and override the rule?

You don't need to read a line of code to ask any of these. But it helps to have written a loop like the ones in this lesson, because now you've seen for yourself that the program running on 400,000 people can be the same few lines you tested on three.

Back to your own programs

Your own programs have rules too. When the Week 5 information tool decides a search matches, or that a record is missing a required field, that's an if statement making a decision about someone's data! But it affects one person, who's sitting right there and can fix it in a second, and that's what makes a small program a good place to write rules and get them wrong. All the habits from this unit carry over to programs where much more is at stake, and this lesson adds one more: when a rule is going to be applied to a lot of people, find out who it gets wrong, and what happens to them, before it goes live.

Try it:

  1. Run the scam filter and confirm the four counts at threshold 1.
  2. Write two new messages, one scam and one not, that the filter gets wrong at threshold 2. Add them to the list (with correct labels) and rerun the threshold comparison. Does a different threshold win now?
  3. Add one phrase to SUSPICIOUS_WORDS that catches the package-fee scam. Rerun the comparison. Did anything else change?
  4. In the averaging example, what extra information would looks_underreported need in order to get Jordan's case right? Where would that information come from, and whose job would it be to provide it?
  5. Pick a rule that applies to you automatically: a spam folder, a late-fee policy, a grade cutoff, a content filter on an app you use. Who gets each kind of mistake, and is there a way to ask a person to take a second look?
