Lesson 3: Text, Unicode, and Standards

Big question

A computer stores bits, not letters. How can a message written on one device arrive as the same human language on another?

This lesson's goals: explain what a character encoding is, use a small encoding table, keep Unicode code points and their byte encodings straight, and describe why technical standards are social achievements as much as technical ones.

Meaning requires an agreement

The bit pattern 01000001 doesn't naturally or inevitably mean the letter A. Read as an unsigned binary number, it's 65. It could be one color channel in a pixel, part of a machine instruction, or one small piece of a sound recording. Bits mean something only when a program interprets them according to an agreed system—and someone had to make that agreement.

A character encoding maps characters to numbers so text can be stored and transmitted. The writer's software turns characters into numbers and then bits; the reader's software follows the same agreement in reverse. If the two sides use different agreements, the bits can arrive perfectly intact while the text comes out as nonsense. Which is exactly why standards matter.

ASCII: an influential early agreement

ASCII, the American Standard Code for Information Interchange, is a historically important seven-bit encoding. Seven bits give 27 = 128 patterns, and ASCII spends them on English letters, digits, punctuation, and control codes such as the line break.

To encode BA!, look up 66, 65, and 33. Written as eight-bit groups, the message becomes:

01000010 01000001 00100001

The spaces are only there to help your human eyes find the byte boundaries—they aren't characters in the encoded message. One more wrinkle: uppercase and lowercase letters have entirely different values. A computer has no built-in sense that A and a are “the same letter in a different outfit”; if software treats them as related, it's because someone wrote rules relating them.

From a keystroke to a file—and back again

Say you save the three-character message Hi! as a plain-text file. (ASCII and UTF-8 happen to use the same values for these three characters, so no arguments break out.)

When you press Save, your editor doesn't store the visible shapes of the letters. It writes those three bytes to the file, in order. Copying the file copies those bytes. When another editor opens it, everything runs in reverse: read the byte values, interpret them as characters using an encoding, and ask a font to draw an H, an i, and a !.

The decimal values in the table are for our benefit, not the computer's—the file does not literally contain the printed digits 72 105 33. (If it did, those five digits and two spaces would themselves be seven characters needing seven character codes, and around we'd go.) At the storage layer, a file is simply a sequence of bytes.

Invisible characters count too. Pressing Enter typically inserts a newline code. A tab, a space, or a carriage return changes how text is arranged even though it never draws a letter. Two files that look nearly identical on screen can contain quite different byte sequences.

Encoding is not encryption. An encoding makes information usable in another representation, and its mapping is completely public. Encryption deliberately hides information from anyone who lacks a key. Turning A into 65 keeps no secrets from anybody.

Why ASCII was not enough

ASCII was designed around a limited set of characters used in American English. Most of the world's writing systems simply aren't in it—no é, no 中, no ش, and certainly no 😊. Many communities built additional encodings of their own, which solved the local problem and created a global one: a value written under one convention could be interpreted as a completely different character under another.

And this is more than an inconvenience. A system that can't correctly store a person's name, language, or communication is treating some of its users as exceptions. Deciding what a standard represents is deciding who gets to participate without workarounds.

Unicode: a shared character repertoire

Unicode is an international standard that aims to assign a unique number to characters across languages and computing systems. That number is called a code point and is usually written as U+ followed by hexadecimal digits—A is code point U+0041. Unicode kept ASCII's original values, so this old familiar character still has decimal value 65.

A code point identifies an abstract character; it doesn't, by itself, specify the exact bytes that land in a file. An encoding form such as UTF-8 defines how code points become bytes. In UTF-8, ASCII characters take one byte, while many other characters take two, three, or four. That variable length keeps ASCII-heavy text compact while leaving room for a vastly larger shared repertoire—a clever compromise.

The Unicode Consortium's introduction to Unicode describes the standard and its goal of consistent text representation across platforms, programs, and languages.

What an encoding mismatch looks like

When a text editor saves café in UTF-8, that final é is stored as the two bytes C3 A9. A program that correctly reads those two bytes as one UTF-8 sequence displays é. A program that mistakenly treats each byte as its own character from an older single-byte encoding displays something like cafÃ©. The file's bits arrived intact; the reader just used the wrong mapping.

You may also run into a diamond or question-mark-shaped replacement symbol, which usually means the program hit a byte sequence it couldn't interpret as valid text under the selected encoding. A blank rectangle is a different ailment: the character decoded correctly, but the chosen font has no glyph for it.

In practice, this is why file formats and network messages declare an encoding such as UTF-8. If text ever comes out looking corrupted, don't panic and don't hit Save: preserve the original bytes, figure out which encoding created the file, and reopen or import it with that encoding. Saving the garbled version can turn a fully reversible misreading into real damage.

A “character” can be more complicated than it looks

People use the word character for several different things, and the differences bite. What a reader experiences as one character may contain multiple code points. The é we just met can be the single code point U+00E9, or an e (U+0065) followed by a combining acute accent (U+0301)—two versions that look identical while containing different code-point and byte sequences. Many emoji that appear as one symbol are likewise little sequences of multiple people, modifiers, or joiners glued together.

So software can't always count visible characters by counting code points or bytes. The Unicode Standard uses the idea of a grapheme cluster to approximate one user-perceived character. This matters whenever a text editor moves the cursor, deletes a symbol, wraps a line, or limits the length of a name; the Unicode text-segmentation standard spells out rules software can follow.

Searching and comparison hit the same trouble. A database that compares only raw bytes could treat the two spellings of é as different even though a reader sees the same name. Unicode normalization gives software standard ways to put equivalent sequences into a consistent form before comparing them.

All of which is a nice example of abstraction doing its job. A person writing a message wants to think about letters and words, not bytes—and application and system software cooperate to keep it that way, until a wrong encoding, a missing font, or a badly designed text field lets the lower layers show through.

Standards are maintained, not discovered

ASCII and Unicode show that representations are collective agreements. Organizations propose rules; companies and open-source projects implement them; people find the omissions and errors; the standards evolve. Compatibility is the whole game—a standard becomes useful only when many independent systems interpret it consistently.

Standards also involve honest judgment calls. A committee must decide whether two symbols are versions of one character or two distinct characters, what to do about older encodings, and how to add new scripts without breaking existing text. Technical constraints matter, but so do language, history, power, and who's in the room.

Everyday life and social impact: when a system cannot spell your name

Names travel through school records, medical systems, payroll, banking, travel reservations, email addresses, and government forms. A form designed for a short ASCII-only “first name” and “last name” may reject an accent, an apostrophe, a space, a non-Latin script, or a naming structure its designers never imagined. One system silently strips a mark while another keeps it, and suddenly a person's records no longer match each other.

Unicode gives systems a shared vocabulary for far more languages, but adopting the standard is only step one. Databases need enough space, fonts need the relevant glyphs, search needs appropriate normalization, interfaces need right-to-left and other layout support—and institutional rules have to stop treating unfamiliar names as invalid.

  • Who benefits? Shared standards let people communicate and let independent systems exchange records.
  • Who might be harmed? People whose languages or names are handled poorly can face inconvenience, embarrassment, duplicate records, delayed services, or an inability to prove that a record belongs to them.
  • Who decides? Standards organizations define code points; software and font makers implement them; institutions set validation rules; affected language communities identify mistakes and missing support.

The problem was never that computers “only understand English.” Computers understand patterns. People decide which patterns a system accepts, and whether supporting everyone counts as a requirement or a nice-to-have.

Lesson takeaway

Text becomes digital when an agreed encoding maps characters to numbers and numbers to bits. ASCII shows the basic method; Unicode and UTF-8 stretch it across languages and systems. Standards are what make communication possible—and they're designed and maintained by people, which means their design decides whose language a system handles well.
