Lesson 3: Text, Unicode, and Standards

Big question

A computer stores bits, not letters. How can a message written on one device arrive as the same human language on another?

By the end of this lesson, you should be able to explain character encoding, use a small encoding table, distinguish Unicode code points from their byte encodings, and describe why technical standards are social as well as technical achievements.

Meaning requires an agreement

The bit pattern 01000001 does not naturally or inevitably mean the letter A. It can mean 65 when interpreted as an unsigned binary number. It can be one color channel in a pixel, part of a machine instruction, or one small piece of a sound recording. Bits acquire meaning when a program interprets them according to an agreed system.

A character encoding maps characters to numbers so text can be stored and transmitted. The writer's software converts characters into numbers and then bits. The reader's software follows the same agreement in reverse. If the two sides use different agreements, the bits may arrive perfectly while the text appears as nonsense. This is why standards matter.

ASCII: an influential early agreement

ASCII, the American Standard Code for Information Interchange, is a historical seven-bit encoding. Seven bits provide 27 = 128 patterns. ASCII assigns those values to English letters, digits, punctuation, and control codes such as a line break.

The spaces above help human readers see byte boundaries; they are not characters in the encoded message. Notice also that uppercase and lowercase letters have different values. A computer does not see “the same letter in a different style” unless software has rules for relating them.

From a keystroke to a file—and back again

Consider saving the three-character message Hi! as a plain-text file. ASCII and UTF-8 use the same values for these three characters:

When you press Save, the text editor does not normally store the visible shapes of the letters. It writes these three bytes to the file in order. Copying the file copies those bytes. When another editor opens it, the process runs in reverse: the editor reads the byte values, interprets them as characters using an encoding, and asks a font to draw glyphs for H, i, and !.

The decimal values in the table are explanations for humans; the file does not literally contain the printed digits 72 105 33. If it did, those five digits and two spaces would themselves be seven characters requiring seven character codes. At the storage layer, the file is simply a sequence of bytes.

Invisible characters count too. Pressing Enter typically inserts a newline code. A tab, space, or carriage return can change how text is arranged even though it does not draw a letter. Two files that look almost identical may therefore contain different byte sequences.

Encoding is not encryption. An encoding makes information usable in another representation; its mapping is public. Encryption intentionally hides information from people who lack a key. Turning A into 65 keeps no secret.

Why ASCII was not enough

ASCII was designed around a limited set of characters used in American English. It does not contain most of the world's writing systems, and it cannot represent characters such as é, 中, ش, or 😊. Many communities developed additional encodings, but using incompatible mappings created a new problem: a value written under one convention could be interpreted as a different character under another.

This is not merely an inconvenience. A system that cannot correctly store a person's name, language, or communication treats some users as exceptions. Deciding what a standard represents affects who can participate without workarounds.

Unicode: a shared character repertoire

Unicode is an international standard intended to assign a unique number to characters across languages and computing systems. That number is called a code point and is usually written with U+ followed by hexadecimal digits. For example, A is code point U+0041. Unicode kept ASCII's original values, so this familiar character still has decimal value 65.

A code point identifies an abstract character; it does not by itself specify the exact bytes placed in a file. An encoding form such as UTF-8 defines how code points become bytes. In UTF-8, ASCII characters use one byte, while many other characters use two, three, or four bytes. This variable length saves space for text dominated by ASCII characters while still allowing a much larger shared repertoire.

The Unicode Consortium's introduction to Unicode describes the standard and its goal of consistent text representation across platforms, programs, and languages.

What an encoding mismatch looks like

Suppose a text editor saves café in UTF-8. The final é is stored as the two bytes C3 A9. If another program correctly interprets those two bytes as one UTF-8 sequence, it displays é. If it mistakenly treats each byte as a separate character from an older single-byte encoding, it may display something like cafÃ©. The file's bits arrived intact; the reader used the wrong mapping.

You may also see a diamond or question-mark-shaped replacement symbol. That often means the program encountered a byte sequence it could not interpret as valid text under the selected encoding. A blank rectangle can indicate a different problem: the character was decoded correctly, but the chosen font has no glyph for it.

In practice, this is why file formats and network messages declare an encoding such as UTF-8. If text suddenly looks corrupted, preserve the original bytes, check which encoding created the file, and reopen or import it with that encoding before saving again. Saving the garbled version can turn a reversible interpretation problem into additional corruption.

A “character” can be more complicated than it looks

People often use the word character for several different things. What a reader experiences as one character may contain multiple code points. For example, é can be represented as the single code point U+00E9, or as e (U+0065) followed by a combining acute accent (U+0301). The two versions can look identical while containing different code-point and byte sequences. Many emoji that appear as one symbol are likewise sequences containing multiple people, modifiers, or joiners.

Software therefore cannot always count visible characters simply by counting code points or bytes. The Unicode Standard uses the idea of a grapheme cluster to approximate one user-perceived character. This matters when a text editor moves the cursor, deletes a symbol, wraps a line, or limits the length of a name. The Unicode text-segmentation standard specifies rules software can use.

It also matters for searching and comparison. A database that compares only raw bytes could treat the two spellings of é as different even though a reader sees the same name. Unicode normalization gives software standard ways to put equivalent sequences into a consistent form before comparing them.

This is a useful example of abstraction. A person writing a message usually wants to think about letters and words, not bytes. Application and system software cooperate to hide the lower layers—until an incorrect encoding, a missing font, or a poorly designed text field exposes them.

Standards are maintained, not discovered

ASCII and Unicode show that representations are collective agreements. Organizations propose rules; companies and open-source projects implement them; people identify omissions and errors; and standards evolve. Compatibility matters because a standard becomes useful only when many independent systems interpret it consistently.

Standards also involve judgment. A committee must decide whether two symbols are versions of one character or distinct characters, how to handle older encodings, and how to add new scripts without breaking existing text. Technical constraints matter, but so do language, history, power, and participation.

Everyday life and social impact: when a system cannot spell your name

Names move through school records, medical systems, payroll, banking, travel reservations, email addresses, and government forms. A form designed for a short ASCII-only “first name” and “last name” may reject an accent, apostrophe, space, non-Latin script, or a naming structure its designers did not anticipate. One system may silently remove a mark while another preserves it, leaving records that no longer match.

Unicode gives systems a shared vocabulary for far more languages, but adopting the standard is only the first step. Databases need sufficient space, fonts need the relevant glyphs, search needs appropriate normalization, interfaces need right-to-left and other layout support, and institutional rules must stop treating unfamiliar names as invalid.

  • Who benefits? Shared standards let people communicate and let independent systems exchange records.
  • Who might be harmed? People whose languages or names are handled poorly can face inconvenience, embarrassment, duplicate records, delayed services, or an inability to prove that a record belongs to them.
  • Who decides? Standards organizations define code points; software and font makers implement them; institutions set validation rules; affected language communities identify mistakes and missing support.

The social problem is not that computers “only understand English.” Computers understand patterns. People decide which patterns a system accepts and whether supporting everyone is treated as a requirement or an optional extra.

Lesson takeaway

Text becomes digital when an agreed encoding maps characters to numbers and numbers to bits. ASCII demonstrates the basic method; Unicode and UTF-8 extend it across languages and systems. Standards make communication possible, but they are designed and maintained by people, and their design affects whose language a system handles well.
