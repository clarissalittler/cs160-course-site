Small Weird Project — HTTP Over Telnet

What you'll do: Open a terminal and talk to a web server directly by typing raw HTTP requests by hand. You'll see exactly what your browser sees — before it makes everything pretty.

This project is NOT graded. It's just for fun and exploration. There's nothing to turn in. If you try it and it's cool, great. If you skip it, that's fine too.

Going Backstage

You've learned about HTTP — how your browser sends requests and web servers send responses. But you've only ever seen it through the browser, which hides all the messy details behind a nice rendered page. In this project, you're going to talk to a web server directly — typing HTTP requests by hand and reading the raw responses. It's like going backstage at a concert. The show looks very different from back there.

What You'll Need

Just a terminal. That's it.

  • Mac / Linux: Open Terminal (it's built in). You already have everything you need.
  • Windows: Open PowerShell or Command Prompt. If telnet isn't available, you can enable it in Windows Features, or just use the curl alternative described below.

Step-by-Step: The Telnet Approach

1. Connect to a web server

Open your terminal and type:

telnet example.com 80

What you just did: you opened a raw TCP connection to the server at example.com on port 80 (the standard HTTP port). You're now connected — the server is listening and waiting for you to say something. No browser, no magic. Just you and a server, talking over a wire.

2. Send an HTTP request

Type the following exactly as shown (capitalization matters):

GET / HTTP/1.1
Host: example.com

Then press Enter twice (you need a blank line after the headers — that blank line tells the server "I'm done talking, your turn").

3. Read the raw response

The server will send back something like this:

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1256
Date: Tue, 25 Feb 2026 10:30:00 GMT
...

Followed by a big block of HTML — <html>, <head>, <body>, the works. That HTML is exactly what your browser would receive. Your browser just takes that HTML and renders it into the nice-looking page you're used to seeing. Here, you're seeing the raw ingredients before they get cooked.

4. Understand what you're looking at

Let's break down what came back:

  • HTTP/1.1 200 OK — the status line. 200 means "everything's fine, here's your page." You learned about status codes in the HTTP lesson.
  • Content-Type: text/html — tells the browser what kind of data this is (HTML text).
  • Content-Length: 1256 — how many bytes of data are coming.
  • Date: — when the server processed your request.
  • Then a blank line, and then the actual HTML body.

Every single time you visit a website, this exact exchange happens behind the scenes. Your browser just does it for you and hides the headers.

Try a Few More Things

Request a specific path

Instead of GET /, try requesting a specific page:

GET /index.html HTTP/1.1
Host: example.com

(Remember the blank line after!) On example.com this gives you the same page, but on other servers it would give you a different resource.

Send a HEAD request

A HEAD request asks for just the headers — no body:

HEAD / HTTP/1.1
Host: example.com

You'll get back the status line and headers, but no HTML. This is how programs check if a page exists without downloading the whole thing — useful when you just want to know if a link is broken.

Why only example.com? Most real websites now use HTTPS (encrypted HTTP), which means plain telnet won't work for them. Telnet sends everything in plain text — no encryption. That's actually great news for security (you'll learn about encryption in Unit 10!), but it means we need a server that still supports plain HTTP for this experiment. example.com is maintained by IANA specifically as a safe, simple example domain.

Alternative: The curl Approach

If telnet isn't working on your machine — it's sometimes disabled by default on modern systems — you can see the same thing using curl. The -v flag (verbose) shows you the full request and response headers:

curl -v http://example.com

Lines starting with > are what your machine sent (the request). Lines starting with < are what the server sent back (the response). It's the same conversation, just displayed in a slightly different format.

Try these too:

curl -v -I http://example.com

The -I flag sends a HEAD request — same as typing HEAD / in telnet.

Experiment!

Try this:

  • Request a page that doesn't exist — try GET /fakepage HTTP/1.1. What status code do you get? (Hint: it's a number you've probably seen before.)
  • Look through the response headers. Are there any you didn't expect? Can you figure out what they mean?
  • Using curl -v, try connecting to a few different HTTP sites. Do the response headers look similar or different?
  • Try curl -v https://example.com (note the s in https). Look at the extra lines of output — that's the TLS encryption handshake happening. It's a lot more complicated than plain HTTP!

What You Just Demonstrated

HTTP is just text. Specifically, it's a structured text conversation between a client and a server. Your browser is an extremely fancy program that sends these text requests, receives text responses, and then renders the HTML into something pretty. But under the hood, it's all just strings going back and forth over a network connection.

That's the point of this project: the browser is an abstraction layer. It hides the details to make your life easier — but the details are always there, and now you've seen them. Next time you visit a website, you'll know exactly what's happening behind that loading spinner.
