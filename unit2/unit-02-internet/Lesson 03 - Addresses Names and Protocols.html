Lesson 3: Addresses, Names, and Protocols

Big question

How do unfamiliar devices agree on whom a message is for, which program should receive it, and what all its bits mean?

By the end of this lesson, you should be able to explain protocols and layers, distinguish IP addresses from domain names and people, trace a DNS lookup, use ports to identify services, and design a complete text-based protocol for a small game.

A protocol is a shared agreement

Suppose a note says only 100000010. Is it an address, a game move, a number, or part of a picture? Even if two people agree that it is a game move, they still need to know where the recipient field ends, which squares exist, and how a reply reports a hit. Bits communicate only when sender and receiver follow the same rules.

A protocol is an agreed set of rules for exchanging information. It can define:

  • the order and size of fields;
  • what each value means;
  • who sends first and which replies are valid;
  • how errors or missing messages are handled; and
  • how an interaction begins and ends.

Human conversations have protocols too. “Hello” begins an exchange; a raised hand requests a turn; a mailing address follows a shared order. Some are written standards and others are social conventions. Either way, cooperation depends on participants having compatible expectations.

Design a Battleship protocol in text

Consider four players numbered 1 through 4. Each uses a four-by-four board whose rows are A through D and columns are 1 through 4. They cannot speak or rely on color. Every move must be one line of zeros and ones that can be sent asynchronously in a message.

Here is one possible fixed-length protocol. It is not the only good design:

A ten-bit protocol for four-player Battleship
FieldLengthMeaning
TO2 bitsPlayer 1 = 00, 2 = 01, 3 = 10, 4 = 11
FROM2 bitsThe same two-bit player mapping
TYPE1 bit0 = shot; 1 = result
ROW2 bitsA = 00, B = 01, C = 10, D = 11
COLUMN2 bits1 = 00, 2 = 01, 3 = 10, 4 = 11
RESULT1 bitFor a result, 0 = miss and 1 = hit; ignored in a shot

Using spaces to show field boundaries, “player 1 to player 3: fire on A2” is 10 00 0 00 01 0. The final filler bit is ignored because the type is shot. “Player 3 to player 1: miss on A2” is 00 10 1 00 01 0. On the wire the bits could be adjacent; both programs know the field boundaries from the protocol.

This design reveals tradeoffs. A fixed ten-bit message is simple to parse but spends one unused bit on every shot. A variable-length design could save that bit, but then it needs another way to determine where the message ends. The protocol also needs a human rule saying that a result should match an earlier shot. A clever bit layout is not yet a complete interaction.

The internet faces the same problems at much larger scale: identifying endpoints, separating fields, choosing meanings, and recovering when expectations are not met.

Layers keep one agreement manageable

The internet is not one enormous protocol that controls radio signals, routing, reliability, and web pages at once. It is a stack of layers. Each layer provides a service to the layer above and uses the layer below. This separation lets people improve one part without redesigning everything.

A simplified four-layer TCP/IP model
LayerQuestion it answersExamples
ApplicationWhat do programs request and reply?HTTP for web resources, DNS for name lookups, email protocols
TransportWhich program should receive the data, and what delivery behavior does the application need?TCP, UDP, ports
InternetWhich host or network should receive this packet across interconnected networks?IP addresses and routing
LinkHow does a packet cross one local link?Wi-Fi, Ethernet, cellular connections; underneath them, radio, copper, or fiber

Layering is an abstraction. A browser can request a page without knowing whether the next link is Wi-Fi or Ethernet. A router can forward an IP packet without understanding whether its payload is a poem, a bank transfer, or part of a video. The lower details still matter, but most software does not have to solve every problem at once.

Encapsulation: messages inside messages

As data moves down the stack, each layer adds its own control information, usually a header. This wrapping is called encapsulation.

  1. The application creates a web request such as “send me the home page.”
  2. TCP adds transport information including source and destination ports and sequence information.
  3. IP adds source and destination IP addresses.
  4. The local-link technology wraps the IP packet for its next hop and carries it as signals.

At the destination, software processes the wrappers in reverse. Link information gets the packet across the final local connection; IP identifies the host; TCP delivers ordered data to the right program; the web server interprets the HTTP request. Each layer reads the part it understands.

A postal analogy has similar layers: a sentence appears inside a card, the card inside an addressed envelope, and the envelope inside a mail sack assigned to a truck. The truck driver need not interpret the sentence. No analogy is exact, but this one captures why several kinds of addressing can appear around one message.

IP addresses identify network interfaces

An IP address is a numeric identifier used to route packets. An IPv4 address contains 32 bits and is usually shown as four decimal values, for example 203.0.113.25. IPv4 provides about 4.3 billion possible bit patterns, far fewer than the number of devices people now connect. IPv6 uses 128 bits and is written in hexadecimal, for example 2001:db8::25, providing an enormously larger address space.

The simple phrase “every device has one unique address” hides important details:

  • A device can have several interfaces and addresses: Wi-Fi, cellular, and temporary IPv6 addresses, for example.
  • An address can change when a device reconnects. This is a dynamic address.
  • Home devices often use reusable private IPv4 addresses such as 192.168.1.20. The router uses network address translation, or NAT, so many devices share one public IPv4 address.
  • One server name can lead to several IP addresses, and many sites can share infrastructure behind one address.

An address identifies a place to deliver packets at a particular time, not a human identity. Investigators and companies can combine an IP address with time, account records, cookies, and provider logs to make inferences, but “this address did it” is not automatically the same as “this person did it.” A household, library, workplace, VPN, or cellular carrier may have many people behind one public address.

Ports identify programs

Reaching the correct device is not enough. Your laptop may be browsing the web, synchronizing files, and joining a game at the same time. A port number helps a transport protocol deliver incoming data to the correct program or service.

If an IP address is like an apartment building's street address, a port is like an apartment number. The analogy is imperfect—ports are software identifiers, not physical rooms—but it explains the two-stage delivery. Common conventions associate HTTP with port 80 and HTTPS with port 443. A client also uses a temporary source port so replies return to the right conversation.

The combination of protocol, IP address, and port identifies a communication endpoint more precisely than an IP address alone. Firewalls can allow or block traffic partly by protocol and port, though modern applications and encryption make the real policy more complicated.

DNS turns names into routing information

People prefer names such as pcc.edu; IP routes packets using numeric addresses. The Domain Name System, or DNS, is a distributed database that connects names to records, including IP addresses. It is often called the internet's phone book, but it behaves more like a hierarchy of delegated directories with extensive caching.

When you request www.example.com, a simplified lookup works like this:

  1. Your device asks a recursive resolver, often operated by an ISP, institution, or chosen DNS service. The resolver first checks its cache.
  2. If necessary, the resolver asks the DNS root system where to find information about the .com top-level domain.
  3. A .com name server points toward the authoritative name servers for example.com.
  4. An authoritative server supplies the requested record for www.example.com.
  5. The resolver returns the result to your device and caches it for a stated period so it need not repeat every step immediately.

DNS separates a stable human-facing name from changing infrastructure. A site can move to a new host and update its DNS records without teaching every visitor a new name. It also creates dependencies: a perfectly healthy web server can seem absent if the needed DNS records or resolver fail.

Names and addresses create points of power

A domain is not merely a label discovered in nature. A registrant obtains it through a registrar; a registry manages its top-level domain; and ICANN coordinates the global system of unique domain names, address allocation, and protocol parameters with other organizations. Control of a domain can be disputed, suspended, transferred, or lost when a registration expires.

DNS can also become a control point. A school or government can configure resolvers to refuse an answer or return a different one. Traditional DNS queries may be visible to the network carrying them, although encrypted DNS protocols can protect queries on part of the path. Blocking DNS does not remove a site's server from the internet, and changing resolvers may sometimes bypass a block, but other blocking methods can operate at other layers.

The ICANN explanation of DNS and DNSSEC traces a lookup in more detail. The ICANN overview explains its limited coordination role; ICANN does not own the internet or generally decide what content belongs on it.

Open specifications let strangers cooperate

Internet protocols are published so independent implementers can build compatible software. Many core specifications appear as Requests for Comments, or RFCs. Despite the modest name, an RFC can be a stable technical standard: RFC 8200 specifies IPv6, RFC 9293 specifies TCP, and RFC 1034 describes DNS concepts.

Openness does not mean every person can easily participate. Standards discussions require time, technical background, language access, and confidence in unfamiliar institutions. An open document also does not force a company to implement it well. We should value interoperability while still asking whose needs were represented when the agreement was made.

Everyday life and social impact: identifiers are not people

A school might block a harmful domain, an employer might log connections for security, or a rights holder might identify an IP address exchanging a file. Each action uses real technical evidence, but the evidence has limits.

  • Who benefits? Shared addresses, ports, names, and protocols let independently written programs find and communicate with one another.
  • Who might be harmed? A whole household or community can be blamed or blocked because people treat a shared address as one person. DNS filtering can protect users, but it can also hide health information, journalism, or political speech.
  • Who decides? Standards groups define formats; ICANN and related organizations coordinate unique identifiers; registries and registrars administer domains; network operators configure resolvers and filters; courts and governments create legal obligations.

Technical precision supports fairer decisions. Before treating an identifier as proof, ask what it actually identifies, at what time, and what additional evidence connects it to a person or action.

Try it: decode, diagnose, and revise

  1. Decode 00 10 1 00 01 0 using the Battleship table.
  2. The message 10 00 0 00 01 0 receives no reply. Name one possible failure or ambiguity the current game protocol does not handle.
  3. A browser reports that example.org cannot be found, but its server answers when reached by a known IP address. Which system is the strongest suspect, and why?
  4. Explain why a public IP address in a log may not uniquely identify one device or one person.
Check your reasoning
  1. Player 3 sends player 1 a result: the shot at A2 was a miss.
  2. The protocol has no message ID, acknowledgment, timeout, or retry rule. The shot or reply could be lost, or the responder may not know which earlier shot a late result matches.
  3. DNS is the strongest suspect because routing to the server's numeric address works while translating the name fails.
  4. The address may be dynamic or shared through NAT, a carrier, public Wi-Fi, a workplace, or a VPN; time and other records are needed.

Connection to the Week 2 assignment

When you trace a web request through the four layers, name the job each layer performs rather than treating TCP/IP as one mystery step. Then look for the failed agreement: Was the name not resolved, the route unavailable, the reliable connection interrupted, or the application unable to respond?

Lesson takeaway

Protocols turn bits into coordinated action. Layers separate problems; encapsulation wraps application data in transport, internet, and link information. IP addresses help route to interfaces, ports distinguish programs, and DNS connects names to records. These identifiers enable an open network, but they also create places where people can observe, misidentify, block, or govern communication.
