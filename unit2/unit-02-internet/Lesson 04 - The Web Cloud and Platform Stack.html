Lesson 4: The Web, Cloud, and Platform Stack

Big question

What happens between clicking a link and seeing a page, and why can a distributed internet still leave many people dependent on the same few companies?

By the end of this lesson, you should be able to trace an HTTPS request and response, explain what encryption protects and what it does not, distinguish a web server from a cloud provider, CDN, and platform, and evaluate convenience, concentration, correlated failure, and personal publishing together.

The web is one service built on the internet

The World Wide Web is a system of linked resources requested over the internet. A browser retrieves a page, reads its HTML, and may make additional requests for style sheets, images, fonts, scripts, audio, or data. Email, multiplayer games, video calls, and file synchronization also use internet protocols, but they are not simply “the web.”

The web became powerful partly because its basic pieces were general:

  • A URL identifies a resource.
  • HTTP defines requests and responses.
  • HTML describes documents with headings, paragraphs, links, images, and other elements.
  • A browser can retrieve and present resources from independently operated servers.

A small organization does not need every browser company to approve its page. If it operates a reachable server and follows shared standards, a person can enter its URL or follow a link. That low-friction ability to publish and connect is one of the web's most important social properties.

Read a URL as a set of instructions

Consider https://example.org/classes/week2.html.

A URL can contain a port, query parameters, and a fragment too. The important distinction is that the host name helps reach a service while the path asks the application for something within it. With HTTPS, intermediaries normally cannot read the full path or page contents, although the destination and other metadata can still reveal information.

One click, many protocols

Suppose you open https://example.org/classes/week2.html. A simplified trace is:

  1. Browser parses the URL. It recognizes HTTPS, the host name, and the resource path.
  2. DNS lookup. Your device obtains one or more IP addresses associated with example.org, often from a resolver's cache.
  3. Route and transport. Packets travel through local and provider networks. The browser establishes a transport connection to the service, usually using port 443.
  4. TLS setup. The client and server negotiate encryption and the browser validates a certificate connecting the service to the requested host name.
  5. HTTP request. Inside the encrypted connection, the browser asks for /classes/week2.html.
  6. HTTP response. The server returns a status, descriptive headers, and a body containing HTML or an error explanation.
  7. Rendering and more requests. The browser parses the HTML and may request the page's CSS, images, scripts, and data.

Each step can fail differently. “Name not found” suggests DNS. A certificate warning suggests a problem validating the secure identity or connection. A 404 Not Found response proves the browser reached a web server, but that server did not find the requested path. A 500-series response usually means the server or an upstream service encountered a problem.

HTTP is a request-and-response protocol

An HTTP message is text-like structured data, though modern versions may encode it efficiently on the wire. A conceptual request might be:

GET /classes/week2.html HTTP/1.1
Host: example.org
Accept: text/html

GET is the method, the path identifies a resource, and headers provide more information. The response might begin:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html lang="en"> ...

200 OK is a status. Content-Type tells the browser how to interpret the body. The blank line separates headers from content. A link can therefore trigger a chain of layered agreements: DNS to find an address, IP to route packets, TCP or another transport to carry an exchange, TLS to protect it, HTTP to request the resource, and HTML to describe the page.

RFC 9110, HTTP Semantics, is the formal specification. You are not expected to read it all. Opening it is useful evidence that the familiar act of loading a page rests on a public, precise agreement rather than a browser company's secret language.

What HTTPS protects

HTTPS is HTTP carried inside Transport Layer Security, or TLS. It mainly provides three protections while data is in transit:

  • Confidentiality: an ordinary intermediary cannot read the request and response contents.
  • Integrity: tampering in transit can be detected.
  • Authentication: certificates help the browser verify that it established the connection for the requested domain rather than an impostor on the network.

Without HTTPS, someone sharing a public network or operating an intermediate network could read or alter an HTTP page, including passwords sent through it. HTTPS is therefore essential, not a decorative padlock.

But the padlock does not mean “this site is honest” or “nobody can see anything.” A malicious site can obtain a valid certificate for its own domain. The site itself receives the content you send and can log it. Malware on your device can see data before encryption. An employer or school that manages a device may install a trusted inspection system. Networks still need addressing and timing information to carry packets, and DNS may reveal the requested name unless an encrypted DNS method is used. Encryption protects particular links and endpoints; it does not erase every form of observation or make a site's business practices trustworthy.

A server, a host, and a cloud are different

A web server is software that responds to web requests. That software must run on computing hardware somewhere. A person could run it on a small computer at home, rent space from a web-hosting company, or rent computing resources from a cloud provider.

Cloud computing lets an organization request servers, databases, storage, and other services without owning the physical machines. The provider pools hardware in data centers and gives customers software-controlled access. This can turn a large up-front purchase into flexible rental, make backups and global deployment easier, and let a small team serve many users.

“In the cloud” does not explain where data is, who can access it, or what happens during an outage. It means the physical and operational details are being handled elsewhere under a contract. The computers still occupy buildings, consume electricity, use cooling systems, fail, and belong to organizations with policies and legal obligations.

CDNs put copies closer to readers

A content delivery network, or CDN, operates servers in many locations and can store cached copies of frequently requested resources near users. If a Portland reader requests an image from a European newspaper, a nearby CDN server may already have a valid copy. That reduces latency and work for the newspaper's origin server.

CDNs can also absorb traffic spikes and attacks that would overwhelm a small server. In that sense, a CDN is distributed infrastructure that can improve everyday resilience. At the same time, many unrelated sites may depend on the same CDN software and control systems. A failure in that shared layer can become a correlated failure: services that look independent to users fail together because of a hidden common dependency.

Platforms centralize participation

A platform hosts interactions among many participants: a social network, video service, app store, marketplace, or learning-management system. Platforms solve hard problems. They supply accounts, storage, discovery, moderation tools, audiences, payments, security staff, and mobile apps. Joining an existing community is easier than operating every part yourself.

The tradeoff is not simply “distributed good, centralized bad.” Centralized services can have excellent engineering and fewer routine failures than thousands of neglected servers. They can fund accessibility teams and respond to abuse. Yet dependence concentrates consequences:

  • One policy change can affect millions of creators or learners.
  • One account suspension can remove a person's audience and archive together.
  • One login or cloud failure can interrupt many otherwise unrelated activities.
  • Moving away can be difficult when contacts, history, and data are not portable.

The useful question is not “Is centralization always wrong?” It is “Which dependencies have we chosen, what do they provide, and what alternatives exist when they fail or misuse their power?”

A real shared-dependency failure

On June 8, 2021, the CDN provider Fastly experienced a global outage. According to Fastly's incident summary, a software bug introduced in May was triggered by a valid customer configuration change. Eighty-five percent of its network returned errors; within 49 minutes, 95 percent was operating normally again.

The technically interesting point is not that one company made an error—every complex system eventually does. It is that many separate sites became unavailable together because they shared an intermediary. The underlying packet network still connected users and servers, but a higher-level dependency failed.

Two different resilience patterns
PatternLikely everyday experienceFailure shape
Many small independent hostsUneven maintenance, performance, and securityMore separate failures, usually affecting fewer sites at once
Many sites share a well-run cloud or CDNOften fast, convenient, and professionally maintainedPotentially fewer failures, but a shared failure can affect many sites together

Good engineering can combine approaches: multiple regions or providers, independent status communication, backups that have actually been tested, and simple fallback services. Those measures cost money and staff attention. Resilience is a design and budget decision.

The infrastructure has local costs

Cloud and platform services feel remote to users, but their data centers draw electricity, use hardware made from mined and manufactured materials, and often use water directly or indirectly for cooling and power generation. Benefits and burdens may fall in different places: global users gain a fast service while a particular community hosts transmission lines, generators, construction, noise, water demand, and tax arrangements.

A December 2024 U.S. Department of Energy summary reported that data centers used about 4.4 percent of U.S. electricity in 2023 and presented a wide projected range of 6.7 to 12 percent by 2028. These are dated estimates, not timeless facts; demand, efficiency, and the electricity mix can change quickly. The lasting lesson is to include material infrastructure and affected communities when evaluating a seemingly virtual service.

The web was a choice—and can still be yours

The web is not the only possible way to organize networked information. Earlier systems such as Gopher organized documents into hierarchical menus. The newer Gemini protocol intentionally supports a smaller set of features than the modern web. Neither alternative is “the internet before it got good.” Each emphasizes different values: simplicity, author control, discoverability, interactivity, security, or commercial capability.

The modern web supports remarkable applications, but a page does not have to be an application or a business. It can be a recipe, a poem, neighborhood history, a class project, a fan page, or links collected for friends. HTML lets people make durable documents that link to one another. Personal sites provide room to choose structure and voice instead of fitting every idea into the same profile and feed.

There are still dependencies. A Neocities page relies on Neocities hosting, DNS, browsers, internet access, and the continued existence of open standards. Yet making the page changes your role. You choose the headings, links, words, image description, and public address. The Week 2 activity is therefore part of the lesson, not a decorative coding exercise: it demonstrates that the web can be a medium people make together, not only a set of products delivered to them.

Everyday life and social impact: convenience, voice, and dependence

  • Who benefits? Cloud services and CDNs let small teams offer reliable global services. Platforms help people find communities and audiences. Open web standards let people publish without permission from a single platform.
  • Who might be harmed? A shared outage can interrupt school, work, health, and public information at once. A platform's rules or ranking system can make a community invisible. Data-center costs may burden a host community. People without appropriate devices or accessible tools may be unable to publish even when hosting is free.
  • Who decides? Standards communities define the web's shared languages; hosting and cloud companies control infrastructure; platform owners set product and moderation rules; site authors choose what they publish; communities and governments make decisions about utilities, land, labor, competition, and rights.

Technical architecture does not settle these questions, but it changes which choices are possible and who has leverage.

Try it: put a web request in order

Put these events in a reasonable order, then identify the layer or organization most closely associated with each:

  • The browser validates a certificate and establishes encrypted communication.
  • A CDN returns a cached copy of an image.
  • DNS returns an IP address for the host name.
  • The browser renders HTML and discovers an image URL.
  • Routers forward packets toward the destination network.
  • The web server returns an HTTP response containing HTML.
  • The browser sends an HTTP request for the page path.

Then answer: What can the destination site learn? What can an ordinary ISP on the route learn when HTTPS is used? What changes if the site itself records your account and every page you view?

Check your reasoning

One reasonable order is DNS; routing and transport; TLS setup; HTTP page request; HTTP HTML response; browser rendering; a new image request answered from a CDN cache. Some low-level packet forwarding occurs throughout, so the list is a conceptual sequence rather than seven isolated moments. The site can receive the requested path, content you submit, IP address, timing, and application identifiers such as cookies. An ordinary ISP carries packets and can see addressing, volume, and timing, but HTTPS normally hides the HTTP path and contents. If the site links requests to an account, transport encryption does not stop the site from building a detailed activity history.

Connection to the Week 2 activity discussion

As you make your Neocities page, use semantic HTML: a real heading for the page title, paragraphs for prose, a meaningful link label, and alt text that communicates an image's purpose. Share the URL and visit classmates' pages. You are creating the exact requestable, linkable resources described in this lesson—and making the web a little less like five identical feeds.

Lesson takeaway

A web page arrives through a stack: URL parsing, DNS, routing, transport, TLS, HTTP, and browser rendering. Cloud providers and CDNs make that experience scalable and often reliable, while shared dependencies create correlated risks and concentrated power. The same web also lets individuals publish and link their own work. Understanding both sides helps us choose convenience without forgetting autonomy, accessibility, or the communities underneath the cloud.
