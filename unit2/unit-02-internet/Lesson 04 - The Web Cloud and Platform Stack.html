Lesson 4: The Web, Cloud, and Platform Stack

Big question

What happens between clicking a link and seeing a page — and why can a distributed internet still leave so many people dependent on the same few companies?

To answer that, we'll follow one click all the way from your browser to a server and back, figure out what that little padlock in your browser actually protects (and what it doesn't), and sort out the difference between a web server, a cloud provider, a CDN, and a platform. Then we'll come back to the question of why so many sites can break at the same time, and what you can do about depending on a few big companies.

The web and the internet

The World Wide Web is a system of pages and files that link to each other, which your browser requests over the internet. When your browser gets a page, it reads the page's HTML, and then it usually fires off more requests for the page's style sheets, images, fonts, scripts, and data. Plenty of other things use the internet too, like email, multiplayer games, and video calls, but they aren't "the web."

Part of what made the web so powerful is that its basic pieces are really simple and general:

  • A URL identifies a resource.
  • HTTP defines requests and responses.
  • HTML describes documents with headings, paragraphs, links, images, and other elements.
  • A browser can retrieve and present resources from independently operated servers.

That means nobody needs permission from a browser company to have a web page. If you run a server people can reach, and you follow the shared standards, anyone can type in your URL or follow a link to you. That ability to publish and connect without asking anyone is one of the most important things about the web, so hold onto it, because we'll come back to it.

Reading a URL

Consider https://example.org/classes/week2.html.

A URL can have a few more pieces too, like a port number or the stuff after a ? or #. But the important split is this: the host name gets you to the right service, and the path asks that service for something specific inside it. With HTTPS, the networks in between normally can't read the path or the page itself, although they can still see which site you're talking to, and when.

One click, many protocols

Suppose you open https://example.org/classes/week2.html. A simplified trace:

  1. Browser parses the URL. It recognizes HTTPS, the host name, and the resource path.
  2. DNS lookup. Your device obtains one or more IP addresses associated with example.org, often from a resolver's cache.
  3. Route and transport. Packets travel through local and provider networks. The browser establishes a transport connection to the service, usually using port 443.
  4. TLS setup. The client and server negotiate encryption, and the browser validates a certificate connecting the service to the requested host name.
  5. HTTP request. Inside the encrypted connection, the browser asks for /classes/week2.html.
  6. HTTP response. The server returns a status, descriptive headers, and a body containing HTML or an error explanation.
  7. Rendering and more requests. The browser parses the HTML and may request the page's CSS, images, scripts, and data.

Each of these steps fails in its own way, which is great news when you're trying to figure out what went wrong. If your browser says it can't find the server's address ("This site can't be reached. The server's IP address could not be found," in Chrome), the DNS lookup failed. A full-page certificate warning ("Your connection is not private") means something went wrong checking that the secure connection really goes to the right site. A 404 Not Found actually tells you a lot of things worked, because you reached the web server! It just doesn't have the page you asked for. And an error in the 500s usually means the server, or some service it depends on, has a problem of its own.

HTTP

An HTTP message looks a lot like structured text, although newer versions of HTTP pack it more efficiently when they actually send it. A request might look like this:

GET /classes/week2.html HTTP/1.1
Host: example.org
Accept: text/html

GET means "send me something," the path says what, and the lines after that (called headers) carry extra information. The response might start like this:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html lang="en"> ...

200 OK is the status, which means everything went fine. Content-Type tells the browser what kind of thing it's getting, and the blank line separates the headers from the actual content. So one click on a link sets off a whole chain of agreements, one inside another: DNS finds an address, IP routes the packets, TCP carries the conversation, TLS protects it, HTTP asks for the page, and HTML describes what the page looks like.

RFC 9110, HTTP Semantics, is the formal specification. Nobody expects you to read the whole thing. But opening it for a minute gives you real evidence: the familiar act of loading a page rests on a public, precise agreement, not on some browser company's secret language.

What HTTPS protects

HTTPS is HTTP carried inside Transport Layer Security, or TLS. While your data is in transit, it mainly provides three protections:

  • Confidentiality: an ordinary intermediary can't read the request and response contents.
  • Integrity: tampering in transit can be detected.
  • Authentication: certificates help the browser verify that it established the connection for the requested domain rather than an impostor on the network.

Without HTTPS, anyone on the same public Wi-Fi as you, or anyone running one of the networks in between, could read or change an HTTP page, including any password you typed into it. That's why it matters whether the padlock is there at all.

It's also why you should take that full-page "Your connection is not private" warning seriously. On public Wi-Fi, like at an airport or a café, the most common cause is fairly harmless: the network wants you to sign in or accept its terms first, and it's trying to show you its sign-in page instead of the site you asked for. But the warning can also mean somebody on the network is pretending to be the site. Your browser can't tell the difference, so don't click past the warning and log in anyway. Find the network's sign-in page first, or switch to cellular data.

But the padlock does not mean "this site is honest," and it doesn't mean "nobody can see anything." A scam site can get a perfectly valid certificate for its own domain! The site itself gets whatever you send it, and can keep a record of it. Malware on your own device can see your data before it ever gets encrypted. If your school or employer manages your device, they might have set it up so they can inspect your traffic. The networks in between still need to see where your packets are going in order to deliver them, and your DNS lookups may reveal which sites you visit unless you're using encrypted DNS. So encryption protects particular parts of the trip, but it doesn't make you invisible, and it can't tell you whether a company deserves your trust.

Servers, hosts, and clouds

A web server is the software that answers web requests, and it has to run on a computer somewhere. You could run it on a little computer at home, rent space from a web-hosting company, or rent computing power from a cloud provider.

Cloud computing lets an organization rent servers, databases, and storage without owning any of the actual machines. The cloud provider fills huge data centers with hardware and rents out pieces of it to customers. So instead of buying a room full of computers up front, a company can rent exactly what it needs, make backups and run copies in other parts of the world more easily, and serve an enormous number of people with a small team.

But "it's in the cloud" doesn't tell you where your data actually is, who can get to it, or what happens when there's an outage. It just means somebody else is handling the physical machines, under a contract. Those computers still sit in real buildings, use electricity, need cooling, break down, and belong to companies with their own rules and legal obligations.

CDNs

A content delivery network, or CDN, runs servers in lots of different places, and keeps cached copies of popular files close to the people asking for them. So if you're in Portland and you open an article from a European newspaper, a CDN server nearby might already have a copy of its images. You wait less, and the newspaper's own server, called the origin server, has less work to do.

CDNs can also soak up sudden floods of traffic, and attacks that would knock a small server right over, so in that way they make the everyday web more reliable. But here's the catch. Lots of sites that have nothing to do with each other might all use the same CDN, and if the CDN breaks, they all break together. That's called a correlated failure: services that look completely separate to you fail at the same time, because of something they were secretly sharing. (When that happens, you'll often see the CDN company's own error page on all of those different sites, which is a big clue.)

Platforms

A platform is a service where lots of people interact, like a video site, an app store, or D2L itself. Platforms solve hard problems for you. If you wanted to run your own video site, you'd need accounts, storage, a way for people to find things, moderators, security staff, and phone apps. Joining a platform that already has all of that (plus an audience!) is far easier than building every piece yourself.

So is it bad that so much runs through a few big companies? It's not that simple. Big services can have excellent engineering, and they often break less than thousands of small servers that nobody's taking care of. They can afford accessibility teams and people to deal with abuse. But when everyone depends on the same few services, the consequences pile up in the same few places:

  • One policy change can affect millions of creators or learners.
  • One account suspension can remove a person's audience and archive together.
  • One login or cloud failure can interrupt many otherwise unrelated activities.
  • Moving away can be difficult when contacts, history, and data are not portable.

So instead of asking whether depending on big companies is good or bad, it's more useful to ask which companies we've chosen to depend on, what we get from them, and what we can do when they fail or misuse their power.

A real shared-dependency failure

On June 8, 2021, the CDN provider Fastly experienced a global outage. According to Fastly's incident summary, a software bug introduced in May was triggered by a valid customer configuration change. Eighty-five percent of its network returned errors; within 49 minutes, 95 percent was operating normally again.

The interesting part isn't that one company made a mistake. Every complicated system eventually does! It's that lots of completely separate sites went down together, because they were all using the same company in the middle. The internet underneath kept carrying packets between people and servers the whole time. What failed was something several layers up that all those sites depended on.

Two different resilience patterns
PatternLikely everyday experienceFailure shape
Many small independent hostsUneven maintenance, performance, and securityMore separate failures, usually affecting fewer sites at once

Sites can protect themselves against this, by using more than one provider or region, keeping a status page somewhere separate, testing their backups, and having a simple fallback version of the site. But all of that costs money and staff time, which is why plenty of sites quite reasonably skip it and accept the risk.

Local costs of infrastructure

Cloud services feel far away when you're using them, but their data centers use electricity, and are built out of hardware made from mined and manufactured materials. They also often use water for cooling, either directly or through the power plants that supply them. And the good and the bad can land in completely different places. People all over the world get a fast service, while one particular town gets the power lines, the generators, the construction, the noise, and the tax deals.

A December 2024 U.S. Department of Energy summary reported that data centers used about 4.4 percent of U.S. electricity in 2023 and presented a wide projected range of 6.7 to 12 percent by 2028. Those are dated estimates, not timeless facts — demand, efficiency, and the electricity mix can all change quickly. What doesn't change is that a “virtual” service is running in real buildings in real places, and somebody lives next to them.

Making your own corner of the web

By the way, the web isn't the only way people have come up with to organize information on the internet. An earlier system called Gopher organized documents into menus inside of menus. A newer one called Gemini deliberately leaves out most of the modern web's features, to keep things simple. Neither one is "the internet before it got good." They just care about different things.

The modern web supports remarkable applications, but a page doesn't have to be an application or a business. It can be a page of your family's recipes, or a list of links you think your friends would like. HTML lets people make durable documents that link to one another, and a personal site gives you room to choose your own structure and voice instead of pouring every idea into the same profile-and-feed mold.

Your own page still depends on other people, of course. A Neocities page relies on Neocities to host it, on DNS, on browsers, on everyone's internet access, and on open standards sticking around. But making the page changes your role. You choose the headings, the links, the words, the image descriptions, and the address. That's the real reason for the Week 2 activity: making a page yourself shows you that the web can be something people make together, and not just a set of products delivered to them.

Everyday life and social impact: convenience, voice, and dependence

Think about where you'd post something you made. Cloud services and CDNs let small teams run reliable services for the whole world, and a platform can hand you a community and an audience on day one. Open web standards mean you can also skip the platform and publish on your own site, without anyone's permission, though then nobody's recommendation system is going to send readers your way.

Who gets hurt when this goes wrong? A shared outage can interrupt school, work, health, and public information all at once. A platform's rules or ranking system can make a whole community invisible. A data center's costs can fall on the town that hosts it. And people without the right devices or accessible tools may not be able to publish at all, even when the hosting is free.

And who decides? Standards groups write the web's shared languages. Hosting and cloud companies control the machines. Platform owners set the rules about what's allowed and what gets shown. Site authors choose what they publish. And communities and governments make decisions about power, land, jobs, competition, and rights. The technology doesn't settle any of that on its own, but it does change who has leverage. A creator with their own site has much more room to push back when a platform changes its rules than a creator whose whole audience lives on that platform.

Try it: put a web request in order

Put these events in a reasonable order, then identify the layer or organization most closely associated with each:

  • The browser validates a certificate and establishes encrypted communication.
  • A CDN returns a cached copy of an image.
  • DNS returns an IP address for the host name.
  • The browser renders HTML and discovers an image URL.
  • Routers forward packets toward the destination network.
  • The web server returns an HTTP response containing HTML.
  • The browser sends an HTTP request for the page path.

Then answer: What can the destination site learn? What can an ordinary ISP on the route learn when HTTPS is used? What changes if the site itself records your account and every page you view?

Check your reasoning

One reasonable order is DNS; routing and transport; TLS setup; HTTP page request; HTTP HTML response; browser rendering; a new image request answered from a CDN cache. Some low-level packet forwarding occurs throughout, so the list is a conceptual sequence rather than seven isolated moments. The site can receive the requested path, content you submit, IP address, timing, and application identifiers such as cookies. An ordinary ISP carries packets and can see addressing, volume, and timing, but HTTPS normally hides the HTTP path and contents. If the site links requests to an account, transport encryption does not stop the site from building a detailed activity history.

Connection to the Week 2 activity discussion

As you make your Neocities page, use HTML for what it means, not just for how it looks: a real heading for the page title, paragraphs for your writing, link text that says where the link goes, and alt text that explains what an image is there for. Then share your URL and visit your classmates' pages. You're making exactly the kind of linkable pages this lesson talked about, and making the web a little less like five identical feeds.

Lesson takeaway

Every web page reaches you through a stack of steps: reading the URL, looking up the name, routing the packets, setting up the connection, securing it, asking for the page, and drawing it on your screen. Cloud providers and CDNs make all of that fast and usually very reliable, but when lots of sites share them, they can fail together, and the companies running them end up with a lot of power. The same web still lets you publish and link your own work, so most of us end up using both: the big services because they're convenient, and our own corners of the web because there we're the ones who decide.
