Lesson 4: The Web, Cloud, and Platform Stack

Big question

What happens between clicking a link and seeing a page — and why can a distributed internet still leave so many people dependent on the same few companies?

The plan for this lesson: trace an HTTPS request and response, sort out what encryption protects and what it doesn't, distinguish a web server from a cloud provider, CDN, and platform, and weigh convenience, concentration, correlated failure, and personal publishing all at once.

The web is one service built on the internet

The World Wide Web is a system of linked resources requested over the internet. A browser retrieves a page, reads its HTML, and may fire off more requests for style sheets, images, fonts, scripts, audio, or data. Email, multiplayer games, video calls, and file synchronization also use internet protocols, but they aren't simply “the web.”

The web became powerful partly because its basic pieces were so general:

  • A URL identifies a resource.
  • HTTP defines requests and responses.
  • HTML describes documents with headings, paragraphs, links, images, and other elements.
  • A browser can retrieve and present resources from independently operated servers.

A small organization doesn't need any browser company's approval to have a page. If it runs a reachable server and follows the shared standards, a person can enter its URL or follow a link. That low-friction ability to publish and connect is one of the web's most important social properties — hold onto it, because we'll come back to it.

Read a URL as a set of instructions

Consider https://example.org/classes/week2.html.

A URL can also carry a port, query parameters, and a fragment. The distinction worth remembering is that the host name gets you to a service, while the path asks that service's application for something inside it. With HTTPS, intermediaries normally can't read the full path or the page contents — though the destination and other metadata can still reveal plenty.

One click, many protocols

Suppose you open https://example.org/classes/week2.html. A simplified trace:

  1. Browser parses the URL. It recognizes HTTPS, the host name, and the resource path.
  2. DNS lookup. Your device obtains one or more IP addresses associated with example.org, often from a resolver's cache.
  3. Route and transport. Packets travel through local and provider networks. The browser establishes a transport connection to the service, usually using port 443.
  4. TLS setup. The client and server negotiate encryption, and the browser validates a certificate connecting the service to the requested host name.
  5. HTTP request. Inside the encrypted connection, the browser asks for /classes/week2.html.
  6. HTTP response. The server returns a status, descriptive headers, and a body containing HTML or an error explanation.
  7. Rendering and more requests. The browser parses the HTML and may request the page's CSS, images, scripts, and data.

Each step fails differently, which is great news for diagnosis. “Name not found” suggests DNS. A certificate warning means trouble validating the secure identity or connection. A 404 Not Found actually proves you reached a web server — it just didn't find the path you asked for. A 500-series response usually means the server or an upstream service hit a problem of its own.

HTTP is a request-and-response protocol

An HTTP message is text-like structured data, though modern versions may encode it efficiently on the wire. A conceptual request might be:

GET /classes/week2.html HTTP/1.1
Host: example.org
Accept: text/html

GET is the method, the path identifies a resource, and headers carry extra information. The response might begin:

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html lang="en"> ...

200 OK is a status. Content-Type tells the browser how to interpret the body. The blank line separates headers from content. So one click on a link sets off a chain of layered agreements: DNS to find an address, IP to route packets, TCP or another transport to carry the exchange, TLS to protect it, HTTP to request the resource, and HTML to describe the page.

RFC 9110, HTTP Semantics, is the formal specification. Nobody expects you to read the whole thing. But opening it for a minute gives you real evidence: the familiar act of loading a page rests on a public, precise agreement, not on some browser company's secret language.

What HTTPS protects

HTTPS is HTTP carried inside Transport Layer Security, or TLS. While your data is in transit, it mainly provides three protections:

  • Confidentiality: an ordinary intermediary can't read the request and response contents.
  • Integrity: tampering in transit can be detected.
  • Authentication: certificates help the browser verify that it established the connection for the requested domain rather than an impostor on the network.

Without HTTPS, anyone sharing a public network — or operating an intermediate network — could read or alter an HTTP page, including passwords sent through it. HTTPS is essential, not a decorative padlock.

But the padlock does not mean “this site is honest,” and it doesn't mean “nobody can see anything.” A malicious site can obtain a perfectly valid certificate for its own domain. The site itself receives whatever content you send and can log it. Malware on your device sees data before it's encrypted. An employer or school that manages a device may have installed a trusted inspection system. Networks still need addressing and timing information just to carry packets, and DNS may reveal the requested name unless an encrypted DNS method is used. Encryption protects particular links and endpoints; it doesn't erase every form of observation, and it says nothing about whether a site's business practices deserve your trust.

A server, a host, and a cloud are different

A web server is software that answers web requests. That software has to run on computing hardware somewhere. A person could run it on a small computer at home, rent space from a web-hosting company, or rent computing resources from a cloud provider.

Cloud computing lets an organization request servers, databases, storage, and other services without owning the physical machines. The provider pools hardware in data centers and hands customers software-controlled access to it. That can turn a large up-front purchase into flexible rental, make backups and global deployment easier, and let a small team serve an enormous number of users.

What “in the cloud” does not tell you: where your data is, who can access it, or what happens during an outage. It means the physical and operational details are being handled elsewhere, under a contract. The computers still occupy buildings, draw electricity, need cooling, break down, and belong to organizations with policies and legal obligations.

CDNs put copies closer to readers

A content delivery network, or CDN, operates servers in many locations and can store cached copies of frequently requested resources near users. If a reader in Portland requests an image from a European newspaper, a nearby CDN server may already have a valid copy — less waiting for the reader, less work for the newspaper's origin server.

CDNs can also absorb traffic spikes and attacks that would flatten a small server. In that sense a CDN is distributed infrastructure that can improve everyday resilience. At the same time, many unrelated sites may depend on the same CDN software and control systems, and a failure in that shared layer can become a correlated failure: services that look independent to users fail together because of a hidden common dependency.

Platforms centralize participation

The word platform covers services that host interactions among many participants: a social network, a video service, an app store, a marketplace, a learning-management system. Platforms solve hard problems — they supply accounts, storage, discovery, moderation tools, audiences, payments, security staff, and mobile apps. Joining an existing community is far easier than operating every part yourself.

The tradeoff isn't simply “distributed good, centralized bad.” Centralized services can have excellent engineering and fewer routine failures than thousands of neglected servers; they can fund accessibility teams and respond to abuse. But dependence concentrates consequences:

  • One policy change can affect millions of creators or learners.
  • One account suspension can remove a person's audience and archive together.
  • One login or cloud failure can interrupt many otherwise unrelated activities.
  • Moving away can be difficult when contacts, history, and data are not portable.

The useful question, then, isn't “Is centralization always wrong?” It's “Which dependencies have we chosen, what do they give us, and what are our options when they fail or misuse their power?”

A real shared-dependency failure

On June 8, 2021, the CDN provider Fastly experienced a global outage. According to Fastly's incident summary, a software bug introduced in May was triggered by a valid customer configuration change. Eighty-five percent of its network returned errors; within 49 minutes, 95 percent was operating normally again.

The interesting part isn't that one company made an error — every complex system eventually does. It's that many separate sites went dark together because they shared an intermediary. The underlying packet network kept connecting users and servers the whole time; what failed was a dependency several layers up.

Two different resilience patterns
PatternLikely everyday experienceFailure shape
Many small independent hostsUneven maintenance, performance, and securityMore separate failures, usually affecting fewer sites at once
Many sites share a well-run cloud or CDNOften fast, convenient, and professionally maintainedPotentially fewer failures, but a shared failure can affect many sites together

Good engineering can mix the approaches: multiple regions or providers, independent status communication, backups that have actually been tested, simple fallback services. All of that costs money and staff attention. Resilience is a design decision and a budget line.

The infrastructure has local costs

Cloud and platform services feel remote to their users, but their data centers draw electricity, use hardware made from mined and manufactured materials, and often use water — directly or indirectly — for cooling and power generation. And the benefits and burdens can land in different places: global users get a fast service while one particular community hosts the transmission lines, generators, construction, noise, water demand, and tax arrangements.

A December 2024 U.S. Department of Energy summary reported that data centers used about 4.4 percent of U.S. electricity in 2023 and presented a wide projected range of 6.7 to 12 percent by 2028. Those are dated estimates, not timeless facts — demand, efficiency, and the electricity mix can all change quickly. The lasting lesson is to include material infrastructure and affected communities when you evaluate a seemingly virtual service.

The web was a choice—and can still be yours

The web isn't the only possible way to organize networked information. Earlier systems such as Gopher organized documents into hierarchical menus. The newer Gemini protocol intentionally supports a smaller set of features than the modern web. Neither one is “the internet before it got good” — each emphasizes different values: simplicity, author control, discoverability, interactivity, security, commercial capability, &c.

The modern web supports remarkable applications, but a page doesn't have to be an application or a business. It can be a recipe, a poem, neighborhood history, a class project, a fan page, links collected for friends. HTML lets people make durable documents that link to one another, and a personal site gives you room to choose your own structure and voice instead of pouring every idea into the same profile-and-feed mold.

There are still dependencies — a Neocities page relies on Neocities hosting, DNS, browsers, internet access, and the continued existence of open standards. But making the page changes your role. You choose the headings, the links, the words, the image descriptions, the public address. The Week 2 activity isn't a decorative coding exercise; it demonstrates that the web can be a medium people make together, not only a set of products delivered to them.

Everyday life and social impact: convenience, voice, and dependence

  • Who benefits? Cloud services and CDNs let small teams offer reliable global services. Platforms help people find communities and audiences. Open web standards let people publish without permission from a single platform.
  • Who might be harmed? A shared outage can interrupt school, work, health, and public information at once. A platform's rules or ranking system can make a community invisible. Data-center costs may burden a host community. People without appropriate devices or accessible tools may be unable to publish even when the hosting is free.
  • Who decides? Standards communities define the web's shared languages; hosting and cloud companies control infrastructure; platform owners set product and moderation rules; site authors choose what they publish; communities and governments make decisions about utilities, land, labor, competition, and rights.

Technical architecture doesn't settle these questions. It does change which choices are possible — and who has leverage.

Try it: put a web request in order

Put these events in a reasonable order, then identify the layer or organization most closely associated with each:

  • The browser validates a certificate and establishes encrypted communication.
  • A CDN returns a cached copy of an image.
  • DNS returns an IP address for the host name.
  • The browser renders HTML and discovers an image URL.
  • Routers forward packets toward the destination network.
  • The web server returns an HTTP response containing HTML.
  • The browser sends an HTTP request for the page path.

Then answer: What can the destination site learn? What can an ordinary ISP on the route learn when HTTPS is used? What changes if the site itself records your account and every page you view?

Check your reasoning

One reasonable order is DNS; routing and transport; TLS setup; HTTP page request; HTTP HTML response; browser rendering; a new image request answered from a CDN cache. Some low-level packet forwarding occurs throughout, so the list is a conceptual sequence rather than seven isolated moments. The site can receive the requested path, content you submit, IP address, timing, and application identifiers such as cookies. An ordinary ISP carries packets and can see addressing, volume, and timing, but HTTPS normally hides the HTTP path and contents. If the site links requests to an account, transport encryption does not stop the site from building a detailed activity history.

Connection to the Week 2 activity discussion

As you make your Neocities page, use semantic HTML: a real heading for the page title, paragraphs for prose, a link label that means something, and alt text that communicates an image's purpose. Share the URL and visit your classmates' pages. You're creating the exact requestable, linkable resources this lesson described — and making the web a little less like five identical feeds.

Lesson takeaway

A web page arrives through a stack: URL parsing, DNS, routing, transport, TLS, HTTP, and browser rendering. Cloud providers and CDNs make that experience scalable and often very reliable, while shared dependencies create correlated risks and concentrated power. The same web still lets individuals publish and link their own work. Holding both sides at once is the skill: choose convenience without forgetting autonomy, accessibility, or the communities underneath the cloud.
