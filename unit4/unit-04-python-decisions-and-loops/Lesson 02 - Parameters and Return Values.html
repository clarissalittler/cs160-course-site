Lesson 2 - Parameters and Return Values

Here's what you'll be able to do once you've worked through this lesson:

  • Define and call a function that accepts parameters.
  • Distinguish a parameter in a definition from an argument in a call.
  • Use return when a result should be stored or used in another expression.
  • Write a plain-language contract describing a function's expected inputs and promised result.

Parameters

Our scene-transition function has a problem: it always goes "across town." We could write transition_to_library(), transition_to_moon(), &c., but that's a whole pile of functions that are identical except for two words. What we want is to keep the part that stays the same and let the caller fill in the part that changes:

def scene_transition(place):
    print("[music rises]")
    print(f"NARRATOR: Meanwhile, at {place}...")
    print("[music fades]")

scene_transition("the library")
scene_transition("the bus stop")
scene_transition("a very small moon")

place is a parameter: a name inside the definition that stands in for information the caller will provide. "the library" is an argument: the specific value one particular call hands over. During that call place refers to "the library"; on the next call it refers to "the bus stop". The two words are fussy, and plenty of working programmers mix them up, but it helps to have one word for the blank and another for what fills it.

More than one parameter

def announce_event(event_name, location, start_time):
    print(f"{event_name}")
    print(f"Location: {location}")
    print(f"Starts: {start_time}")

announce_event("Repair café", "Library room 2", "Saturday at 1 PM")

Arguments match up with parameters by position: first with first, second with second, and so on. Python doesn't know that "Library room 2" is a place and "Saturday at 1 PM" is a time; it only knows which one came second and which came third. So the call has to supply the right number of values in the right order, and descriptive parameter names are your best defense against mixing them up.

And of course you can call a function from inside a loop:

for copy_number in range(1, 4):
    announce_event("Repair café", "Library room 2", f"Session {copy_number}")

Local names

Parameters, and any variables you create inside a function, are local to that function:

def show_double(number):
    doubled = number * 2
    print(doubled)

show_double(6)
print(doubled)  # NameError: doubled is not defined here

Why would Python be set up this way? It seems restrictive at first, but think about what the alternative would mean: every variable in every function would be visible everywhere, and a function you wrote in March could accidentally overwrite a variable you wrote in May just because they happened to share a name. Keeping names local means a function can do its work in its own little workspace, and each call gets a fresh one.

Printing vs. returning

This is another funny thing to keep in mind: a function that prints is talking to a user. A function that returns a value is talking to the rest of the program:

def calculate_tip(meal_cost, tip_rate):
    tip = meal_cost * tip_rate
    return tip

suggested_tip = calculate_tip(30.00, 0.18)
total = 30.00 + suggested_tip
print(f"Tip: ${suggested_tip:.2f}")
print(f"Total: ${total:.2f}")

When Python reaches return tip, the function stops and the whole call, calculate_tip(30.00, 0.18), turns into the value 5.4. It's as if that expression were crossed out and the number written in its place. That's why you can store the result in a variable, or add it to something, or hand it to print().

Compare these two:

def print_double(number):
    print(number * 2)

def calculate_double(number):
    return number * 2

print_double(5)                # displays 10
result = calculate_double(5)  # stores 10
print(result + 1)              # displays 11

Try writing result = print_double(5) and then print(result + 1). You'll see 10 printed, and then a TypeError, because print_double gives nothing back for result to hold. The question to ask is: who needs this result next, a person looking at the screen, or more code?

A function contract

A contract is a descriptive promise about how the function should behave: here's what you give this function, and here's what it will do or give back. For example:

calculate_tip(meal_cost, tip_rate)

  • expects two numbers: a dollar amount and a rate written as a decimal,
  • returns the dollar amount of the tip,
  • does not print or ask the user for input.

So that last line tells us something fun: because the function takes parameters, runs, and never stops to ask the user anything, we can test it by just calling it:

print(calculate_tip(100, 0.20))  # expected: 20.0
print(calculate_tip(0, 0.20))    # expected: 0.0
print(calculate_tip(25, 0))      # expected: 0.0

These are simple, albeit useful, little tests. Normal case, zero cost, zero rate. If the function also asked for input, we'd have to sit there typing values every time we wanted to check it. Keeping "talk to the user" and "do the math" in separate functions makes both of them easier to get right.

What parameters allow

Choosing a function's parameters is a design decision and it constrains more about how people use your code than you might think! If a drawing function takes a color and a size, then color and size are what callers get to change, and nothing else. If a profile function takes "first name" and "last name," it has assumed everyone's name comes in two pieces. If a transit estimator takes a driving speed, it has decided that every other way of getting around isn't part of the picture.

What happens when someone with one name, or three, runs into that profile function? A parameter list is a small statement about which differences the program expects to exist. So when you write one, it helps to ask yourself whether the fixed part really needs to be fixed, whether the caller has enough control, and whether a default favors one kind of user over another without saying so.

Try it: Build and test a reusable function. Choose one:

  • a text function that prints a scene or a quiz question with changeable details;
  • a drawing function that changes a shape's size or turn angle; or
  • a calculation function that returns a converted measurement or a price.

Give it at least one parameter, call it with three different arguments, and write its contract. If it computes a value, return that value and use it after the call.
