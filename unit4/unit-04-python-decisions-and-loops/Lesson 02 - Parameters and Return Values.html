Lesson 2 - Parameters and Return Values

Here's what you'll be able to do once you've worked through this lesson:

  • Define and call a function that accepts parameters.
  • Distinguish a parameter in a definition from an argument in a call.
  • Use return when a result should be stored or used in another expression.
  • Write a plain-language contract describing a function's expected inputs and promised result.

Make the useful parts changeable

Our scene-transition function has a limitation: it always goes to the same place. We could write transition_to_library(), transition_to_moon(), &c. — a whole pile of nearly identical functions. The better abstraction separates the stable pattern from the one piece of information that changes:

def scene_transition(place):
    print("[music rises]")
    print(f"NARRATOR: Meanwhile, at {place}...")
    print("[music fades]")

scene_transition("the library")
scene_transition("the bus stop")
scene_transition("a very small moon")

place is a parameter: a local name in the definition that stands in for information the caller will provide. "the library" is an argument: the particular value one call supplies. During that call, place temporarily refers to "the library"; on the next call, it refers to "the bus stop". (Parameter, argument — the vocabulary is a little fussy, but it's genuinely handy to have separate words for the placeholder and the value that fills it.)

More than one parameter

def announce_event(event_name, location, start_time):
    print(f"{event_name}")
    print(f"Location: {location}")
    print(f"Starts: {start_time}")

announce_event("Repair café", "Library room 2", "Saturday at 1 PM")

Arguments line up with parameters by position: first with first, second with second, and so on. So a call needs the right number of values in the right order — Python won't guess what you meant. Descriptive parameter names go a long way toward preventing mix-ups.

And nothing stops you from calling a function inside a loop:

for copy_number in range(1, 4):
    announce_event("Repair café", "Library room 2", f"Session {copy_number}")

Local names stay inside the function

Parameters — and any variables you create inside a function — are normally local to that call:

def show_double(number):
    doubled = number * 2
    print(doubled)

show_double(6)
print(doubled)  # NameError: doubled is not defined here

This boundary might feel restrictive, but it's doing you a favor: a function can do its work without accidentally clobbering unrelated variables elsewhere in the program. Each call gets its own fresh set of local values.

Printing a result is not returning it

This next distinction trips up almost everybody at first, so let's take it slowly. A function that prints communicates with a person. A function that returns a value communicates with the rest of the program:

def calculate_tip(meal_cost, tip_rate):
    tip = meal_cost * tip_rate
    return tip

suggested_tip = calculate_tip(30.00, 0.18)
total = 30.00 + suggested_tip
print(f"Tip: ${suggested_tip:.2f}")
print(f"Total: ${total:.2f}")

When Python reaches return tip, the function call itself becomes that value — you can picture calculate_tip(30.00, 0.18) being crossed out and replaced by 5.4. That's why the result can be stored in a variable or dropped into a bigger calculation.

Compare:

def print_double(number):
    print(number * 2)

def calculate_double(number):
    return number * 2

print_double(5)                # displays 10
result = calculate_double(5)  # stores 10
print(result + 1)              # displays 11

The printing function isn't “worse.” It's doing a different job. The question to ask is: who needs this result next — a person looking at the screen, or code that's going to keep working with it?

A function contract

A contract is a short plain-language promise: here's what you may hand this function, and here's what it will do or give back. For example:

calculate_tip(meal_cost, tip_rate)

  • expects two numbers: a dollar amount and a rate written as a decimal,
  • returns the dollar amount of the tip,
  • does not print or ask the user for input.

The contract helps keep jobs separate. The outer program can handle asking the user for input; the calculation function just calculates — which means we can test it with any values we like:

print(calculate_tip(100, 0.20))  # expected: 20.0
print(calculate_tip(0, 0.20))    # expected: 0.0
print(calculate_tip(25, 0))      # expected: 0.0

These are informal tests, but they're real tests. Because the function returns a result and never pauses to ask for input, it's easy to call it repeatedly with normal cases and boundary cases and check what comes back.

Parameters define permitted variation

Choosing parameters is a design decision, and a surprisingly loaded one. If a drawing function accepts color and size, then color and size are what callers get to vary — nothing else. If a profile function requires only “first name” and “last name,” it has assumed that everyone's name fits that structure. If a transit estimator accepts only a driving speed, it has decided that every other way of getting around is outside the model.

A parameter list, in other words, is a small statement about which differences the program expects to exist. So ask: do the fixed parts truly need to be fixed? Does the caller have enough control? Does a default favor one kind of user over another without saying so?

Build and test a reusable function. Choose one:

  • a text function that prints a scene, label, stanza, or quiz question with changeable details;
  • a drawing function that changes a shape's size, turn angle, or narrated label; or
  • a calculation function that returns a converted measurement, price, or time.

Give it at least one parameter, call it with three different arguments, and write its contract. If it computes a value, return that value and use it after the call.
