Lesson 4 - Decisions and Logical Operators

By the end of this lesson, you'll be able to:

  • Use if, elif, and else to choose among paths.
  • Combine Boolean expressions with and, or, and not.
  • Trace branch order and construct a test that reaches every path.
  • Explain how a program's categories and rules encode human decisions.

From a question to an action

So far we've run statements in sequence, repeated them with loops, and grouped them into functions. But our programs still follow the same path regardless of the values they encounter. An if statement lets a Boolean question choose whether a block runs. That's another kind of control flow: deciding which instructions happen next.

temperature = float(input("Outdoor temperature in degrees F: "))

if temperature <= 32:
    print("Watch for ice.")

print("Check current conditions before traveling.")

The last line isn't indented, so it runs whether or not the ice warning appeared. Just as with loops, indentation is how Python knows which statements the condition controls. This is a place where Python is unusual: most languages use curly braces or keywords to mark the body, and Python decided that since programmers indent anyway, the indentation might as well be the syntax.

Two paths: if and else

hour = int(input("Showtime hour in 24-hour time: "))

if hour < 17:
    print("This is a matinee.")
else:
    print("This is an evening show.")

Exactly one of the two branches runs. Never both, never neither. Notice that else has no condition of its own. It just means "none of the conditions above me were true."

Several paths: elif

temperature = float(input("Temperature in degrees F: "))

if temperature < 32:
    description = "below freezing"
elif temperature < 60:
    description = "cool"
elif temperature < 80:
    description = "mild"
else:
    description = "hot"

print(f"That is {description} by this program's categories.")

Python checks the conditions top to bottom, runs the first one that's true, and skips all the rest. Take 55: temperature < 60 is the first true condition, so we get "cool." Now, 55 is also less than 80, so isn't it "mild" too? No, because Python never gets that far. It found a true condition and stopped looking.

This means the order matters! If temperature < 80 came first, it would catch 55 before the "cool" branch ever got a look. So arrange numeric thresholds from one end to the other, and then test right at the fenceposts: 31, 32, 59, 60, 79, and 80.

Combine questions with logical operators

Real rules usually depend on more than one fact at a time, so we need ways to combine Booleans:

  • A and B is true only when both A and B are true.
  • A or B is true when at least one is true, including when both are true.
  • not A reverses the Boolean value.
age = int(input("Age: "))
has_student_id = input("Current student ID? yes/no: ").strip().lower() == "yes"

if age <= 12 or age >= 65:
    print("Age-based reduced price applies.")
elif has_student_id:
    print("Student reduced price applies.")
else:
    print("Standard price applies.")

One caution about or. In everyday English, "you can have soup or salad" usually means one, not both. Python's or has no such restriction: it's satisfied when either side is true, and it's still satisfied when both are. So when you translate a rule from English, check which "or" the rule actually means, rather than trusting the sound of the word.

Translate the rule before writing the code

Suppose a community tool library says:

A person may reserve a power tool if they are a member, have completed safety orientation, and the tool is available.

That goes into Python almost word for word:

can_reserve = is_member and orientation_complete and tool_available

Now suppose the policy also lets staff reserve unavailable tools for maintenance:

can_reserve = (is_member and orientation_complete and tool_available) or is_staff

The parentheses show the reader that the three member requirements go together, and is_staff is a separate condition. Python already gives and higher precedence than or, so removing these particular parentheses would produce the same result. We keep them because the policy is easier to read with its grouping visible. Before coding up a compound policy like this, it helps to write out some example cases in a decision table:

MemberOrientationAvailableStaffExpected result
TrueTrueTrueFalsemay reserve
TrueFalseTrueFalsemay not reserve
FalseFalseFalseTruemay reserve for maintenance
FalseTrueTrueFalsemay not reserve

A table like this is useful for debugging, but it's also something a person who has never seen Python can read. The tool library's staff could look at it and say "wait, that third row isn't what we meant," which is a much better time to find out than after the program is running.

Put a decision inside a function

def describe_reading_time(minutes):
    if minutes < 0:
        return "invalid time"
    elif minutes <= 10:
        return "a quick read"
    elif minutes <= 30:
        return "a medium read"
    else:
        return "a long read"

print(describe_reading_time(8))
print(describe_reading_time(25))
print(describe_reading_time(-1))

Each call can come back with a different answer, and the whole classification rule lives under one name. That makes it reusable, and it also means there's one place to go when you want to test every branch.

Who makes the rules?

There is nothing about the number 31 that makes it "a long read." A programmer picked that threshold, for some purpose, with some audience in mind. In a small creative program that's no big deal: if the label feels wrong, you change it. But the very same if structure shows up in programs that screen job applications or decide who qualifies for public benefits, and there a branch can decide what a real person gets or doesn't get.

When code sorts people into categories or hands out resources, ask:

  • What information is used, and what relevant information is missing?
  • Who chose the categories and thresholds?
  • Which boundary cases are likely?
  • Can a person understand, correct, or appeal the result?
  • Are the labels respectful and useful for the stated purpose?

Getting the condition right is necessary, but it's not the same thing as choosing a fair condition. Testing can tell you whether the code follows the rule. It can't tell you whether the rule is fair, so that question goes back to whoever wrote it, and ideally to the people it gets applied to as well.
