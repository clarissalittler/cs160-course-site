Lesson 4 - Decisions and Logical Operators

At the end of this lesson, you will be able to:

  • Use if, elif, and else to choose among paths.
  • Combine Boolean expressions with and, or, and not.
  • Trace branch order and construct a test that reaches every path.
  • Explain how a program's categories and rules encode human decisions.

From a question to an action

Until now, our statements have normally run in sequence. An if statement changes that flow: its indented body runs only when its Boolean condition is True.

temperature = float(input("Outdoor temperature in degrees F: "))

if temperature <= 32:
    print("Watch for ice.")

print("Check current conditions before traveling.")

The final line is not indented, so it runs whether or not the ice warning appears. Indentation is not decoration; it marks which statements are controlled by the condition.

Choose between two paths with if and else

hour = int(input("Showtime hour in 24-hour time: "))

if hour < 17:
    print("This is a matinee.")
else:
    print("This is an evening show.")

Exactly one branch runs. else does not have its own condition; it means “none of the preceding conditions in this chain were true.”

Choose among several paths with elif

temperature = float(input("Temperature in degrees F: "))

if temperature < 32:
    description = "below freezing"
elif temperature < 60:
    description = "cool"
elif temperature < 80:
    description = "mild"
else:
    description = "hot"

print(f"That is {description} by this program's categories.")

Python checks conditions from top to bottom and runs the first true branch, then skips the rest. For 55, temperature < 60 is the first true condition, so the result is “cool.” It is also true that 55 is less than 80, but Python never reaches that condition.

Order matters. If temperature < 80 appeared first, it would capture 55 before the more specific boundary was checked. Arrange numeric thresholds from one end toward the other and test the fenceposts: 31, 32, 59, 60, 79, and 80.

Combine questions with logical operators

Many rules depend on more than one fact:

  • A and B is true only when both A and B are true.
  • A or B is true when at least one is true, including when both are true.
  • not A reverses the Boolean value.
age = int(input("Age: "))
has_student_id = input("Current student ID? yes/no: ").strip().lower() == "yes"

if age <= 12 or age >= 65:
    print("Age-based reduced price applies.")
elif has_student_id:
    print("Student reduced price applies.")
else:
    print("Standard price applies.")

Python's or is inclusive: both sides may be true. Everyday speech sometimes uses an exclusive “either/or,” meaning one but not both, so translate the actual rule instead of relying on the sound of the word.

Translate the rule before writing the code

Suppose a community tool library says:

A person may reserve a power tool if they are a member, have completed safety orientation, and the tool is available.

The direct translation is:

can_reserve = is_member and orientation_complete and tool_available

Now suppose the policy also allows staff to reserve unavailable tools for maintenance:

can_reserve = (is_member and orientation_complete and tool_available) or is_staff

Parentheses make the intended grouping clear. Before coding a compound policy, list examples in a decision table:

MemberOrientationAvailableStaffExpected result
TrueTrueTrueFalsemay reserve
TrueFalseTrueFalsemay not reserve
FalseFalseFalseTruemay reserve for maintenance
FalseTrueTrueFalsemay not reserve

A table is not only for debugging. It lets other people inspect whether the code matches the stated policy.

Put a decision inside a function

def describe_reading_time(minutes):
    if minutes < 0:
        return "invalid time"
    elif minutes <= 10:
        return "a quick read"
    elif minutes <= 30:
        return "a medium read"
    else:
        return "a long read"

print(describe_reading_time(8))
print(describe_reading_time(25))
print(describe_reading_time(-1))

Each call may return a different result. The function packages the classification rule under a name, which makes it reusable and gives us one place to test every branch.

Rules in code are still rules made by people

The phrase “a long read” is not inherent in the number 31. The programmer chose a threshold for some purpose and audience. In low-stakes creative software, revising that choice may be easy. In hiring, lending, healthcare, education, or public benefits, a branch may shape someone's opportunities.

When code classifies people or allocates resources, ask:

  • What information is used, and what relevant information is missing?
  • Who chose the categories and thresholds?
  • Which boundary cases are likely?
  • Can a person understand, correct, or appeal the result?
  • Are the labels respectful and useful for the stated purpose?

Writing the condition correctly is necessary. It is not the same as choosing a just condition.
