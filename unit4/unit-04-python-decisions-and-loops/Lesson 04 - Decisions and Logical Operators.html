Lesson 4 - Decisions and Logical Operators

Our goals for this lesson — by the end, you'll be able to:

  • Use if, elif, and else to choose among paths.
  • Combine Boolean expressions with and, or, and not.
  • Trace branch order and construct a test that reaches every path.
  • Explain how a program's categories and rules encode human decisions.

From a question to an action

If all our programs could ever do was run straight through, statement after statement, we'd basically have a very elaborate calculator. The if statement is what changes that: its indented body runs only when its Boolean condition is True.

temperature = float(input("Outdoor temperature in degrees F: "))

if temperature <= 32:
    print("Watch for ice.")

print("Check current conditions before traveling.")

The final line isn't indented, so it runs whether or not the ice warning appears. Indentation isn't decoration here — it's how Python knows which statements the condition controls.

Choose between two paths with if and else

hour = int(input("Showtime hour in 24-hour time: "))

if hour < 17:
    print("This is a matinee.")
else:
    print("This is an evening show.")

Exactly one branch runs — never both, never neither. And else has no condition of its own; it simply means “none of the conditions above me were true.”

Choose among several paths with elif

temperature = float(input("Temperature in degrees F: "))

if temperature < 32:
    description = "below freezing"
elif temperature < 60:
    description = "cool"
elif temperature < 80:
    description = "mild"
else:
    description = "hot"

print(f"That is {description} by this program's categories.")

Python checks the conditions from top to bottom, runs the first true branch, and skips everything after it. Take 55: temperature < 60 is the first condition that's true, so the result is “cool.” Yes, 55 is also less than 80 — but Python never gets that far.

Which means order matters! If temperature < 80 came first, it would grab 55 before the more specific boundary ever got checked. Arrange numeric thresholds from one end toward the other and test the fenceposts: 31, 32, 59, 60, 79, and 80.

Combine questions with logical operators

Real rules usually hinge on more than one fact at a time:

  • A and B is true only when both A and B are true.
  • A or B is true when at least one is true, including when both are true.
  • not A reverses the Boolean value.
age = int(input("Age: "))
has_student_id = input("Current student ID? yes/no: ").strip().lower() == "yes"

if age <= 12 or age >= 65:
    print("Age-based reduced price applies.")
elif has_student_id:
    print("Student reduced price applies.")
else:
    print("Standard price applies.")

One caution: Python's or is inclusive — it's perfectly satisfied when both sides are true. Everyday speech sometimes means an exclusive “either/or,” one but not both, so translate the actual rule instead of trusting the sound of the word.

Translate the rule before writing the code

Suppose a community tool library says:

A person may reserve a power tool if they are a member, have completed safety orientation, and the tool is available.

Translated directly into Python:

can_reserve = is_member and orientation_complete and tool_available

Now suppose the policy also allows staff to reserve unavailable tools for maintenance:

can_reserve = (is_member and orientation_complete and tool_available) or is_staff

The parentheses make the grouping unmistakable: the member requirements travel together, and is_staff is its own separate door in. Before coding a compound policy, list some example cases in a decision table:

MemberOrientationAvailableStaffExpected result
TrueTrueTrueFalsemay reserve
TrueFalseTrueFalsemay not reserve
FalseFalseFalseTruemay reserve for maintenance
FalseTrueTrueFalsemay not reserve

A table like this isn't only for debugging. It's something other people can read — no Python required — to check whether the code matches the stated policy.

Put a decision inside a function

def describe_reading_time(minutes):
    if minutes < 0:
        return "invalid time"
    elif minutes <= 10:
        return "a quick read"
    elif minutes <= 30:
        return "a medium read"
    else:
        return "a long read"

print(describe_reading_time(8))
print(describe_reading_time(25))
print(describe_reading_time(-1))

Each call can come back with a different answer. The function wraps the whole classification rule up under one name, which makes it reusable — and gives us exactly one place to go when we want to test every branch.

Rules in code are still rules made by people

There is nothing about the number 31 that makes it “a long read.” A programmer chose that threshold, for some purpose, with some audience in mind. In low-stakes creative software that's no big deal — if the label feels wrong, you revise it and move on. But the very same if structure shows up in hiring, lending, healthcare, education, and public benefits, and there a branch can shape someone's real opportunities.

When code classifies people or allocates resources, ask:

  • What information is used, and what relevant information is missing?
  • Who chose the categories and thresholds?
  • Which boundary cases are likely?
  • Can a person understand, correct, or appeal the result?
  • Are the labels respectful and useful for the stated purpose?

Writing the condition correctly is necessary. It is not the same thing as choosing a just condition.
