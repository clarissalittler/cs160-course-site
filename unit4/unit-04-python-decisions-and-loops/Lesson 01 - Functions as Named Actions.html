Lesson 1 - Functions as Named Actions

At the end of this lesson, you will be able to:

  • Distinguish calling an existing function from defining a new function.
  • Define, call, and reuse a function with no parameters.
  • Explain why a function definition does not run its body immediately.
  • Choose a coherent group of steps and give it a descriptive name.

You have been calling functions all along

In Unit 3 you used print(), input(), int(), float(), type(), and range(). Each call used a function somebody else had already defined. A function packages a useful action behind a name. You supply information when necessary; the function does its work; it may produce a result.

Now you will teach Python a new action of your own. Suppose a tiny radio play uses the same transition several times:

print("[music rises]")
print("NARRATOR: Meanwhile, across town...")
print("[music fades]")

We could copy those lines every time. But the three lines form one idea: a scene transition. A function lets us name that idea.

Define first, call second

def scene_transition():
    print("[music rises]")
    print("NARRATOR: Meanwhile, across town...")
    print("[music fades]")

print("SCENE 1: At the bus stop")
scene_transition()
print("SCENE 2: At the library")
scene_transition()
print("SCENE 3: On the moon")

The definition has several parts:

  • def tells Python we are defining a function.
  • scene_transition is the name of the new action.
  • The parentheses will later hold parameters; they are empty for now.
  • The colon begins the body.
  • The indented statements belong to the function.

When Python reaches the def, it remembers the recipe but does not perform it. The body runs only when a later line calls scene_transition(). In this example the same three-line action runs twice.

A definition is not a call. If your file contains only:

def cheer():
    print("You can debug this!")

it will display nothing. Python learned the action, but nobody asked it to perform the action. Add cheer() on an unindented line after the definition.

A function changes how we read a program

Without a function, the reader must interpret three low-level print calls each time. With one, the main sequence reads like a set of meaningful verbs:

show_title()
introduce_character()
scene_transition()
deliver_closing_line()

This is abstraction: we put details behind a name so we can reason at a larger scale. The details still matter, but we can examine them when needed rather than holding every line in our heads at once.

A good function usually performs one coherent job. show_title() tells us more than stuff(). A function called show_title_and_ask_age_and_calculate_tax() is probably doing too many unrelated things.

Functions and loops solve different problems

A loop says, “repeat this block.” A function says, “call this group of steps by a meaningful name.” They work well together:

def print_refrain():
    print("We are still here; we are still making.")

for verse_number in range(1, 4):
    print(f"Verse {verse_number}")
    print_refrain()

The function identifies what the repeated action means; the loop controls how many times it happens. Neither idea replaces the other.

Functions in a drawing program

The same structure works with ColabTurtle commands:

def draw_square():
    for side in range(4):
        forward(80)
        right(90)

draw_square()
right(45)
draw_square()

In words: draw_square() repeats a forward movement and a right turn four times. The program draws one square, rotates 45 degrees, and draws a second square. That text description is part of the artifact, not an apology for being unable to see the canvas.

Reusing code also means maintaining one source

If the radio play uses ten copied transitions and you want to change the sound cue, you must find and edit ten copies. If they all call one function, you edit the definition once. This is sometimes summarized as “Don't Repeat Yourself,” but avoiding repeated typing is only part of the benefit. A shared definition reduces the chance that one outdated copy survives.

Functions also support collaboration. Teammates can agree that show_result() will perform a certain job, then work on different parts of the program. But names can conceal important behavior, too. A function called calculate_risk() sounds objective even if it embeds questionable assumptions. Abstraction should make a program easier to understand, not shield consequential rules from inspection.

Make a named action. Start with three or more related statements from a text, turtle, calculator, or sound-oriented program.

  1. Give the group a descriptive verb-style name.
  2. Place it in a function definition.
  3. Call the function at least twice.
  4. Change the definition and confirm that every call now uses the change.
  5. Explain in one sentence what a reader is allowed to forget when they see the function's name.
