Lesson 1 - Functions as Named Actions

By the time you finish this lesson, you'll be able to:

  • Distinguish calling an existing function from defining a new function.
  • Define, call, and reuse a function with no parameters.
  • Explain why a function definition does not run its body immediately.
  • Choose a coherent group of steps and give it a descriptive name.

You've been calling functions all along

You've been using functions since your very first line of Python. In Unit 3 you called print(), input(), int(), float(), type(), and range(), and every one of them was a function that somebody else wrote and gave a name to. That's what a function is: a chunk of code with a name. You hand it whatever information it needs, it does its work, and sometimes it hands you a result back.

Now it's your turn to teach Python a new one. Say you're writing a tiny radio play, and the same transition keeps coming up between scenes:

print("[music rises]")
print("NARRATOR: Meanwhile, across town...")
print("[music fades]")

We could paste those lines in every time the scene changes. But those three lines aren't three separate thoughts. They're one idea, "scene transition," and it would be nice to be able to say so.

Define first, call second

def scene_transition():
    print("[music rises]")
    print("NARRATOR: Meanwhile, across town...")
    print("[music fades]")

print("SCENE 1: At the bus stop")
scene_transition()
print("SCENE 2: At the library")
scene_transition()
print("SCENE 3: On the moon")

Let's go through the definition piece by piece:

  • def tells Python we're defining a function.
  • scene_transition is the name of our new action.
  • The parentheses will hold parameters later; for now they're empty.
  • The colon begins the body.
  • The indented statements belong to the function.

Here's the thing that surprises people: when Python reads the def, nothing gets printed. Python memorizes the recipe but doesn't cook anything. The body only runs when a later line calls scene_transition(), which this program does twice, and both times it gets the same three lines.

A definition is not a call. If your whole file is:

def cheer():
    print("You can debug this!")

then running it displays nothing at all. Python learned how to cheer, but nobody asked it to. Add cheer() on an unindented line after the definition and you'll get your pep talk. This is probably the single most common "why doesn't my function do anything?" bug, so if it happens to you, you're in good company.

Functions and readability

Without functions, anyone reading the radio play has to decode the same three print calls every time they show up. With functions, the main part of the program reads like a list of things that happen:

show_title()
introduce_character()
scene_transition()
deliver_closing_line()

This is called abstraction: hiding details behind a name so that we can think about the big picture. The details still matter! We just don't have to hold every line in our heads at once, and when we do need them, we know where to look.

For this to work, a function should do one job that you can name. show_title() tells you a lot more than stuff() does. And if you ever catch yourself writing show_title_and_ask_age_and_calculate_tax(), the name itself is telling you that this should be three functions.

Functions vs. loops

A loop says "do this block again." A function says "here's a name for this group of steps." Those are different ideas, and they combine nicely:

def print_refrain():
    print("We are still here; we are still making.")

for verse_number in range(1, 4):
    print(f"Verse {verse_number}")
    print_refrain()

The function says what the repeated action is; the loop says how many times it happens. Neither one replaces the other.

Functions in a drawing program

Exactly the same structure works with ColabTurtle commands:

def draw_square():
    for side in range(4):
        forward(80)
        right(90)

draw_square()
right(45)
draw_square()

In words: draw_square() moves forward and turns right, four times over. The program draws one square, rotates 45 degrees, and draws a second square on top of it. That written description isn't an afterthought, by the way. Being able to say what a drawing program does, in a sentence, is part of understanding it, and it's what makes the program legible to someone who can't see the canvas.

Reusing a function

Imagine the radio play has ten pasted-in transitions and you decide to change the sound cue. Now you have to hunt down all ten, and if you miss one, that stale copy sits there waiting to confuse somebody later. If all ten places call one function instead, you change the definition once and you're done. Programmers have a slogan for this, "Don't Repeat Yourself," and that sounds like it's about saving typing but it isn't, really. The real benefit is that there's only one copy to get right!

Functions are also how people work together on a program: teammates agree on what show_result() is supposed to do, and then each goes off to build a different piece. But notice that a name can hide as easily as it reveals. A function called calculate_risk() sounds neutral and objective even if the calculation inside is built on dubious assumptions. Abstraction is supposed to make a program easier to understand. It shouldn't turn into a place where important rules go to avoid being looked at.

Make a named action. Take three or more related statements from a text, turtle, calculator, or sound-oriented program, whichever one you've been enjoying.

  1. Give the group a descriptive verb-style name.
  2. Put it in a function definition.
  3. Call the function at least twice.
  4. Change the definition and confirm that every call now uses the change.
  5. Explain in one sentence what a reader is allowed to forget when they see the function's name.
