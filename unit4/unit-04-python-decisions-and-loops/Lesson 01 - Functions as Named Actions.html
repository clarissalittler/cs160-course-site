Lesson 1 - Functions as Named Actions

By the time you finish this lesson, you'll be able to:

  • Distinguish calling an existing function from defining a new function.
  • Define, call, and reuse a function with no parameters.
  • Explain why a function definition does not run its body immediately.
  • Choose a coherent group of steps and give it a descriptive name.

You have been calling functions all along

You've been using functions since your very first line of Python. In Unit 3 you called print(), input(), int(), float(), type(), and range() — every one of them a function somebody else had already defined. A function packages a useful action behind a name: you hand it whatever information it needs, it does its work, and sometimes it hands you a result back.

Now it's your turn to teach Python an action of your own. Say you're writing a tiny radio play, and the same transition keeps coming up:

print("[music rises]")
print("NARRATOR: Meanwhile, across town...")
print("[music fades]")

We could copy those lines every single time the scene changes. But those three lines aren't really three separate thoughts — they're one idea, a scene transition, and a function lets us give that idea a name.

Define first, call second

def scene_transition():
    print("[music rises]")
    print("NARRATOR: Meanwhile, across town...")
    print("[music fades]")

print("SCENE 1: At the bus stop")
scene_transition()
print("SCENE 2: At the library")
scene_transition()
print("SCENE 3: On the moon")

Let's break down the pieces of that definition:

  • def tells Python we're defining a function.
  • scene_transition is the name of our new action.
  • The parentheses will hold parameters later; for now they're empty.
  • The colon begins the body.
  • The indented statements belong to the function.

When Python reaches the def, it memorizes the recipe but doesn't cook anything. The body runs only when a later line calls scene_transition() — which this example does twice, getting the same three-line action both times.

A definition is not a call. If your file contains only:

def cheer():
    print("You can debug this!")

it will display nothing at all. Python learned the action, but nobody asked it to do the action. Add cheer() on an unindented line after the definition and you'll get your pep talk.

A function changes how we read a program

Without a function, anyone reading the program has to decode the same three low-level print calls every time they show up. With one, the main sequence reads like a list of meaningful verbs:

show_title()
introduce_character()
scene_transition()
deliver_closing_line()

This is abstraction: tucking details behind a name so we can think at a larger scale. The details still matter! We just don't have to hold every line in our heads at once — we can go look them up when we need them.

A good function usually does one coherent job. show_title() tells us a lot more than stuff() does. And if you ever find yourself writing show_title_and_ask_age_and_calculate_tax(), the name itself is warning you that the function is juggling too many unrelated things.

Functions and loops solve different problems

A loop says “do this block again.” A function says “here's a meaningful name for this group of steps.” Different jobs — and they get along great:

def print_refrain():
    print("We are still here; we are still making.")

for verse_number in range(1, 4):
    print(f"Verse {verse_number}")
    print_refrain()

The function says what the repeated action means; the loop says how many times it happens. Neither idea replaces the other.

Functions in a drawing program

The same structure works just as well with ColabTurtle commands:

def draw_square():
    for side in range(4):
        forward(80)
        right(90)

draw_square()
right(45)
draw_square()

In words: draw_square() repeats a forward movement and a right turn four times. The program draws one square, rotates 45 degrees, and draws a second square. That written description is part of the work itself, by the way — not an apology for anyone who can't see the canvas.

Reusing code also means maintaining one source

Imagine the radio play has ten copied transitions and you decide to change the sound cue. Now you get to hunt down and edit all ten — and if you miss one, that stale copy lives on to confuse everyone later. If all ten spots call one function instead, you edit the definition once and you're done. Programmers sometimes summarize this as “Don't Repeat Yourself,” but I'd say saving keystrokes is the smaller benefit; having one source of truth to keep correct is the bigger one.

Functions also make collaboration possible: teammates can agree on what show_result() is supposed to do, then go work on different parts of the program. But a name can conceal behavior as easily as it reveals it. A function called calculate_risk() sounds neutral and objective even if the calculation inside rests on questionable assumptions. Abstraction should make a program easier to understand — it shouldn't become a place to hide consequential rules from inspection.

Make a named action. Grab three or more related statements from a text, turtle, calculator, or sound-oriented program — whichever you've been enjoying.

  1. Give the group a descriptive verb-style name.
  2. Place it in a function definition.
  3. Call the function at least twice.
  4. Change the definition and confirm that every call now uses the change.
  5. Explain in one sentence what a reader is allowed to forget when they see the function's name.

Coming next: right now those empty parentheses mean a function can only ever do one fixed thing. Parameters will let each call bring its own information, and return will let a function hand a value back for the rest of the program to use.
