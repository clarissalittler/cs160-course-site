Lesson 1 - Make Something Happen

At the end of this lesson, you will be able to:

  • Run, change, and explain a short Python program.
  • Describe the relationship among an algorithm, source code, and an interpreter.
  • Plan a small program as a sequence of inputs, processing steps, and outputs.
  • Test an algorithm with more than one example.

Programming begins with a wonderfully direct idea: you write an instruction, ask the computer to carry it out, and observe what happens. We will spend plenty of time planning and explaining programs, but you do not need to earn your way to the Run button. Let us make something happen immediately.

Your first running program

Open the browser-based Python workspace your instructor provides, or use one of the choices on Setting Up a Python Interpreter. Type these lines exactly, then choose Run:

print("Hello, computer!")
print("I made this program run.")

The words should appear in the output area. Each line is a statement: an instruction Python can execute. Python normally executes statements from top to bottom, so the first message appears before the second.

print is a function Python already knows. A function call asks a named function to do its job. The parentheses contain the information we give it—in this case, the text to display. You do not need to know how print works inside in order to use it, just as you do not need to build a microwave before pressing its buttons. In Unit 4, you will define new functions of your own.

Predict, run, change. Before running each experiment, predict what you think will happen:

  1. Swap the two lines.
  2. Change one message to something you would genuinely like a tiny program to say.
  3. Add a third print(...) call.
  4. Remove one closing quotation mark, run the program, and read the final line of the error. Then put the quotation mark back.

That last experiment is not vandalism. Deliberately making and repairing a small error is one of the safest ways to learn what the language expects.

What happens when you choose Run?

The text you write is source code. Python is both the name of a programming language and the everyday name for the interpreter that reads Python source code and carries out its instructions. A browser-based editor may hide the interpreter behind a friendly Run button, but the same basic process is happening:

  1. You write and save source code.
  2. The interpreter reads the first statement and executes it.
  3. It continues in order unless an instruction changes that flow or an error stops it.
  4. The program produces output or changes some state.

A program is not the same thing as its output. The source code is the recipe; one particular run is a meal made from that recipe. The same program can produce different output when it receives different input.

Before code: decide what should happen

An algorithm is a step-by-step method for completing a task. A recipe is an algorithm. Directions to a classroom are an algorithm. A checklist for registering for a course is an algorithm. A program is an algorithm expressed precisely enough for a computer to carry it out.

Computers are fast and literal. They do not fill in a missing step using common sense, and they do not know what you meant instead of what you wrote. That is why programmers often sketch an algorithm in pseudocode: precise but informal instructions written for people rather than an interpreter.

Goal: calculate the cost per person for a shared meal

Ask for the total cost of the meal
Ask how many people are sharing it
Divide the total cost by the number of people
Display the cost per person

Pseudocode does not have one official grammar. Its job is to expose the thinking. This example also exposes three parts that appear in many programs:

  • Input: information entering the program—the bill and the number of people.
  • Processing: work the program performs—division.
  • Output: information leaving the program—the result it displays.

Programs may also store information between steps. In the next lesson, we will give stored values names called variables.

Precision is a human question, too

“Cost per person” sounds neutral, but our little algorithm already makes choices. Does it include a tip? Is everyone expected to pay an equal share? What happens if one person did not eat? Who decides the rounding rule? A computer will perform the division quickly, but speed does not make the assumptions fair.

This is true of serious software as well. A scheduling system, benefits form, or content recommendation system follows instructions written by people. When a program causes harm, “the computer decided” is not a complete explanation. Someone chose the inputs, categories, rules, and goals. Learning to program includes learning to notice those choices.

Test the idea before trusting it

Try the meal-sharing algorithm by hand with several cases:

  • $60 shared by 3 people should produce $20 per person.
  • $25 shared by 2 people should produce $12.50 per person.
  • $60 shared by 0 people cannot be divided. The algorithm needs a rule for that case.

The first case is a normal case, the second checks a result with a decimal, and the third is an edge case that reveals a missing assumption. Testing is not something we do only after a program is finished. It is part of deciding what “finished” should mean.

Try it: a tiny program plan. Choose something a computer could calculate or assemble in a few steps: a commute-time estimate, a unit conversion, a short greeting, or a two-line poem. Write:

  1. the intended output,
  2. any input it would need,
  3. three to six pseudocode steps, and
  4. two examples you would use to test it.

Then write two or three print() calls that create a rough first version. It does not have to be interactive yet. The important thing is the cycle: imagine, make, observe, revise.
