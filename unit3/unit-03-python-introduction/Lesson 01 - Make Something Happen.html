Lesson 1 - Make Something Happen

Here's what you'll be able to do by the end of this lesson:

  • Run, change, and explain a short Python program.
  • Describe the relationship among an algorithm, source code, and an interpreter.
  • Plan a small program as a sequence of inputs, processing steps, and outputs.
  • Test an algorithm with more than one example.

Programming is, at heart, a pretty simple idea: you write down an instruction, you hand it to the computer, and the computer does it. Everything else—planning, explaining, fixing—we can build up as we go, so let's make something happen right now!

Your first running program

Open the browser-based Python workspace your instructor provides, or pick one of the options on Setting Up a Python Interpreter. Type these two lines exactly as written and hit Run:

print("Hello, computer!")
print("I made this program run.")

You should see both messages show up in the output area. Each of those lines is a statement, which is the fancy name for a single instruction that Python knows how to carry out. Python runs statements from top to bottom, one after another, which is why the first message shows up before the second. That might seem too obvious to even mention, but "top to bottom, one at a time" is the thing we'll keep coming back to whenever a program does something surprising.

So what is print? It's a function: a chunk of code with a name, that somebody else already wrote, and that you get to use by writing the name followed by parentheses. Doing that is called a function call, and whatever you put inside the parentheses is the information you're handing over—here, the text you want displayed. You don't have to know how print works on the inside in order to use it, any more than you need to know how a microwave works to heat up leftovers. (In Unit 4 you'll get to write functions of your own, which is where things start to get really fun.)

Predict, run, change. Here are four experiments. Before you run each one, say out loud what you think will happen:

  1. Swap the two lines.
  2. Change one of the messages to something you'd actually want a tiny program to say.
  3. Add a third print(...) line.
  4. Delete one of the closing quotation marks, run the program, and read the last line of the error message. Then put the quotation mark back.

Yes, I'm asking you to break the program on purpose. Breaking something small and then fixing it is one of the fastest ways to learn what a language actually wants from you, and it's a lot less stressful than the first time it breaks by accident.

What happens when you hit Run?

The text you typed is source code. Now here's a slightly confusing thing about the word "Python": it's the name of the language, but it's also what everybody calls the interpreter, the program that reads your source code and does what it says. When you press Run in a browser-based editor, you're really sending your code off to an interpreter and getting its output back. Whether the interpreter is hidden behind a button or running on your own laptop, the same thing happens:

  1. You write some source code.
  2. The interpreter reads the first statement and does it.
  3. It moves on to the next one, and the next, unless some instruction tells it to do otherwise or an error stops it cold.
  4. Along the way the program prints things, or changes something, or both.

One distinction to keep straight: a program is not the same thing as its output. The source code is more like a recipe, and each run is one meal made from that recipe. Give the same program different input and you get a different meal.

Before code: decide what should happen

An algorithm is a step-by-step method for getting something done. A recipe is an algorithm. Directions to a classroom are an algorithm. So is the checklist you follow to register for a course. A program is just an algorithm written down precisely enough that a computer can follow it.

And "precisely enough" is where all the difficulty lives. Computers are fast, but they're also extremely literal. Have you ever tried to explain a complicated task to someone entirely in writing, without being able to point or demonstrate? It's hard! People fill in the gaps with common sense. A computer won't. It has no idea what you meant, only what you wrote. That's why programmers often sketch an algorithm first in pseudocode: instructions that are careful and step-by-step, but written for a person rather than an interpreter.

Goal: calculate the cost per person for a shared meal

Ask for the total cost of the meal
Ask how many people are sharing it
Divide the total cost by the number of people
Display the cost per person

There's no official grammar for pseudocode. Its only job is to get your thinking out of your head and onto the page where you can look at it. This little example also happens to have the three parts that show up in an enormous number of programs:

  • Input: information coming into the program—the bill and the number of people.
  • Processing: the work the program does—here, one division.
  • Output: information going back out—the answer it displays.

Programs can also store information in between steps. Next lesson we'll give stored values names, which is what variables are for.

How precise?

"Cost per person" sounds like a neutral bit of arithmetic, but look at how many choices are already hiding inside our four-line algorithm. Does the total include the tip? Does everyone pay the same, even the person who only had water? What about rounding—who eats the extra penny? The computer will do the division in a microsecond, but being fast doesn't make any of those choices right. Somebody made them.

This scales up. A scheduling system, a benefits application, the thing that decides what shows up in your feed: every one of them is following instructions that people wrote. So when a program does something harmful, "the computer decided" is never the whole story. Someone chose the inputs, the categories, the rules, the goals. Learning to program means learning to see those choices, including the ones you make yourself.

Testing the idea

Try running the meal-sharing algorithm by hand, no computer needed, on a few cases:

  • $60 shared by 3 people should come out to $20 each.
  • $25 shared by 2 people should come out to $12.50 each.
  • $60 shared by 0 people... can't be divided at all. Our algorithm doesn't say what to do here!

The first case is ordinary. The second checks that we handle a result with cents in it. The third is what programmers call an edge case: an input right at the boundary of what makes sense, where the algorithm's missing assumptions show up. Notice that we found a hole in the plan before writing a single line of Python. That's what testing is really for. It isn't a final step you tack on once the program is done; it's how you figure out what "done" means in the first place.

Try it: a tiny program plan. Pick something small a computer could calculate or put together in a few steps—a commute-time estimate, a unit conversion, a greeting, a two-line poem, &c. Write down:

  1. the intended output,
  2. any input it would need,
  3. three to six pseudocode steps, and
  4. two examples you would use to test it.

Then write two or three print() lines that make a rough first version. It doesn't need to take input yet. The point is to go through the full cycle once: imagine it, make it, look at what happened, change it.
