Lesson 3 - Input, Output, and Strings

In this lesson you'll learn how to:

  • Collect text with input() and store the returned value.
  • Convert number-shaped text with int() or float().
  • Create readable output with print() and f-strings.
  • Design prompts and output that tell a user what the program needs and what it produced.

From a speech to a conversation

A program made entirely of print() calls gives the same speech every time you run it. Input is what turns the speech into something interactive. The built-in input() function shows a prompt, waits for the person to type something and hit Enter, and then hands back whatever they typed:

name = input("What name would you like me to use? ")
print("Hello", name)

There are two things happening in that first line. First, input(...) gets the text from the user, and second the name = part stores it. If you wrote input("Name: ") on its own, Python would still show the prompt and wait for an answer, and then the answer would vanish, because you didn't store it anywhere.

Input

Here's something that might seem weird at first: if the user types 25, input() gives you the string "25", not the number 25. Why? Because all a keyboard sends is characters, and Python has no way of knowing whether those two characters are an age, a bus route, or half of a password. So it hands you the raw text and lets you decide. If you want to do arithmetic, you have to convert it yourself:

age_text = input("How old are you? ")
age = int(age_text)
age_next_year = age + 1
print(age_next_year)

Or, nesting one function call inside the other, all in one line:

age = int(input("How old are you? "))

Use int() when only whole numbers make sense and float() when a fractional value is fine:

people = int(input("How many people? "))
distance_miles = float(input("Distance in miles: "))

What if the user types three where int() was expecting digits? Python raises a ValueError and the program stops. That's not really the user's fault; typing a word for a number is a perfectly normal thing for a person to do. It just means our program doesn't have a plan yet for that response. Unit 4 will show us how to check simple text responses and numeric ranges. Recovering from a failed conversion takes exception handling, which we won't cover in this sequence. For now, test with number-shaped input and recognize what happens when the conversion fails.

Build messages with f-strings

An f-string is an ordinary string with the letter f stuck in front of the opening quotation mark. It creates a little "template" you can drop data into in order to "format", that's where the 'f' comes from, the final text. Anything you put inside curly braces gets evaluated, and its value gets dropped into the text:

title = input("Title of your tiny publication: ")
pages = int(input("How many pages? "))
print(f"Your publication '{title}' will have {pages} pages.")

Unlike +, an f-string is happy to include a number without you converting it to a string first. And the braces can hold a small calculation, not just a variable name:

print(f"Printing two copies will require {pages * 2} page-sides.")

For money and measurements it helps to control how many decimal places show up. Putting :.2f after the value asks for exactly two digits after the decimal point:

cost = 7.5
print(f"Estimated cost: ${cost:.2f}")

Formatting only changes how the value is displayed. The variable cost is still the number 7.5; we've just asked to see it written as 7.50.

A complete small program

Here's the meal-sharing plan from Lesson 1, now as actual Python. Each step of the pseudocode turned into a line of code, in the same order:

# Input
meal_total = float(input("Total cost of the meal in dollars: $"))
number_of_people = int(input("How many people are sharing the cost? "))

# Process
cost_per_person = meal_total / number_of_people

# Output
print(f"Each person pays ${cost_per_person:.2f}.")

A line that starts with # is a comment. Python skips comments entirely; they're notes for the humans reading the code. The best comments explain why something is there, or flag a decision that isn't obvious. You don't need to translate every line into English, since a line like cost_per_person = meal_total / number_of_people already says what it does.

Predict, run, investigate, modify.

  1. Predict the output for a $48 meal shared by 4 people.
  2. Run that case and compare the result with your prediction.
  3. Run a case where the result does not divide evenly, such as $20 shared by 3.
  4. Add an input for a tip percentage and include the tip before dividing.
  5. Change at least one prompt so the expected unit is unmistakable.

The user interface

Your prompts and your output are a user interface, a small one, and the first rule of any user interface is that it shouldn't make people guess. Compare input("Number? ") with input("Trip distance in miles: "). The second one says what it wants and what unit it wants it in. Output needs the same care. If a program prints a bare 12.5, the person now has to remember what that number was supposed to be. Label it!

Clear text also matters for accessibility. Don't put an important result only in a color, a spacing trick, an emoji, or a picture. A screen reader can announce "Estimated travel time: 35 minutes" directly, but "Result: red" means nothing without the visual context around it.

And ask only for what the program actually needs. A zine generator needs the name you'd like printed on the cover. It doesn't need a legal name, a birth date, or an email address. While this seems like a trivial issue for the kinds of little toys and fun projects we write together in this class, in the real world of software design every piece of information you collect is something you're now responsible for keeping safe, so the less you collect, the better. You may have already experienced how often signing up for services asks for information you don't want to give and they're bad at protecting!

Make it yours. Write a short program that asks for at least two pieces of information and produces something you'd actually want to read — a tiny event announcement, a two-line poem, a museum label, a recipe scaler, or a trip estimate. Include:

  • descriptive variable names,
  • at least one useful prompt,
  • at least one f-string, and
  • output that makes sense without seeing your source code.
