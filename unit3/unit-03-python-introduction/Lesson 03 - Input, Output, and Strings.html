Lesson 3 - Input, Output, and Strings

In this lesson you'll learn how to:

  • Collect text with input() and store the returned value.
  • Convert number-shaped text with int() or float().
  • Create readable output with print() and f-strings.
  • Design prompts and output that tell a user what the program needs and what it produced.

From a speech to a conversation

A program made of nothing but fixed print() calls delivers the same speech every time you run it. Input is what turns the speech into a conversation. The built-in input() function shows a prompt, waits for the user to type something, and hands whatever they typed back to the program:

name = input("What name would you like me to use? ")
print("Hello", name)

That assignment matters. If you write input("Name: ") without storing the result, Python still politely waits for an answer — and then the answer evaporates, because the program never gave it a name. Functions can produce values; assignment is how we keep them.

Input always begins as text

Even when a user types 25, input() gives you the string "25". Which is fair enough — a keyboard sends characters, and Python can't guess whether 25 is an age, a bus route, or part of a password. If we're planning to do arithmetic, we have to convert explicitly:

age_text = input("How old are you? ")
age = int(age_text)
age_next_year = age + 1
print(age_next_year)

The shorter form nests the function calls:

age = int(input("How old are you? "))

Reach for int() when only whole numbers make sense, and float() when a fractional value is reasonable:

people = int(input("How many people? "))
distance_miles = float(input("Distance in miles: "))

If the user types three where int() expects number-shaped text, Python raises a ValueError. That doesn't make the user “bad input.” It means our program has no plan yet for an entirely possible response. We'll build input-validation loops in Unit 4.

Build clear messages with f-strings

An f-string is just a string with the letter f in front of its opening quotation mark. Anything inside curly braces gets evaluated and dropped into the text:

title = input("Title of your tiny publication: ")
pages = int(input("How many pages? "))
print(f"Your publication '{title}' will have {pages} pages.")

Unlike concatenation, an f-string will happily include numbers without you converting them to strings by hand. The braces can even hold a small expression:

print(f"Printing two copies will require {pages * 2} page-sides.")

For money and measurements, a little formatting makes output much easier to read. :.2f asks for exactly two digits after the decimal point:

cost = 7.5
print(f"Estimated cost: ${cost:.2f}")

Formatting only changes how the value is displayed, not the stored value itself — cost is still the number 7.5.

A complete small program

Here's the meal-sharing idea from Lesson 1 as actual running Python. The pseudocode maps onto the code in the same order:

# Input
meal_total = float(input("Total cost of the meal in dollars: $"))
number_of_people = int(input("How many people are sharing the cost? "))

# Process
cost_per_person = meal_total / number_of_people

# Output
print(f"Each person pays ${cost_per_person:.2f}.")

A line beginning with # is a comment. Python ignores comments completely; they're notes for the people reading the code. Good comments explain a purpose or a non-obvious choice — they don't need to translate every single line into English.

Predict, run, investigate, modify.

  1. Predict the output for a $48 meal shared by 4 people.
  2. Run that case and compare the result with your prediction.
  3. Run a case where the result does not divide evenly, such as $20 shared by 3.
  4. Add an input for a tip percentage and include the tip before dividing.
  5. Change at least one prompt so the expected unit is unmistakable.

The user interface is part of the program

Your prompts and output are a tiny user interface, and a user interface shouldn't make anyone guess. Compare input("Number? ") with input("Trip distance in miles: ") — the second one says what it wants and in what unit. Output deserves labels too: printing a bare 12.5 quietly assigns the user homework, because now they have to remember what 12.5 was supposed to represent.

Clear text is also an accessibility feature. Don't communicate an important result only through color, spacing, emoji, or a picture. A screen reader can announce "Estimated travel time: 35 minutes" directly, while a message like "Result: red" may mean nothing at all without the surrounding visual context.

And programs should only ask for information they actually need. A zine generator may need a preferred display name; it probably doesn't need a legal name, birth date, or email address. Every piece of data you collect is a piece of data you're now responsible for.

Make it yours. Write a short program that asks for at least two pieces of information and produces an intentional text artifact — a tiny event announcement, a two-line poem, a museum label, a recipe scaler, or a trip estimate. Include:

  • descriptive variable names,
  • at least one useful prompt,
  • at least one f-string, and
  • output that makes sense without seeing your source code.
