Expressions produce values

An expression is any bit of code Python can evaluate to produce a value. A literal like 5 is an expression. So are price * quantity and input("Name: "). Expressions can be stored, displayed, or tucked inside larger expressions.

Two kinds of division solve different problems

Ordinary division answers “what's the quotient, fractional part and all?” Floor division and remainder answer a different question: “how many complete groups fit, and what's left over?”

minutes = 135
hours = minutes // 60
minutes_left = minutes % 60
print(f"{minutes} minutes is {hours} hours and {minutes_left} minutes.")

Since 60 fits into 135 two complete times with 15 left over, the program prints 135 minutes is 2 hours and 15 minutes. This same pair of operators can turn inches into feet-and-inches, pack objects into full boxes, or tell you whether a number is even:

number = 18
remainder_after_pairs = number % 2
print(remainder_after_pairs)  # 0 means no item was left without a partner

In Unit 4, number % 2 == 0 will become a complete yes-or-no question.

Order of operations and units

Python follows the order of operations you learned in math class: parentheses first, then exponents, then multiplication and division, then addition and subtraction, with same-level operators normally going left to right. Parentheses are a good habit even when they're not strictly required, because they make the grouping you intended visible:

average = (score_1 + score_2 + score_3) / 3

Without those parentheses, only score_3 would be divided by 3 before the other scores were added on. A program can run without a single error and still compute the wrong thing.

Units are part of the calculation, too. Adding 3 hours to 12 miles doesn't mean anything, but Python will cheerfully add the bare numbers for you anyway. Put units in variable names, prompts, or comments, and convert values to compatible units before combining them.

Replace unexplained numbers with named constants

A named constant is a variable whose value isn't supposed to change while the program runs. Python doesn't actually enforce this — it's the honor system — so programmers write these names in ALL_CAPS to signal the intent:

TIP_RATE = 0.18

meal_cost = float(input("Meal cost before tip: $"))
tip = meal_cost * TIP_RATE
total = meal_cost + tip
print(f"Tip: ${tip:.2f}")
print(f"Total: ${total:.2f}")

TIP_RATE explains what 0.18 means and keeps the policy in one place. Mind you, that number isn't a law of nature. A tax rate, a wage, an eligibility threshold, an estimated speed — any of these can depend on place, time, or circumstance. Good code makes its changeable assumptions visible and says where they came from.

When Python gives you a traceback

You're going to write code, hit Run, and get back red text. A lot. This is completely ordinary programming — an error message is evidence, not a grade on your ability. When Python stops, it usually prints a traceback, and there's a right order to read it in:

  1. Read the last line first. It names the error type and gives a short explanation.
  2. Find the line number that points into your code.
  3. Compare what that line needs with the values and names it actually has.
  4. Change one thing, then run again.
price = input("Price: $")
tax = price * 0.08
print(tax)
Traceback (most recent call last):
  File "program.py", line 2, in <module>
    tax = price * 0.08
TypeError: can't multiply sequence by non-int of type 'float'

The last line says TypeError: the operation doesn't fit the types involved. input() gave us a string, so the fix is to convert it: price = float(input("Price: $")).

Four common messages

  • SyntaxError or IndentationError: Python can't even make sense of the program's grammar. Look for a missing quote, parenthesis, or colon, or indentation that doesn't line up.
  • NameError: Python has never heard of a name you used. Check for a typo, a capitalization slip, or a variable used before it was assigned.
  • TypeError: an operation doesn't make sense for the kinds of values involved — adding a string and an integer, say.
  • ValueError: the requested conversion is reasonable in general, just not for this particular value — int("twelve") being the classic.

When no error message appears

A logic error lets the program run just fine — it simply produces a wrong answer. Suppose a discount program says:

DISCOUNT_RATE = 0.20
original_price = 50.00
sale_price = original_price + original_price * DISCOUNT_RATE
print(f"Sale price: ${sale_price:.2f}")

Python reports no problem at all, but a 20% discount on $50 should be $40, not $60 — that operator should be subtraction. Only a test with a known expected answer will catch this kind of mistake.

Useful test cases include a normal case, a boundary or unusual case, and — once the program is ready to handle it — an invalid case. Write the expected result down before you run, so the computer's confident-looking output doesn't talk you into agreeing with it.
