Expressions produce values

An expression is any piece of code Python can be evaluated to get a value. The literal 5 is an expression. So is price * quantity, and so is input("Name: "). Expressions can be stored in variables, printed, or tucked inside bigger expressions. Here are the arithmetic operators you have to work with:

OperatorMeaningExampleResult
+addition7 + 29
-subtraction7 - 25
*multiplication7 * 214
/ordinary division7 / 23.5
//floor division7 // 23

**exponent7 ** 249

Two kinds of division

Why does Python have two division operators? Because they perform two different computations about two different kinds of number. Ordinary / computes "what's the quotient, decimals and all?" for numbers that can have decimal points. Floor division // and remainder % together let you compute the answer to "how many times does this go into that?" and "what's the remainder?"

minutes = 135
hours = minutes // 60
minutes_left = minutes % 60
print(f"{minutes} minutes is {hours} hours and {minutes_left} minutes.")

60 goes into 135 twice with 15 left over, so this prints 135 minutes is 2 hours and 15 minutes. The same pair of operators turns inches into feet-and-inches, tells you how many full boxes you can pack, or checks whether a number is even:

number = 18
remainder_after_pairs = number % 2
print(remainder_after_pairs)  # 0 means no item was left without a partner

The remainder operator is one of those small tools that shows up everywhere once you know to look for it. In Unit 4 we'll write number % 2 == 0 as an actual yes-or-no question.

Order of operations and units

Python follows the same order of operations as math class: parentheses, then exponents, then multiplication and division, then addition and subtraction, going left to right among operators at the same level. Even when parentheses aren't strictly required, they're a good habit, because they show the reader what grouping you meant:

average = (score_1 + score_2 + score_3) / 3

Leave the parentheses out and Python divides only score_3 by 3, then adds the other two scores on. While you and I can easily infer that the parentheses should have been there because we know what an average is, the Python interpreter doesn't make inferences. That's what we want, right? At some point you need the instructions to the computer to be very predictable. The downside is that this "do what I said because you don't know what I mean" means that a program can run without a single complaint and still compute the wrong thing.

Units are part of a calculation too, even though Python has no idea they exist. Adding 3 hours to 12 miles is meaningless, but Python sees 3 + 12 and gives you 15 without a second thought. Keeping units straight is your job: put them in variable names, prompts, or comments, and convert to matching units before combining anything.

Give your data names

A named constant is a variable whose value isn't supposed to change while the program runs. Python doesn't actually enforce this (it's the honor system), so programmers write these names in ALL_CAPS as a signal that says "don't reassign me":

TIP_RATE = 0.18

meal_cost = float(input("Meal cost before tip: $"))
tip = meal_cost * TIP_RATE
total = meal_cost + tip
print(f"Tip: ${tip:.2f}")
print(f"Total: ${total:.2f}")

Compare that to a bare 0.18 sitting in the middle of a calculation. TIP_RATE says what the number is for, and it puts the policy in exactly one place, so if it changes you change only one line. Good code makes its adjustable assumptions visible!

When Python shows you errors

You are going to write code, hit Run, and get red text back. A lot. This happens to everyone who programs, at every level, forever, so let's make sure you know how to read it. When Python stops on an error it prints a traceback explaining what went wrong. Here's some hints on how to read and use it:

  1. Read the last line first. It names the error type and gives a short explanation.
  2. Find the line number that points into your code.
  3. Compare what that line needs with the values and names it actually has.
  4. Change one thing, then run again.
price = input("Price: $")
tax = price * 0.08
print(tax)
Traceback (most recent call last):
  File "program.py", line 2, in <module>
    tax = price * 0.08
TypeError: can't multiply sequence by non-int of type 'float'

The last line says TypeError: the operation doesn't work on these types. Line 2 is trying to multiply, and one of the things being multiplied came from input(), which we know hands back a string. So the fix is to convert: price = float(input("Price: $")).

Four errors you'll meet a lot

  • SyntaxError or IndentationError: Python can't even make sense of the program's grammar. Look for a missing quote, parenthesis, or colon, or indentation that doesn't line up.
  • NameError: Python has never heard of a name you used. Check for a typo, a capitalization slip, or a variable used before it was assigned.
  • TypeError: an operation doesn't make sense for the kinds of values involved, like adding a string and an integer.
  • ValueError: the conversion you asked for is reasonable in general, just not for this particular value. int("twelve") is the classic.

When there's no error message at all

A logic error is the sneakier kind. The program runs fine and produces an answer; the answer is just wrong. Say a discount program does this:

DISCOUNT_RATE = 0.20
original_price = 50.00
sale_price = original_price + original_price * DISCOUNT_RATE
print(f"Sale price: ${sale_price:.2f}")

Python has no complaints. But a 20% discount on $50 should give $40, not $60, so that + should have been a -. Nothing in Python can catch this for you, because Python has no idea what a discount is. The only thing that catches it is a test with a known right answer.

Good tests include a normal case, a boundary or unusual case, and, once the program is ready for it, an invalid case. And write down the expected result before you run the program. Computers print their answers with total confidence, and it is surprisingly easy to look at a wrong number and think "sure, that seems about right."
